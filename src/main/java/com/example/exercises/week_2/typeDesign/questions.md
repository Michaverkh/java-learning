1. Почему класс с подходящими methods не реализует Java interface автоматически? - потому что в джава тип должен быть
   явно превязан к сущности. В джава нет "утиной типизации", как например в TS

   > **Комментарий:** В целом верно. Точнее: система типов Java номинативная — класс должен явно объявить
   > `implements SomeInterface`. Одного совпадения набора методов недостаточно. TypeScript в этом сравнении лучше
   > называть структурно типизированным языком, а не просто языком с «утиной типизацией».

2. Когда abstract class лучше interface? - Когда есть необходимость в статических методах и хранении служебных для
   класса данных

   > **Комментарий:** Частично верно. Статические методы не являются причиной выбора: они допустимы и в interface.
   > Abstract class уместнее, когда родственным подтипам нужны общее состояние экземпляра, constructor, `protected`
   > members или общая частичная реализация алгоритма. При этом класс может наследоваться только от одного класса.

3. Какие три разных ограничения выражает `final`? - final запрещает присвоить переменной друшую ссылку, также нельзя
   унаследоваться от класса, объявленного через final

   > **Комментарий:** Ответ неполный. `final` у variable/field запрещает повторное присваивание, у method — override,
   > у class — наследование. При этом `final`-ссылка и `final`-класс сами по себе не делают объект неизменяемым.

4. Чем sealed interface отличается от обычного interface? - interface жестко фиксирует название . типы параметров и
   возвращаемого значения метода . А sealed фиксирует только названия разрешенных методов

   > **Комментарий:** Неверно. И обычный, и sealed interface одинаково задают сигнатуры методов. Отличие в границе
   > расширения: обычный interface может реализовать любой подходящий класс, а sealed interface перечисляет разрешённые
   > прямые подтипы через `permits`. Благодаря закрытому набору вариантов compiler может, например, проверить полноту
   > `switch`.

5. Почему record не гарантирует глубокую immutability? - потому что поля record могут хранить ссылки на изменяемые
   объекты.

   > **Комментарий:** Верно. Ссылку в component нельзя заменить, но объект по ней может измениться. Для коллекций и
   > других изменяемых компонентов часто нужны защитные копии, например `List.copyOf(source)`.

6. Почему `BigDecimal` component требует решения о scale до использования сгенерированного record equality? - потому что
   BigDecimal объявленные со значениями "0.0001" "0.001" могут привратиться в 0 и 0 посде scale

   > **Комментарий:** Неверно. Главная проблема не в округлении до нуля, а в том, что `BigDecimal.equals` учитывает
   > scale: `new BigDecimal("10.0")` и `new BigDecimal("10.00")` не равны через `equals`, хотя `compareTo` считает их
   > численно равными. Record использует `equals` компонентов, поэтому scale нужно нормализовать в constructor либо
   > явно реализовать согласованные `equals` и `hashCode`.

7. Почему enum сравнивают через `==`? - Потому что num хранит константы

   > **Комментарий:** Идея верная, но её стоит уточнить: каждая enum-константа — единственный экземпляр своего enum-типа.
   > Поэтому сравнение ссылок через `==` корректно и безопасно, в том числе когда одна из переменных равна `null`.

8. Почему нельзя хранить enum через `ordinal()`? - ordinal () указывает на порядковый номер, а он может меняться

   > **Комментарий:** Верно. Добавление, удаление или перестановка констант меняет `ordinal()`, из-за чего сохранённые
   > данные начинают означать другое значение. Для хранения нужен стабильный строковый или явно заданный код.

9. Когда sealed hierarchy лучше enum? - когда важно зафиксировать нейминг будущих методов, а не хранить фиксированные
   значения

   > **Комментарий:** Неверно. Sealed hierarchy лучше, когда закрытые варианты имеют разные данные или существенно
   > разное поведение: например, `Succeeded(TransferId)` и `Rejected(RejectionReason)`. Enum лучше для фиксированного
   > набора singleton-значений одного типа, например статусов или валют.

10. Почему signature `Account findById(...)` не сообщает Java compiler о nullability? - потому что Account не обернут в
    Optional<>

    > **Комментарий:** Вывод практический верный, но причина глубже: обычная система типов Java не различает `Account`
    > и «nullable Account», поэтому метод с таким return type формально может вернуть и объект, и `null`. `Optional<Account>`
    > — один из способов явно выразить нормальное отсутствие результата в контракте.

11. Почему `Optional` чаще подходит для return type, чем для parameter или field? - для parameter или field лучше явно
    обработать null

    > **Комментарий:** Ответ требует уточнения. В return type `Optional` заставляет вызывающий код явно обработать
    > отсутствие результата. В parameter он обычно лишь добавляет wrapper в месте вызова; яснее предложить перегрузки,
    > разные команды или осмысленный nullable-контракт на границе системы. В fields он усложняет модель, сериализацию и
    > работу некоторых framework. Кроме того, сама ссылка на `Optional` теоретически всё ещё может оказаться `null`.

12. Чем отличаются `Optional.of` и `Optional.ofNullable`? - Optional.of запрещает null, а Optional.ofNullable приводит
    null к empty. Только вопрос зачем тогда нужен Optional.of если концепция Optional подразумевает отсутствие значения

    > **Комментарий:** Ответ верный. `Optional.of(value)` нужен, когда значение по контракту обязано существовать: он
    > сразу обнаружит нарушение контракта через `NullPointerException`, вместо того чтобы ошибочно превратить баг в
    > допустимое отсутствие. `ofNullable` используют именно на границе, где `null` ожидаем и означает отсутствие.

13. Почему `orElseGet` может быть правильнее `orElse`? лямбда внутри orElse вызывается сразу. Если он дорогой, лучше
    использовать orElseGet. В этом случае лямбда выполнится только в случае остутствия значения Optional

    > **Комментарий:** Смысл верный, но формулировка неточна: `orElse` принимает готовое значение, а не `Supplier`.
    > Поэтому выражение в `orElse(expensiveCall())` вычисляется до вызова метода даже при непустом `Optional`.
    > `orElseGet(() -> expensiveCall())` вызывает supplier только при отсутствии значения.

14. Почему `List<PremiumAccount>` не является `List<Account>`? - потому что это два разных типа. Иначе мы могли бы
    добавлять Account account в List<PremiumAccount> что не совсем корректно

    > **Комментарий:** Верно. Java generics инвариантны именно для сохранения type safety: если бы такое присваивание
    > разрешалось, через ссылку `List<Account>` в настоящий `List<PremiumAccount>` можно было бы добавить обычный
    > `Account`.

15. Что значит PECS? Producer Extends — источник значений: `? extends T`; - Consumer Super — приёмник значений:
    `? super T`.

    > **Комментарий:** Верно. Дополнение: PECS применяется к роли параметра конкретной операции. Одна и та же коллекция
    > в разных методах может выступать и producer, и consumer.

16. Чем `List<?>` отличается от `List<Object>`? List<?> позволяет безопасно читать элементы как Object, но не позволяет
    добавлять обычные значения.

    > **Комментарий:** Верно, но стоит добавить вторую половину сравнения. `List<?>` означает список неизвестного типа и
    > может ссылаться, например, на `List<String>`. `List<Object>` — список именно `Object`: в него можно добавлять
    > значения любых reference types, но переменной такого типа нельзя присвоить `List<String>`.

17. Что происходит с unbounded `T` после erasure? После erasure T без bound превращается в Object; compiler сохраняет
    type safety на местах использования и при необходимости вставляет cast:

    > **Комментарий:** Верно. Лишнее двоеточие в конце не влияет на смысл. Для bounded type parameter стирание происходит
    > до его первого bound, а не обязательно до `Object`.

18. Почему разрешён `instanceof List<?>`, но запрещён `instanceof List<String>`? List<String> и List<Account> стираются
    до List

    > **Комментарий:** Верно. Runtime может проверить, что объект является `List`, но не способен проверить тип его
    > элементов. `List<?>` не требует такой проверки: wildcard как раз означает неизвестный тип элементов.

19. Почему нельзя перегрузить `process(List<Account>)` и `process(List<Transfer>)`? потому что перегрузка выбирается уже
    в рантайме, а там происходит erasure, поэтому JVM увидит process (List)` и `process (List)

    > **Комментарий:** Итог про одинаковые сигнатуры после erasure верный, но overload выбирается compiler на этапе
    > компиляции, а не в runtime. Оба метода получили бы один JVM descriptor `process(List)`, поэтому class file не может
    > содержать такую пару методов.

20. Что такое heap pollution? Heap pollution возникает, когда переменная parameterized type ссылается на объект с
    несовместимым содержимым

    > **Комментарий:** Верно. Обычно это становится возможным из-за raw types, unchecked casts или небезопасной работы с
    > generic varargs, а проявиться может позже как `ClassCastException` в месте чтения.

21. Зачем compiler создаёт bridge methods? чтобы сохранить полиморфизм

    > **Комментарий:** Верно, но слишком кратко. После erasure сигнатура переопределяющего метода иногда перестаёт
    > совпадать с erased-сигнатурой базового generic-метода. Compiler создаёт синтетический bridge method с ожидаемой
    > erased-сигнатурой, который делает нужный cast и делегирует вызов настоящему методу, сохраняя override и dynamic
    > dispatch.

22. В каком смысле reflection видит generics, а в каком — нет? Reflection может увидеть generic declaration field или
    superclass, но произвольный экземпляр List<T> обычно не знает свой runtime argument.

    > **Комментарий:** Верно. Generic metadata объявлений может сохраняться в class file и читаться через специальные
    > reflection API, но runtime-объект `new ArrayList<String>()` обычно не хранит информацию, позволяющую отличить его от
    > `new ArrayList<Account>()`.

23. Какие возможности TypeScript generics нельзя напрямую перенести в Java? Conditional/mapped types и keyof, indexed
    access

    > **Комментарий:** Верно. Это хорошие примеры более выразительных операций TypeScript на уровне типов. Также в Java
    > нет прямых аналогов структурных generic constraints и многих преобразований типов, построенных на union types.

24. Почему отдельные records `AccountId` и `TransferId` полезнее общего `UUID`? наверное для того чтобы нельзя было
    сделать так: AccountId accountId; List<TransferId> list.add (accountId) - будет ошибка

    > **Комментарий:** Основная идея верна. Главная практическая польза — compiler не позволит случайно передать
    > `TransferId` в метод, ожидающий `AccountId`, хотя внутри обоих находится `UUID`. Такие nominal wrappers также дают
    > каждому идентификатору собственное имя, место для проверки инвариантов и связанные с ним методы. Пример со списком
    > тоже демонстрирует несовместимость типов, но чаще ошибка возникает непосредственно в параметрах repository или
    > service methods.
