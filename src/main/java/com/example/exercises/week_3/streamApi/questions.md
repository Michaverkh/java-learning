1. Почему `stream().filter(...)` без терминальной операции не фильтрует список? - потому что лямбда внутри вызывается
   только после вызова терминальной опирации

   > Комментарий Codex: Верно насчёт ленивости. Важно также, что `filter` не изменяет исходный список даже после терминальной операции: он создаёт новый поток с подходящими элементами.
2. Чем отличается `map` от `flatMap` по типу результата? При работе с вложенными списками обычный map при должной лямбде
   делает из вложенных листов потоки. flatMap инициализирует один поток предварительно "развернув" вложенные массивы в
   линейную струткуру

   > Комментарий Codex: Направление мысли правильное. Точнее: `map(List::stream)` преобразует `Stream<List<T>>` в `Stream<Stream<T>>`, то есть вложенные потоки становятся элементами. `flatMap(List::stream)` возвращает `Stream<T>` и включает элементы вложенных списков в один общий поток.
3. Почему нельзя повторно вызвать `count` и `toList` на одном потоке? Потому что после первого раза выполение потока
   может уже завершиться

   > Комментарий Codex: Верно. Терминальная операция потребляет поток, поэтому повторный вызов обычно приведёт к `IllegalStateException`. Для нового обхода нужно создать новый поток из исходной коллекции.
4. В каких случаях `findFirst` не обойдёт весь источник, а сортировка перед ним потребует его прочитать? - findFirst
   прекращает поиск после первого результата.

   > Комментарий Codex: Ответ верный, но неполный. `findFirst` может завершиться раньше на упорядоченном потоке без операций, требующих накопления данных, например после `filter`. Но `sorted()` должна прочитать все элементы, чтобы определить самый первый элемент в отсортированном порядке, поэтому последующий `findFirst` уже не сокращает этот обход.
5. Почему `allMatch` возвращает `true` для пустого потока и где это может скрыть ошибку? МОжет дать ошибку когда нам
   нужно узнать что записи вообще существуют

   > Комментарий Codex: Верно. Нет элемента, который нарушил бы условие, поэтому результат — `true`. Ошибка возможна, если по этому значению сделать вывод «все записи корректны», хотя записей не было вовсе; при необходимости отдельно проверь их наличие.

6. Чем оборот отличается от чистого изменения баланса?

   > Комментарий Codex: Ответ отсутствует. Оборот показывает объём поступлений и расходов отдельно, а чистое изменение — их алгебраическую сумму. Например, поступление `1000.00` и расход `-1000.00` дают оборот `2000.00`, но чистое изменение `0.00`.
7. Зачем `reduce` нужны нейтральное значение и ассоциативность? Для того чтобы всегда возвращать результат, а не null

   > Комментарий Codex: Это только часть ответа. Нейтральное значение позволяет корректно обработать пустой поток, например вернуть `0` для суммы. Ассоциативность нужна, чтобы результат не зависел от группировки элементов, в том числе при параллельном выполнении. `reduce` без начального значения возвращает `Optional`, а не `null`.
8. Почему изменяемый список лучше накапливать через `collect`, а не `reduce`? Первый вариант работает последовательно,
   но усложняет контракт и станет небезопасным при параллельном добавлении в ArrayList. Изменение отдельного внутреннего
   контейнера в collect предусмотрено механизмом накопления: обычный коллектор может создать независимые контейнеры для
   частей данных и затем объединить их. Изменять один общий список из лямбды — другое поведение.

   > Комментарий Codex: Хороший ответ. Уточнение: `collect` не обязательно работает последовательно; его контракт как раз задаёт создание и объединение независимых контейнеров, поэтому он подходит и для параллельного потока. `reduce` предназначен прежде всего для сведения элементов к одному значению.
9. Что случится при повторном ключе в `toMap` без функции объединения? он перезапишет value этого ключа

   > Комментарий Codex: Здесь нужно исправить: значение не перезапишется. `Collectors.toMap` без функции объединения выбросит `IllegalStateException` при повторном ключе. Правило выбора значения нужно задать явно третьим аргументом `toMap`.
10. Почему обязательный аудит нельзя помещать в `peek`? Из за терминальных опираций. Они могут прервать обход списка и
    не все значения могут быть обработаны

    > Комментарий Codex: Верно. `peek` годится для наблюдения и отладки, но не для обязательного действия: короткозамыкающие операции, например `findFirst`, могут не обработать часть элементов. Кроме того, без терминальной операции `peek` вообще не выполнится.
11. Почему `limit(100)` после `findAll()` не ограничивает загрузку из БД? в этом случае мы ограничиваем список уже после
    получения данных из бд

    > Комментарий Codex: Верно. База данных уже вернула все строки в `findAll()`, а `limit` ограничивает только их дальнейшую обработку в памяти. Ограничение нужно передавать в запрос к базе: через пагинацию, `LIMIT` или другой механизм конкретного хранилища.
12. Почему `parallelStream()` не обеспечивает атомарность перевода? стримы не обеспечивают многопоточность.

    > Комментарий Codex: Здесь формулировка неточна: `parallelStream()` как раз может выполнять части обработки в нескольких потоках. Но он не даёт транзакцию, блокировки и согласованное изменение двух балансов. Атомарность перевода обеспечивают граница транзакции и механизмы хранилища, а не Stream API.
