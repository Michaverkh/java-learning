1. Чем starter отличается от автоконфигурации и управления версиями? Starter — зависимость, которая приводит нужный
   набор библиотек для определённой задачи.

   **Комментарий: частично верно.** Starter ты описал правильно, но вопрос просит различить три механизма.
   Starter подключает набор библиотек; автоконфигурация создаёт и настраивает beans при выполнении условий;
   управление версиями через родительский POM или BOM задаёт согласованные версии зависимостей.
   Например, starter добавляет библиотеки для HTTP, автоконфигурация настраивает веб-инфраструктуру,
   а управление версиями определяет, какие версии библиотек использовать.

2. Почему `server.port` не запускает сервер без веб-зависимостей? server.port само по себе не превращает консольное
   приложение в сервер. Для этого нужны соответствующие библиотеки и конфигурация.

   **Комментарий: верно.** `server.port` — значение настройки для сервера. Оно используется при создании
   веб-сервера, но само не добавляет его реализацию и не включает веб-приложение.

3. Какие три возможности объединяет `@SpringBootApplication`? @SpringBootConfiguration — помечает основной класс
   конфигурации, специализируя @Configuration; @EnableAutoConfiguration — включает подбор автоконфигураций;
   @ComponentScan — включает поиск компонентов начиная с пакета основного класса

   **Комментарий: верно.** По умолчанию сканируется пакет класса с `@SpringBootApplication` и его подпакеты.
   В нашем случае это `com.example.wallet`, поэтому соседний `com.example.exercises` в эту область не входит.

4. Почему собственный bean не всегда автоматически заменяет инфраструктурный? Потому что собственный bean может
   находиться за пределами сканирования SpringBootApplication

   **Комментарий: основная причина другая.** Если компонент не найден сканированием и не зарегистрирован другим
   способом, он вообще не стал bean. Но даже зарегистрированный bean не обязан отключать автоконфигурацию:
   это зависит от её условий. Например, `@ConditionalOnMissingBean(SomeType.class)` разрешает создание
   стандартного bean только при отсутствии bean указанного типа. Если твой bean удовлетворяет этой проверке,
   стандартный не создаётся. Без подходящего условия автоматической замены может не быть.
   См. [условия автоконфигурации](https://docs.spring.io/spring-boot/reference/using/auto-configuration.html).

5. Почему `application-test.yml` недостаточно для активации `test`? Maven profile и Spring profile относятся к разным
   механизмам: сборке и настройке приложения соответственно.

   **Комментарий: утверждение верное, но не отвечает на вопрос.** Имя `application-test.yml` означает
   «загрузить эти настройки, когда профиль `test` активен», а не «активировать `test`».
   Профиль нужно включить отдельно: например, через `@ActiveProfiles("test")` в тесте или параметр
   `--spring.profiles.active=test` при запуске. Сам файл должен быть доступен приложению:
   файл из `src/test/resources` доступен тестам, но не включается в основной JAR.

6. Какое имя переменной соответствует `wallet.transfer.max-amount`? max-amount

   **Комментарий: неверно.** Здесь речь о переменной окружения: `WALLET_TRANSFER_MAXAMOUNT`.
   Точки заменяются подчёркиваниями, дефисы удаляются, буквы переводятся в верхний регистр.
   `max-amount` — только часть имени настройки в YAML. Для PowerShell пример задания переменной:
   `$env:WALLET_TRANSFER_MAXAMOUNT = "5000.00"`.

7. Что победит: профильный YAML, переменная окружения или аргумент `--...`? аргумент

   **Комментарий: верно.** Для одной и той же настройки в обычном запуске Boot приоритет среди этих источников:
   аргумент `--...` → переменная окружения → профильный YAML. Например, при значениях `7000`, `5000`
   и `100000` соответственно итоговый лимит будет `7000`.

8. Чем ошибка преобразования `abc` отличается от отрицательного лимита? В первом случае это Ошибка преобразования, во
   втором: Ошибка проверки ограничения

   **Комментарий: верно.** `abc` нельзя преобразовать в `BigDecimal`, поэтому корректное числовое значение
   ещё не получено. `-1.00` успешно преобразуется в `BigDecimal`, но затем нарушает `@DecimalMin`.
   В обоих случаях наше приложение должно отказать в запуске, однако причина и сообщение об ошибке различаются.

9. Почему нужны одновременно `@NotNull` и `@DecimalMin`? NotNull проверяет наличие значения, но не гарантирует что оно
   валидно

   **Комментарий: частично верно.** Нужно также объяснить обратную сторону: `@DecimalMin` считает `null`
   допустимым, поэтому без `@NotNull` отсутствие значения не нарушит это ограничение.
   Вместе они требуют наличия лимита и его значения строго больше нуля при
   `@DecimalMin(value = "0.00", inclusive = false)`.
   См. [описание ограничений Jakarta Validation](https://jakarta.ee/specifications/bean-validation/3.1/jakarta-validation-spec-3.1.pdf).

10. Проверит ли Jakarta Validation объект, созданный обычным `new`, без вызова валидатора? нет

    **Комментарий: верно.** Аннотации ограничений сами ничего не исполняют. Проверку должен запустить
    валидатор или интеграция с ним, как Spring Boot при связывании наших настроек с `@Validated`.
    Поэтому `new TransferProperties(null)` сам по себе не вызовет проверку `@NotNull`.

11. Почему корректный объект настроек ещё не гарантирует корректность перевода? Это только одно из условий

    **Комментарий: верно, но стоит конкретизировать.** Проверка настроек подтверждает допустимость самого
    лимита, например `1000.00`. Она не сравнивает с ним сумму конкретного перевода — это делает
    `TransferLimitPolicy`. Кроме лимита, `TransferService` проверяет положительность суммы, валюту,
    существование и активность счетов, различие отправителя и получателя, достаточность остатка.

12. Что произойдёт при изменении YAML после запуска приложения? Ничего. Чтобы изменения применились, приложение нужно
    перезапустить

    **Комментарий: верно для нашего приложения, но есть важное уточнение.** Если изменён исходный YAML
    в `src/main/resources`, а запуск выполняется через `java -jar`, нужно сначала пересобрать JAR,
    затем перезапустить приложение. Перезапуск прежнего JAR прочитает прежнюю копию настроек внутри него.
    Если изменён подключённый внешний YAML, достаточно перезапуска: пересборка не требуется.

13. Почему пароль в неактивном `application-prod.yml` внутри ресурсов всё равно попадёт в JAR? Имя профиля prod не
    защищает его содержимое: ресурс из src/main/resources попадёт в JAR независимо от того, активен профиль при сборке
    или нет.

    **Комментарий: верно.** При стандартной сборке Maven копирует ресурсы, а Spring выбирает активные
    профильные настройки уже при запуске. Неактивный файл остаётся внутри архива и доступен для извлечения.

14. Чем отличаются исходный YAML, ресурс в `target/classes` и внешний конфигурационный файл? в в `target/classes`
    попадает ресурс выбранной конфигурации. Про внешний конфигурационный файл не совсем понял.

    **Комментарий: здесь нужно исправить понимание сборки.** В `target/classes` копируются ресурсы
    из `src/main/resources`, включая файлы неактивных профилей. Выбор Spring-профиля не отбирает файлы для сборки.

    - **Исходный YAML** — файл проекта, например `src/main/resources/application-local.yml`, который ты редактируешь.
    - **Ресурс в `target/classes`** — его копия, подготовленная Maven для запуска и упаковки.
      При сборке Boot JAR она попадает внутрь архива в `BOOT-INF/classes`.
      Менять её вручную не стоит: следующая сборка может перезаписать изменения.
    - **Внешний конфигурационный файл** — отдельный YAML вне JAR, который приложение читает при запуске.
      Он позволяет менять настройки одного и того же собранного приложения без пересборки.

    Например, создай в корне проекта папку `local-config` и положи туда `application-local.yml`:

    ```yaml
    wallet:
      transfer:
        max-amount: "5000.00"
    ```

    Запусти приложение из корня проекта, явно добавив эту папку к местам поиска настроек:

    ```powershell
    java -jar target/java-learning-1.0-SNAPSHOT.jar --spring.profiles.active=local --spring.config.additional-location=file:./local-config/
    ```

    В этом примере внешний файл переопределит лимит из JAR на `5000.00`, если нет более приоритетного
    значения из переменной окружения или аргумента запуска. Остальные настройки сохранятся.
    Имя папки `local-config` выбрано произвольно: Boot узнаёт о ней из параметра `additional-location`.
    Папка должна существовать, иначе этот запуск завершится ошибкой.
    Тестовые ресурсы отдельно копируются из `src/test/resources` в `target/test-classes` и в основной JAR не входят.
    См. [источники настроек и их приоритеты](https://docs.spring.io/spring-boot/3.4/reference/features/external-config.html).
