# Неделя 10. Практика: JDBC, пул соединений и миграции

[← Подробный разбор](../../../../../../../lerning-materials/week-10/jdbc-connection-pool-and-migrations.md) ·
[Требования Wallet Service](../../wallet/technical-requirements.md)

## Результат практики

Переведи Wallet Service с in-memory хранилищ на PostgreSQL только настолько, насколько нужно для чтения данных через
`JdbcTemplate`. Схему создаёт Flyway; приложение не содержит `CREATE TABLE`, seed-скриптов и захардкоженного пароля.
Денежные операции и конкурентные переводы пока не реализуй: их транзакционные границы будут отдельной темой.

## 1. Локальная инфраструктура

1. Добавь `compose.yaml` с PostgreSQL, именованным volume и healthcheck.
2. Передавай пароль через `WALLET_DB_PASSWORD`; добавь локальный `.env` в `.gitignore`, если используешь файл.
3. Создай профиль `local`, который подключается к контейнеру. Не используй роль `postgres` как пользователя
   приложения.
4. Запусти контейнер и проверь готовность через `docker compose ps`.

**Критерий:** после перезапуска контейнера данные переживают restart; секрет не появляется в отслеживаемом файле и в
выводе приложения.

## 2. Зависимости и конфигурация

1. Добавь `spring-boot-starter-jdbc`, PostgreSQL JDBC Driver со scope `runtime`,
   `spring-boot-starter-flyway` и модуль `flyway-database-postgresql`.
2. Настрой `spring.datasource` через переменные окружения с безопасными локальными значениями только для URL и имени
   пользователя.
3. Явно установи небольшой локальный `maximum-pool-size`, например 8, и `connection-timeout` 3 секунды.
4. Убедись, что Spring создал один `DataSource`, а не ручной дубликат.

**Критерий:** приложение не запускается, если пароль не задан; после его задания получает соединение из HikariCP.

## 3. Первая миграция

1. В `src/main/resources/db/migration` создай `V1__create_wallet_tables.sql`.
2. Создай таблицы `client`, `account`, `transfer`, `ledger_entry`, `idempotency_record`, `outbox_event`, `audit_log`.
3. Перенеси критичные ограничения из требований: внешние ключи, уникальность внешнего идентификатора клиента,
   неотрицательный баланс, положительную сумму, разные счета перевода, нужную уникальность идемпотентности.
4. Не добавляй в миграцию `DROP TABLE`, тестовые UUID и данные SQL-лаборатории.

**Критерий:** на чистой БД миграция выполняется, а повторный старт приложения не применяет её второй раз. В таблице
`flyway_schema_history` есть успешная запись о `V1`.

## 4. Чтение через JdbcTemplate

1. Реализуй инфраструктурный адаптер чтения баланса счёта по `UUID` через `JdbcTemplate`.
2. Реализуй чтение истории для счёта за полуоткрытый период `[from, to)` с лимитом размера страницы. Верни только
   поля, нужные DTO, а не `SELECT *`.
3. Все значения пользователя передавай параметрами. Направление сортировки выбирай закрытым `enum` или фиксированным
   SQL, не строкой из HTTP-параметра.
4. Для отсутствующего счёта явно выбери контракт (`Optional` или доменное исключение) и согласуй его с существующим
   application service.

**Критерий:** SQL находится в адаптере persistence, не в controller; в коде нет конкатенации значений пользователя
с SQL; connection, statement и result set не закрываются вручную поверх `JdbcTemplate`.

## 5. Миграция вперёд

1. После успешного `V1` добавь `V2__add_transfer_description.sql`, которая добавляет nullable `description` к
   `transfer`.
2. Проверь, что `V1` не менялся, а в истории Flyway появились две успешные версии.
3. Объясни в `notes.md`, как ты добавил бы обязательное поле без остановки совместимости: расширение схемы,
   заполнение старых данных, переключение кода, ограничение в следующем релизе.

**Критерий:** история миграций линейна, старая версия файла не переписана, а миграция безопасна для существующих
строк.

## 6. Диагностика

Ответь в `notes.md`:

1. Почему не закрытый connection приводит к таймауту HikariCP, хотя PostgreSQL продолжает работать?
2. Почему увеличение `maximum-pool-size` не исправляет медленный запрос или блокировку?
3. Чем отличаются SQL injection через значение и небезопасный выбор имени столбца для сортировки?
4. Почему `flyway repair` не является обычным способом исправить изменённую миграцию?
5. Что произойдёт с уже записанными данными при `docker compose down -v`?
