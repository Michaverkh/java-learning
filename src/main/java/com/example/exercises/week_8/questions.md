- Почему перевод — отдельный ресурс, а баланс нельзя менять обычным редактированием счёта? перевод — отдельный ресурс
  так как мы должны хранить историю переводов. баланс нельзя менять обычным редактированием счёта так как это
  транзакионная опирация затрагивающая несколько действий.

  **Комментарий:** Верно по направлению, но история — не единственная причина. Перевод имеет собственные
  идентификатор, участников, сумму и результат; его можно получить отдельным запросом. Прямая замена баланса скрывает
  причину изменения и обходит правила денежных операций. Даже пополнение одного счёта должно согласованно менять
  баланс и создавать запись истории. Для перевода дополнительно нужно атомарно изменить оба счёта.

- В чём разница отсутствующего поля и `null` в Merge Patch и как это сохранить при привязке к Java? отсутствующего поля
  -значит ничего не поменялось. null - удалить значение. В Java можно проверить существует ли поле в объекте. И если да,
  равно ли оно null. Это две разные проверки.

  **Комментарий:** Семантика верная: отсутствие поля означает «оставить прежнее значение», а `null` в Merge Patch
  означает удаление свойства. Удаление обязательного поля сервер должен отклонить. В Java важно, как разобрано тело:
  обычный DTO с полем `String name` обычно превращает и отсутствие, и явный `null` в Java `null`. Для различения можно
  использовать `JsonNode`: сначала `has("name")`, затем `get("name").isNull()`.

- Почему PATCH с добавлением в массив может не быть идемпотентным? Допустим приоднократном выполнении запросы мы
  добавляем элемент в массив. Далее делаем такой-же запросс и дубль не добавляется.

  **Комментарий:** Здесь наоборот: обычное добавление не проверяет дубли автоматически. Например, JSON Patch
  `{"op":"add","path":"/tags/-","value":"new"}` добавляет элемент в конец массива. Повтор этой операции
  добавит ещё один `"new"`, поэтому эффект одного и двух запросов различается. Отдельная защита от повторов могла бы
  предотвратить дубль, но сама операция `add` этого не гарантирует. В JSON Merge Patch массив заменяется целиком —
  это другой сценарий.

- Что изменится для интерфейса, если перевод начнёт возвращать `202` вместо `201`? Какого именно интерфейса, уточни
  вопрос

  **Комментарий:** Имеется в виду пользовательский интерфейс приложения, вызывающего API, например React-приложение.
  В текущем контракте `201` означает, что синхронный перевод завершён. `202` означает, что запрос принят в обработку,
  но завершение ещё не подтверждено. Интерфейс должен показать ожидание, а затем узнать итог через отдельный запрос
  состояния или уведомление сервера. Только после подтверждения можно показать успех; возможен и окончательный отказ.
  Для этого backend должен предоставить способ узнать результат. Создавать React-приложение в рамках задания не нужно.

- Почему два запроса с разными ключами идемпотентности всё равно могут нарушить баланс? Они могут выполнятся в одно и
  то-же время.

  **Комментарий:** Верно, но уточни механизм нарушения. Разные ключи обозначают разные команды, поэтому защита от
  повторов разрешит обе. При балансе `100.00` два списания по `80.00` могут одновременно прочитать `100.00` и пройти
  проверку средств. Без атомарной защиты оба могут считаться успешными: возможны отрицательный баланс или потеря
  одного изменения и расхождение с историей. Транзакции с подходящими блокировками либо проверкой версии должны
  обеспечить успех только одного списания и итоговый баланс `20.00`.

- Почему проверка ETag только в контроллере не защищает от гонки? Это как-то связано с многопоточностью

  **Комментарий:** Да, но ключевой момент — промежуток между проверкой и записью. Запрос A проверил версию 7;
  запрос B успел изменить ресурс до версии 8; затем A сохраняет изменение, хотя его условие уже устарело.
  Проверка ожидаемой версии и запись должны быть атомарными, например через
  `UPDATE ... WHERE id = :id AND version = :expected_version`. Гонка возможна и между разными экземплярами сервиса,
  поэтому замок внутри одного Java-процесса не решает её для общей БД.

- Что делать после тайм-аута перевода и почему нельзя сразу выдать новый ключ? Потому что timeout не гарантирует что
  транзакция на backend была отменена. Нужно дать возможность выполнить retry с тем-же ключом.

  **Комментарий:** Верно. Повтор должен сохранить не только ключ, но и прежнее тело команды. Если перевод уже
  выполнен, сервер вернёт сохранённый результат. Новый ключ обозначает новую команду и может привести к повторному
  списанию. Поэтому клиент сохраняет ключ и тело, считает исход неопределённым и выполняет ограниченные повторы
  в пределах согласованного срока защиты.

- Почему `422` допустим в другом API, но не должен внезапно заменить `400` в нашем? коды помогают отделить ошибку
  парсинга json (некорректный формат параметров запроса) от ошибки значений самих параметров

  **Комментарий:** Ты объяснил возможный смысл разделения: `400` для некорректного запроса, `422` для содержимого,
  которое удалось разобрать, но нельзя обработать по смыслу. Однако главный вопрос здесь — совместимость.
  В нашем контракте ошибки проверки входа возвращают `400 VALIDATION_ERROR`. Клиент может обрабатывать их именно
  по статусу `400`; внезапная замена на `422` изменит его поведение. Другое API вправе выбрать `422`, если это заранее
  описано. Не все ошибки значений относятся к `422`: например, недостаточный баланс у нас — конфликт состояния `409`.

- Может ли добавление нового значения перечисления сломать старый TypeScript-клиент? Если речь про массив, возможно
  значение может некорректно отобразиться в интерфейсе, если мы установили в контракте массив enum например

  **Комментарий:** Под перечислением имеется в виду набор допустимых значений одного поля, например
  `status: "ACTIVE" | "BLOCKED" | "CLOSED"`, а не массив. Если сервер добавит `"SUSPENDED"`, старый клиент может
  получить значение, которого нет в его типах и обработчиках. TypeScript не проверяет JSON во время выполнения:
  `switch` без обработки неизвестного статуса может не вернуть результат, а таблица подписей — вернуть `undefined`.
  Если клиент дополнительно проверяет допустимые значения, он может отклонить весь ответ. Поэтому новый вариант
  перечисления способен нарушить работу старого клиента; нужна предусмотренная обработка неизвестных значений.

- Почему валидный OpenAPI ещё не доказывает соответствие работающего сервиса контракту? OpenAPI и сервис могут быть
  рассинхронизированны

  **Комментарий:** Верно. Валидность OpenAPI подтверждает корректность самого описания, но не поведение сервиса.
  Например, схема требует строку для `amount`, а сервер принимает JSON-число; описан `201`, а сервер возвращает `200`;
  заявлена защита повторов, а перевод выполняется дважды. Даже генерация через springdoc не доказывает все обещания:
  аннотации могут быть неточными, а бизнес-правила и атомарность требуют отдельных проверок фактического поведения.
