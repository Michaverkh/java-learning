1. Почему чтение через `GET` не должно списывать деньги, даже если браузер делает запрос один раз? Согласно REST - GET
   это опирация чтения, которая не должна никак менять состояние

   > **Комментарий — в целом верно.** Это свойство безопасного метода HTTP, а не только правило REST. `GET` не должен запрашивать изменение предметных данных: например, списание денег. Технические побочные действия, такие как запись лога, допустимы. Клиент или посредник может повторить запрос, поэтому нельзя опираться на предположение «браузер вызовет его один раз».

2. Чем безопасный метод отличается от идемпотентного? Может ли статус повторного ответа отличаться? идемпотентного -
   значит при равных входных условиях - возвращать всегда один и тот-же результат.

   > **Комментарий — нужно исправить.** Безопасность означает, что клиент не запрашивает изменение предметных данных. Идемпотентность означает, что несколько одинаковых запросов имеют тот же предполагаемый эффект на сервере, что и один. Совпадение статуса и тела ответа не обязательно: первый `DELETE` может вернуть `204`, повторный — `404`, а ресурс остаётся удалённым. Например, `PUT`, заменяющий данные ресурса, идемпотентен, но не безопасен. [Семантика методов HTTP](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2).

3. Чем `Content-Type` отличается от `Accept`? Откуда берутся `415` и `406`? Content-Type - тип данных принимаемого или
   возвращаемого ответов. Accept — допустимые типы ответа.

   > **Комментарий — частично верно, статусы не раскрыты.** `Content-Type` описывает фактический формат тела того сообщения, в котором находится: запроса или ответа. `Accept` в запросе задаёт допустимые форматы ответа. `415` означает, что сервер не поддерживает формат отправленного тела; `406` — что сервер не может предложить подходящий клиенту формат ответа. Для вашего JSON API пример: запрос с XML может дать `415`, а требование только XML в `Accept` — `406`.

4. Что произойдёт до входа в контроллер при неправильном UUID? Выбросится 400 ошибка со стороны Spring MVC.

   > **Комментарий — верно для аргумента типа UUID.** Spring не сможет преобразовать строку из пути в `UUID`, возникнет `MethodArgumentTypeMismatchException`, а обработка MVC сформирует HTTP `400`. Исключение и HTTP-статус — разные вещи: исключение возникает внутри приложения, статус получает клиент. Тело метода контроллера не выполняется. Неизвестный, но синтаксически корректный UUID — другой случай: существование счёта проверяет сервис, результатом будет `404`.

5. Почему `@RestController` возвращает DTO через преобразователь сообщений? @RestController объединяет @Controller и
   @ResponseBody: результат метода становится телом ответа через преобразователь сообщений. Возвращённая строка в
   REST-контроллере — тело, а не имя шаблона.

   > **Комментарий — верно.** Для DTO в JSON API преобразователь сериализует объект в JSON. Небольшое уточнение: `@RestController` не требует возвращать именно DTO — можно вернуть и другой объект. DTO выбираем сами, чтобы явно задать публичные поля ответа и не связывать API со структурой внутренней сущности.

6. Почему `TransferService` не должен возвращать `ResponseEntity`? Service не должен отдавать наружу внутреннюю
   реализацию сущности. Это нарушает принцип открытости - закрытости.

   > **Комментарий — причина другая.** `ResponseEntity` описывает HTTP-ответ: статус, заголовки и тело. Сервис отвечает за прикладной сценарий и должен быть пригоден для вызова из теста, фоновой задачи или обработчика сообщения без HTTP. Поэтому сервис возвращает результат операции, а контроллер превращает его в `ResponseEntity`. Возврат сущности из сервиса контроллеру допустим; преобразование в DTO выполняется на границе API. Принцип открытости-закрытости здесь не основное объяснение — речь о разделении ответственности и зависимости от транспорта.

7. Почему создание DTO ответа не должно генерировать новый ID перевода? сущность перевода - не изменеема. Она храниться
   в истории. Если мы поменяем id теряется консистентность

   > **Комментарий — направление верное, объяснение стоит уточнить.** DTO должен представлять действительно созданный перевод и содержать его сохранённый ID. Даже если запись перевода не изменять, новый ID только в DTO уже сделает ответ ложным: клиент получит идентификатор несуществующего перевода, а `Location` может указывать на ресурс, который не удастся прочитать. Причина не в обязательной неизменяемости всей сущности, а в сохранении её идентичности при преобразовании в ответ.

8. Какие поля внутреннего `Account` клиенту нельзя разрешать устанавливать? accountId, clientId, createdAt

   > **Комментарий — неполно.** Нельзя позволять напрямую задавать `balance` и `status`: баланс меняется денежными операциями, статус — предусмотренными командами с проверками. `accountId` и `createdAt` задаёт сервер. С `clientId` важна граница: в текущем маршруте создания он приходит из пути, но сервер проверяет клиента, а после подключения безопасности — право создавать ему счёт. Нельзя разрешать произвольно менять владельца существующего счёта через тело запроса.

9. Чем ошибка Jackson отличается от нарушения `@DecimalMin`? ошибка Jackson - ошибка парсинга json строки. Это может
   быть неккоректный символ, лишня запятая и т.д. @DecimalMin обрабатывает значение переменной

   > **Комментарий — в целом верно.** Ошибка преобразователя JSON бывает не только синтаксической: корректный JSON может содержать значение, которое нельзя преобразовать в ожидаемый тип. `@DecimalMin` проверяет уже полученное числовое значение на нижнюю границу. Обычно первое даёт `HttpMessageNotReadableException`, второе при отдельной проверке DTO — `MethodArgumentNotValidException`. Ограничение метода может изменить путь проверки DTO.

10. Почему сумма строкой в JSON полезна JS-клиенту, хотя на сервере используется `BigDecimal`? в JS нет прямых аналогов
    числовых типов данных из java , по этому выбирают универсальную строку

    > **Комментарий — нужно уточнить основную причину.** JavaScript `number` хранит числа в двоичном формате с плавающей точкой и не представляет многие десятичные дроби точно: например, `0.1 + 0.2 !== 0.3`. `BigDecimal` позволяет точно хранить десятичные денежные значения. Строка вроде `"1250.00"` передаёт их без преобразования в `number` при чтении JSON и сохраняет два дробных знака. Но последующее `Number(amount)` снова может потерять точность; для расчётов нужна подходящая стратегия, например десятичная библиотека. [Числа JavaScript](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Number).

11. Почему `@Valid` не заменяет проверки бизнес-инвариантов? @Valid говорит лишь о том что необходимо проверить входные
    параметры на соотвествие данным. Проверки усуществляются через аннотации @Min (1) @Max (100) и т.д

    > **Комментарий — верно, но не хватает границы ответственности.** `@Valid` запускает проверку объявленных ограничений объекта, а бизнес-инварианты часто зависят от текущего состояния: существует ли счёт, активен ли он, достаточно ли средств. Они должны выполняться в сервисе или доменной модели, в том числе при вызове вне HTTP. Даже корректная сумма и достаточный остаток на момент ранней проверки не защищают от конкурентного списания.

12. Когда появится `MethodArgumentNotValidException`, а когда `HandlerMethodValidationException`?
    MethodArgumentNotValidException относится к проверке отдельного объекта, переданного аргументом контроллера.
    HandlerMethodValidationException относится к проверке контракта метода контроллера.

    > **Комментарий — верно.** Добавь конкретный критерий: `@Valid @ModelAttribute HistoryRequest`, где `@Min` находится внутри DTO, даёт первый путь. `@RequestParam @Min(0) int page` включает проверку метода и даёт второй. В смешанной сигнатуре прямое ограничение включает проверку метода и охватывает DTO с `@Valid`. Ошибки преобразования могут возникнуть раньше. Эти правила подразумевают встроенную проверку MVC без `@Validated` на классе и без локальной обработки через `BindingResult`. [Подробный разбор](../../../../../../../lerning-materials/week-07/validation/mvc-validation-exceptions.md).

13. Почему проверка результата метода не должна возвращать клиенту `400`? 400 - обычно говорит о том, что клиент отпраил
    невалидный параметр / body

    > **Комментарий — верно, добавь следствие.** Если сервер нарушил ограничение собственного возвращаемого значения, ошибся сервер, поэтому нужен `500`, а не `400`. Для `HandlerMethodValidationException` это различают через `isForReturnValue()`. Тело метода к этому моменту уже выполнилось; такая проверка сама по себе не откатывает изменения состояния.

14. Почему `@ControllerAdvice` не обрабатывает автоматически любой отказ фильтра безопасности? Он обрабатывает только
    то, что отражено @ExceptionHandler или наследуется от ResponseEntityExceptionHandler

    > **Комментарий — нужно исправить причину.** Фильтры выполняются до `DispatcherServlet`. Исключение, возникшее в фильтре безопасности до входа в MVC, не попадает автоматически в механизм обработки исключений контроллеров. Наличие подходящего `@ExceptionHandler` само по себе этого не меняет. Для отказов аутентификации и доступа Spring Security использует, в частности, `AuthenticationEntryPoint` и `AccessDeniedHandler`. [Цепочка обработки Spring Security](https://docs.spring.io/spring-security/reference/servlet/architecture.html).

15. Зачем в ошибке нужны одновременно `code`, `detail` и `correlationId`? код дает понять к какой категории ошибок
    относится исключения по REST. detail - предоставляет смысловое описание. А по correlationId можно вычислить
    связанные с этим запросом записи в журналах и связанные ответы.

    > **Комментарий — почти верно.** Здесь `code` — стабильный код приложения, например `ACCOUNT_NOT_FOUND`, а не HTTP-статус и не категория «по REST». HTTP-статус отдельно сообщает общую семантику отказа. `detail` объясняет конкретную ситуацию человеку, `correlationId` помогает найти обработку запроса в журналах. Для этого идентификатор нужно действительно включать в записи логов: наличие в ответе само по себе их не связывает.

16. Почему сортировки только по времени недостаточно для пагинации? потмому что могут быть несколько записей одного и
    того-же времени

    > **Комментарий — верно.** При равном времени нужен дополнительный уникальный критерий, иначе взаимный порядок записей не определён и границы страниц могут стать нестабильными. В выбранном контракте это `createdAt DESC, id DESC`. ID не обязан отражать время создания: он нужен для однозначного порядка записей с равным временем.

17. Почему `totalElements` считается до выбора страницы, но после фильтрации? Это связано с работой пагинации. мы должны
    дать на клиент информацию о кол-ве записей и страницах конретно для установленных параметров фильтрации

    > **Комментарий — верно.** `totalElements` — количество всех записей, удовлетворяющих фильтрам, а `items.size()` — количество записей выбранной страницы. Например, из 65 подходящих записей страница может содержать 20, но `totalElements` остаётся 65. Иначе клиент неверно рассчитает число страниц. За последней страницей `items` пуст, а общее количество сохраняется.

18. Почему устойчивый порядок не даёт неизменный снимок между двумя HTTP-запросами? новые операции сдвигают страницы,
    поэтому возможны повторы и пропуски.

    > **Комментарий — верно.** Устойчивый порядок однозначно упорядочивает текущие данные, но не фиксирует их между запросами. Например, после чтения первой страницы новая запись в начале списка сдвигает границу: последняя запись первой страницы может повториться на второй. При удалениях из изменяемых наборов возможны и пропуски; в неизменяемой истории Wallet Service основной пример — добавление новых операций.

19. Что возвращать при повторе завершённого перевода с тем же ключом и телом? Такой запрос должен отметаться на уровне
    контроллера ошибкой с подходящим кодом

    > **Комментарий — неверно.** Повтор завершённого перевода с тем же ключом и тем же нормализованным телом должен вернуть сохранённые статус и тело исходного ответа, без нового списания. Если исходный ответ был `201`, повтор тоже возвращает сохранённый `201`. Ошибка `409 IDEMPOTENCY_KEY_REUSED` нужна при том же ключе, но другом теле. Это прямо закреплено в [требованиях Wallet Service](../../wallet/technical-requirements.md#9-идемпотентность).

20. Почему `ConcurrentHashMap` не делает перевод и сохранение ответа атомарными? Потому что Два запроса могут
    одновременно увидеть отсутствие ключа.

    > **Комментарий — верно для последовательности «проверить наличие → выполнить перевод → сохранить ответ», но ответ неполный.** `ConcurrentHashMap` обеспечивает безопасность отдельных операций с картой. Даже атомарный `putIfAbsent` не объединяет списание, зачисление, сохранение перевода, истории и ответа в одну атомарную операцию. Между ними возможны конкурентные действия или сбой. Общую согласованность нужно обеспечивать отдельно; после подключения БД — подходящей транзакцией и защитой конкурирующих операций.

21. Почему ключ идемпотентности не заменяет блокировку конкурентных списаний с одного счёта? Разные ключи
    идемпотентности одновременно могут списывать с одного счёта в случае нескольких потоков.

    > **Комментарий — верно.** Ключ защищает от повторения одной логической операции, но разные переводы имеют разные ключи. Два перевода могут одновременно прочитать один остаток и оба решить, что средств достаточно. Проверка доступности денег и изменение баланса должны быть согласованы, например блокировкой или проверкой версии с обработкой конфликта.

22. Как потеря записи идемпотентности после успешного списания может привести к дублю? Если клиент создаст такой-же
    запрос. 

    > **Комментарий — верно, но раскрой механизм.** Деньги уже списаны, а запись «этот ключ обработан, вот сохранённый ответ» потеряна. Клиент повторяет запрос с тем же ключом, например после потери ответа. Сервер не находит запись и принимает повтор за новую операцию, списывая деньги ещё раз. Поэтому денежное изменение и сохранение результата идемпотентности должны быть согласованы; в БД их обычно включают в одну транзакцию. Новый ключ вообще обозначает отдельную операцию и не защищает от такого повтора.
