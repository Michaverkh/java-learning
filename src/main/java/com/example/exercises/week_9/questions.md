## Как выполнять

Используй временные таблицы и данные из
[SQL-лаборатории](../../../../../../../lerning-materials/week-09/relational-model-and-sql.md#lab). Все задания
выполняются SQL-запросами; подключать Spring, JDBC и ORM пока не нужно.

Сохраняй свои запросы в `sql/answers.sql` рядом с этим файлом, а объяснения — в `notes.md`. Перед каждым запросом
напиши, что означает одна строка результата и сколько строк ты ожидаешь. Проверки ограничений выполняй отдельно, через
точки сохранения, чтобы одна ожидаемая ошибка не мешала следующей.

Сокращения: C1 — Анна, C2 — Борис, C3 — Вера; A1 и A3 принадлежат Анне, A2 — Борису. Это обозначения для текста; в SQL
используй полные UUID из исходных данных.

## 1. Объясни схему без запуска запросов

1. Найди все первичные и внешние ключи. Укажи, где допустимо отсутствие дочерних строк.
2. Почему `client.external_id` уникален, а `account.client_id` — нет?
3. Почему `UNIQUE(operation_id)` не подходит для журнала переводов?
4. Что именно запрещает `UNIQUE(operation_id, account_id)`? Запрещает ли оно третью запись на другом счёте?
5. Почему `operation_id` не имеет FK на `transfer`? Какую дыру в проверке данных это оставляет?
6. Какие проверки выполняются для одной строки, а какие требуют согласовать несколько строк?
7. Почему нельзя гарантировать неизменяемость журнала только с помощью показанных PK, FK и `CHECK`?

**Критерий:** объяснение каждой связи опирается на требования кошелька, а не на привычку «всегда добавлять индекс».

## 2. Раздели неправильно спроектированную таблицу

Дана структура:

```text
account_id, client_id, client_name, client_external_id,
account_currency, account_balance, operation_1, operation_2, operation_3
```

1. Покажи аномалии вставки, изменения и удаления.
2. Раздели структуру на таблицы; укажи ключи и зависимости.
3. Объясни, где нарушена 1NF и почему имя клиента не принадлежит строке счёта.
4. Для отдельного примера с ключом `(operation_id, account_id)` объясни, почему `account_currency`
   зависит от части ключа.
5. Объясни, почему в итоговой модели остаются и `account.balance`, и `ledger_entry.balance_after`.

**Критерий:** клиент без счетов представим без фиктивного счёта; добавление четвёртой операции не меняет схему.

## 3. Найди ошибки ограничений

По очереди попробуй выполнить следующие изменения, каждый раз откатывая эксперимент:

1. Создать клиента с занятым `external_id`.
2. Создать счёт с несуществующим `client_id`.
3. Изменить баланс счёта на `-0.01`.
4. Сделать A1 закрытым, сохранив баланс 700.
5. У существующего перевода сделать отправителя равным получателю.
6. У записи `TRANSFER_OUT` изменить сумму на положительную.
7. Создать вторую запись для той же пары `(operation_id, account_id)` с новым `id`.
8. Удалить A1, пока на него ссылается история.

Для каждой ошибки укажи нарушенное ограничение. Затем проверь два случая, которые **не обязаны завершиться ошибкой**:

- записать в `numeric(19, 2)` значение `1.239` и прочитать его обратно;
- создать запись `TRANSFER_IN` с новым `operation_id`, которого нет в `transfer`, соблюдая остальные ограничения.

Объясни, почему первый случай не выполняет требование отклонения лишних дробных знаков, а второй показывает ограничение
учебной схемы. Такие эксперименты не должны оставаться в исходном наборе.

## 4. SELECT, NULL и границы периода

1. Получи все счета Анны, отсортированные по `id`. Ожидаются A1 и A3.
2. Получи перевод без описания. Ожидается перевод на 250.
3. Получи переводы, описание которых отличается от `Возврат за обед`, включая отсутствие описания.
4. Получи историю A2 за период `[2026-10-02T00:00:00Z, 2026-10-03T00:00:00Z)`. Ожидаются две записи: +250 и -50, с
   балансами 350 и 300.
5. Выведи историю A1, новые записи первыми. При одинаковом времени используй `id` как второй ключ.
6. Объясни результат `NULL = NULL`, `TRUE OR NULL`, `42 NOT IN (1, NULL)`.

**Критерий:** фильтрация по отсутствию использует `IS NULL` или соответствующие операторы, а не `= NULL`.

## 5. Соединения и пустые группы

1. Получи все счета с именами владельцев: три строки.
2. Получи всех клиентов с их счетами через `LEFT JOIN`: четыре строки, включая Веру с пустыми полями счёта.
3. Получи все счета и только их пополнения, сохранив A3: три строки.
4. Перенеси условие о типе пополнения из `ON` в `WHERE`. Объясни, почему теперь две строки.
5. Соедини A1 одновременно с журналом и исходящими переводами. Предскажи и проверь шесть строк.
6. Объясни, почему `DISTINCT` не является универсальным исправлением ошибки из предыдущего пункта.

**Критерий:** прежде чем суммировать значения, ты можешь объяснить число строк после каждого соединения.

## 6. Обороты и сверка баланса

1. Для каждого счёта верни число записей, приход и положительный расход, включая A3 с нулями.
2. Повтори расчёт только за 2 октября в UTC. Ожидаемые пары «приход / расход»:
   A1 — 0 / 250, A2 — 250 / 50, A3 — 0 / 0.
3. Через `HAVING` выбери счета, имеющие минимум четыре записи: только A2.
4. Посчитай внешние пополнения отдельно от входящих переводов: 1100 и 300 соответственно.
5. Сравни `account.balance` с суммой полной истории и верни только расхождения: ноль строк.
6. В точке сохранения измени баланс A1 с 700 на 701. Проверь, что запрос сверки находит A1, затем откати изменение.

**Критерий:** `COUNT(*)` после `LEFT JOIN` не используется как число операций; отсутствие суммы преобразуется в ноль.

## 7. Подзапросы и диагностические запросы

1. Через `NOT EXISTS` найди счета без операций: A3.
2. Через `NOT EXISTS` найди клиентов без счетов: Вера.
3. Найди переводы, для которых нет ровно одной исходящей записи на `-transfer.amount` для отправителя и одной входящей
   на `+transfer.amount` для получателя. Проверь также общее число записей и нулевую сумму.
4. Напиши обратную проверку: найди записи типов `TRANSFER_IN` и `TRANSFER_OUT`, для которых нет строки `transfer`.
5. В отдельном эксперименте добавь корректную по локальным ограничениям запись `TRANSFER_IN` с несуществующим
   идентификатором перевода и убедись, что запрос из пункта 4 находит её. Откати эксперимент.

**Критерий:** диагностика из пункта 3 находит и перевод вообще без журнала; все диагностики на исходном наборе пусты.

## 9. Свяжи SQL с будущим репозиторием

Опиши SQL для метода чтения истории без реализации JDBC:

- вход: идентификатор счёта, начало и конец периода, размер страницы;
- выход: идентификатор записи, идентификатор операции, тип, знаковая сумма, баланс после операции, время, необязательное
  назначение перевода;
- пополнения и списания остаются в результате;
- порядок однозначен, размер результата ограничен;
- значения пользователя будут передаваться параметрами;
- право чтения счёта должно проверяться отдельно либо выражаться дополнительными условиями доступа.

Объясни, почему нельзя возвращать `SELECT *` как стабильный контракт API и почему одного фильтра по `account_id`
недостаточно для авторизации. Перечисли, какие таблицы из полного технического задания ещё не вошли в лабораторию.

## Самопроверка без полного решения

<details>
<summary>Подсказки к наиболее частым ошибкам</summary>

- Для пустого счёта `LEFT JOIN` создаёт строку с `NULL` справа. Считай непустой `e.id`.
- Для сохранения пустых счетов ограничения периода журнала относятся к `ON`.
- Нулевая сумма двух записей не доказывает, что они относятся к правильным счетам и имеют правильные типы.
- Начинай проверку отсутствующих записей с родительской таблицы; иначе потерянные записи не попадут в запрос.
- Проверка «осиротевших» записей должна начинаться с журнала.
- Рассчитай окно во внутреннем запросе, а нужный период отфильтруй во внешнем.
- Текущий баланс — сумма полной истории при нулевом начале. Промежуточный баланс дополнительно зависит от порядка.
- Не смешивай число переводов с числом записей журнала: у одного перевода две записи.

</details>
