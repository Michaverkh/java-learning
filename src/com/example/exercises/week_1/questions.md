1. Почему heap JVM и оперативная память процесса — не одно и то же? оперативную память процесса потребляет не только
   heap. Её потребляют также stack главного потока, stack http потока, metaspace и др.
   > Комментарий: Верно. Точнее: heap — лишь одна из областей памяти JVM; процесс также использует стеки всех потоков,
   > metaspace, память JIT-компилятора, буферы и другие нативные структуры.
2. Что создаётся при вызове метода и что происходит с этим после возврата? создается новый стек фрейм, после возврата
   фрейм снимается
   > Комментарий: Верно. Stack frame содержит локальные переменные, параметры, промежуточные результаты и информацию,
   > необходимую для возврата из метода.
3. Почему два потока имеют разные локальные переменные, но могут конфликтовать при изменении `Account`? потому что
   Account это mutable объект, который находится в heap. И оба потока теоретически могут иметь к нему доступ
   > Комментарий: Верно. Важно, что конфликт возникает, когда оба потока получили ссылки на один и тот же `Account` и
   > меняют его состояние без подходящей синхронизации.
4. Когда объект может быть собран GC? Когда он становится "недостижимым"
   > Комментарий: Верно. Недостижимым означает: до объекта нельзя дойти по цепочке ссылок от GC roots, например от
   > локальных переменных работающих методов или `static`-полей.
5. Почему `cached` в static-поле может быть причиной утечки памяти? Потому что GC считает его всегда "достижимым"
   > Комментарий: Верно по сути. Ссылка из `static`-поля достижима, пока загружен содержащий её класс; поэтому объект и
   > всё, на что он ссылается, могут жить неоправданно долго.
6. Чем `StackOverflowError` отличается от `OutOfMemoryError: Java heap space`? StackOverflowError - ошибка переполнения
   стека (например когда забыли добавить выход ищ рекурсии). OutOfMemoryError - переполнение heap
   > Комментарий: Верно. Для второй ошибки точнее сказать: JVM не смогла выделить место под объект в heap; причиной могут
   > быть слишком маленький heap или слишком много объектов, которые всё ещё достижимы.
7. Что означает `-Xmx`, и почему процесс может использовать больше этой величины? Xmx показывает сколько процесс может
   выделить на heap. Процесс использует больщше так как помимо хип еще память тратиться на stack главного потока, stack
   http потока, metaspace и др.
   > Комментарий: Верно. `-Xmx` задаёт верхний предел именно для Java heap, а не для всей памяти процесса. Учитываются
   > также стеки всех потоков, metaspace, нативная память JVM и библиотеки.
8. Где находится string pool в современной HotSpot JVM? - в heap
   > Комментарий: Верно: в современных HotSpot JVM, включая Java 21, String Pool находится в heap. Схема с Permanent
   > Generation относится к старым версиям Java и здесь неприменима.
9. Почему `"RUB" == "RUB"` не доказывает, что `==` допустим для строк? потому что механизм String pool не дает такой
   гарантии. Это лишь механизм оптимизации
   > Комментарий: Верно по главной мысли. `==` проверяет идентичность объектов, а не текст. Два литерала обычно дадут
   > один объект из пула, но строка из HTTP-запроса, БД или `new String("RUB")` может быть отдельным объектом с тем же
   > содержанием. Для значений нужно применять `equals()`.
10. Как `new String("RUB")` отличается от строкового литерала? - тем что при такой записи принудительно создастя новый
    объек даже если литерал "RUB" уже есть в String pool
    > Комментарий: Верно. Литерал обычно использует канонический экземпляр из пула, а `new String("RUB")` создаёт другой
    > объект с тем же содержанием.
11. Что возвращает `intern()` и почему его нельзя применять к неограниченным пользовательским данным? - ищет или
    добавляет канонический экземпляр. Потому что pool будет удерживать много уникальных строк и увеличит расход heap.
    > Комментарий: Верно. `intern()` возвращает ссылку на канонический экземпляр строки из пула: уже существующий или
    > добавленный. Для неограниченного пользовательского ввода это способно заметно увеличить расход heap.
12. Почему GC не заменяет `try-with-resources`? У них разные роли. GC ищет недостижимы объекты, а try-with-resources
    закрывает соединения или процессы.
    > Комментарий: Верно. GC освобождает память и делает это в неопределённый момент, а `try-with-resources` гарантирует
    > своевременный вызов `close()` для файлов, сетевых соединений, JDBC-ресурсов и других внешних ресурсов.
