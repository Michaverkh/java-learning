1. Чем класс отличается от объекта? - класс создает объект

   > **Замечание проверяющего:** Ответ стоит уточнить: класс — это тип и описание структуры и поведения, а объект —
   > конкретный экземпляр этого класса со своим состоянием. Объект может быть создан через `new`, фабричный метод,
   > reflection и другие механизмы, поэтому «класс создаёт объект» — слишком узкая формулировка.

2. Что хранится в переменной reference type? - копия ссылки на объект

3. Создаёт ли `Account second = first` новый объект? - нет он просто копирует ссылку

4. Какие этапы проходит объект при `new`? объект инициализируется и создается

   > **Замечание проверяющего:** Ответ неполный. Упрощённая последовательность: вычисляются аргументы конструктора,
   > выделяется память, поля получают default values, затем запускается цепочка инициализации от `Object` к конкретному
   > классу. На уровне каждого класса выполняются его field initializers и instance initializer blocks, а затем тело его
   > constructor. После успешного завершения выражение `new` возвращает ссылку на объект.

5. Когда compiler создаёт default constructor? - когда не задан пользовательский

   > **Замечание проверяющего:** Точнее: compiler добавляет default constructor только тогда, когда в классе вообще не
   > объявлен ни один constructor. Если объявить любой constructor, даже `private`, default constructor уже не создаётся.

6. Почему после объявления конструктора с параметрами `new Account()` может перестать компилироваться? - Потому что при
   `new Account()` вызывается конструктор, который ожидает обязательные параметры

   > **Замечание проверяющего:** `new Account()` не пытается вызвать constructor с параметрами. Compiler ищет именно
   > no-argument constructor. После объявления constructor с параметрами compiler перестаёт генерировать default
   > no-argument constructor, поэтому подходящего constructor больше нет. При необходимости его нужно объявить явно.

7. Чем instance member отличается от static member? - instance member доступен только экземпляру, а static member самому
   классу

   > **Замечание проверяющего:** Главное различие — принадлежность. Instance member относится к конкретному объекту:
   > у разных экземпляров могут быть разные значения instance fields. Static member относится к классу и существует в
   > одном экземпляре на уровне class loader. Instance method может обращаться и к instance, и к static members, а static
   > method не может напрямую обратиться к instance member без ссылки на объект.

8. Почему наличие private fields и публичных setters ещё не гарантирует хорошую инкапсуляцию? - потому что у экземпляра
   могут быть мутирующие методы

   > **Замечание проверяющего:** Проблема не в самом наличии мутирующих методов, а в том, ограничивают ли они допустимые
   > изменения. Универсальный setter может разрешить установить некорректное значение или нарушить связь между полями.
   > Хорошая инкапсуляция скрывает представление и предоставляет операции предметной области, например `deposit` и
   > `withdraw`, которые сохраняют инварианты объекта.

9. Что такое инвариант объекта? - условие, которое должно оставаться истинным для любого наблюдаемого корректного
   состояния объекта.

10. Какие members участвуют в dynamic dispatch? - статические

    > **Замечание проверяющего:** Здесь ответ неверный. В dynamic dispatch участвуют переопределяемые instance methods.
    > Static methods выбираются по declared type на этапе компиляции и скрываются (`method hiding`), а не переопределяются.
    > Также в dynamic dispatch не участвуют constructors, fields, `private` и `final` methods.

11. Чем overriding отличается от overloading? - overriding — когда мы переопределяем одноименный метод наследуемого
    класса. overloading — когда мы создаем несколько экземпляров метода с одинаковым названием, но с разной реализацией.
    И реализация выбирается на этапе компиляции в зависимости от переданных параметров

    > **Замечание проверяющего:** Для overriding недостаточно одинакового имени: subtype предоставляет новую реализацию
    > instance method с совместимой сигнатурой. Она выбирается во время выполнения по runtime type объекта. При overloading
    > объявляется несколько методов с одним именем, но разными списками параметров; конкретная сигнатура выбирается на
    > этапе компиляции. Один только другой return type перегрузку создать не позволяет.

12. Почему overload выбирается по declared type, а override — по runtime type? при overload важно только какие параметры
    переданы на вход (это видно на этапе компиляции). А для override - важен конкретный экземпляр

    > **Замечание проверяющего:** Направление верное. Для overload compiler использует количество аргументов и их
    > compile-time/declared types, а не runtime types объектов. После выбора сигнатуры instance method runtime выполняет
    > dynamic dispatch и выбирает override по фактическому классу объекта-получателя вызова.

13. Что Java-класс наследует от `Object`? `equals` и `hashCode`

    > **Замечание проверяющего:** Не только их. Среди основных методов `Object`: `equals`, `hashCode`, `toString`,
    > `getClass`, `clone`, `wait`, `notify` и `notifyAll`. Часть методов имеет ограничения доступа или специальные правила
    > использования. Поэтому корректнее сказать, что `Object` является корнем иерархии классов и предоставляет общий
    > базовый контракт для всех объектов.

14. Почему при переопределении `equals` обычно нужно переопределить `hashCode`? потому что дефолтный `hashCode` может
    приводить к непредсказуемым результатам

    > **Замечание проверяющего:** Причина — формальный контракт: если `a.equals(b)` возвращает `true`, то
    > `a.hashCode() == b.hashCode()` также обязательно должно быть `true`. Если оставить identity-based `hashCode` из
    > `Object`, равные по значению объекты могут попасть в разные buckets, и `HashMap`/`HashSet` будут работать некорректно.
    > Обратное неверно: одинаковый hash code не гарантирует `equals` из-за возможных коллизий.

15. Чем reference identity отличается от value equality? reference identity определяет равенство ссылок, а value
    equality - значений

16. Почему `final List<T>` не обязательно immutable? Мы не можем записать в переменную с таким именем что-то другое, но
    можем мутировать сам list. Ссылка останется прежней, но содержимое изменится

17. Когда abstract class уместнее interface? когда abstract class определяет базу тесной иерархии

    > **Замечание проверяющего:** Верно. Дополнительно abstract class уместен, когда тесной иерархии нужны общее состояние,
    > protected API, constructors или частично реализованный алгоритм. Interface предпочтительнее для общего контракта,
    > который могут реализовывать несвязанные классы.

18. Почему Java interface сильнее отличается от TypeScript interface, чем кажется по синтаксису? Java interface — сущность,
    которая доступна как на этапе компиляции, так и на этапе runtime. TypeScript interface на этапе преобразования в JS
    исчезает

    > **Замечание проверяющего:** Ответ верный. Ещё одно существенное различие: Java использует явно объявленное отношение
    > `implements`/`extends`, тогда как TypeScript в основном применяет structural typing. Java interface сохраняется в
    > bytecode, участвует в `instanceof`, reflection и dynamic dispatch; TypeScript interface после компиляции не существует.

19. Что означает номинативная типизация Java? Противоположность - "утиная" типизация (как в TS). номинативная
    типизация - смотрит на имя типа, а не на внутреннюю реализацию. например два одинаковых по реализации интерфейса но
    имеющих разные имена будут разными типами в Java

    > **Замечание проверяющего:** Основная мысль верная, но TypeScript точнее называть structurally typed, а не просто
    > «утиной» типизацией. В Java совместимость определяется явно объявленными отношениями типов (`extends`, `implements`),
    > а не только именем. Класс с подходящими методами не становится реализацией interface автоматически — он должен явно
    > указать `implements`.

20. Когда inheritance предпочтительнее composition? - Когда прослеживается четкая логичная иерархия `is-a`

    > **Замечание проверяющего:** Одного отношения `is-a` недостаточно. Оно должно быть устойчивым, базовый класс должен
    > быть спроектирован для расширения, а subtype — сохранять контракт и быть взаимозаменяемым с родителем. Если требуется
    > только повторно использовать код или заменять отдельное правило поведения, чаще предпочтительнее composition.

21. Почему вызов overridable method из constructor опасен? - потому что он может вызвать override наследника до его
    инициализации

22. Когда downcast указывает на проблему дизайна? - когда потребителю постоянно нужен конкретный subtype

23. Чем sealed hierarchy Java похожа на discriminated union TypeScript? - она четко фиксирует разрешенный нейминг и
    структуру будущих наследников

    > **Замечание проверяющего:** Сходство не в нейминге. Оба механизма описывают закрытый набор допустимых вариантов.
    > `sealed`-тип перечисляет разрешённые direct subtypes через `permits` или структуру исходных файлов, а discriminated
    > union объединяет конечный набор вариантов по общему discriminator field. Благодаря закрытому набору compiler может
    > проверять полноту обработки вариантов, например в `switch`.

24. Почему domain object часто не должен иметь универсальный setter для каждого поля? - потому что в этом случае есть
    риск получения неконсистентного состояния
