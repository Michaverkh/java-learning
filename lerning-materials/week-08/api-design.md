## Цель и отправная точка

На прошлой неделе ты научился проводить HTTP-запрос через контроллер в прикладной сервис. Теперь задача — спроектировать
контракт, с которым frontend и backend смогут развиваться независимо. Хороший контракт объясняет не только форму JSON,
но и смысл действий, последствия повторов, конфликты, ограничения и правила изменения API.

Основой примеров служат [требования Wallet Service](../../src/main/java/com/example/wallet/technical-requirements.md).
Здесь сохраняются `/api/v1`, строковое представление денег, синхронный перевод, `201` для создания денежной операции,
`200` для команд изменения статуса и действующие машинные коды ошибок.

Не повторяем устройство контроллеров, Jackson и обработчиков исключений:

- [Spring MVC и REST](../week-07/spring-mvc-and-rest.md);
- [проверка DTO и аргументов метода](../week-07/validation/mvc-validation-exceptions.md);
- [основы идемпотентности](../week-07/spring-mvc-and-rest.md#idempotency).

Примеры с редактированием имени клиента и условными командами через `If-Match` — учебные расширения. Они помогают понять
проектирование, но не означают, что эти возможности уже реализованы или входят в исходный обязательный API.

## 1. Что входит в контракт

С точки зрения React-разработчика контракт легко принять за набор интерфейсов TypeScript. Однако тип
`Promise<TransferResponse>` не отвечает на вопрос: что произошло, если обещание отклонено из-за потери соединения?
Перевод мог завершиться, хотя браузер не получил ответ.

Для каждой операции договорённость должна включать:

| Часть контракта         | Вопрос, на который нужно ответить                                       |
| ----------------------- | ----------------------------------------------------------------------- |
| Адрес и метод           | Какой ресурс читаем или какое действие выполняем?                       |
| Вход                    | Какие поля, заголовки и параметры обязательны?                          |
| Семантика полей         | Что означают отсутствие, `null`, пустая строка и ноль?                  |
| Успешный результат      | Когда действие считается завершённым, какой статус и тело вернутся?     |
| Отказ                   | Как клиент различает исправимый ввод и конфликт состояния?              |
| Повтор                  | Можно ли повторить запрос после неопределённого результата?             |
| Конкурентность          | Как определить, что клиент редактирует устаревшие данные?               |
| Доступ                  | Кто может вызвать операцию и получить результат?                        |
| Эволюция                | Какие изменения сохранят работоспособность прежнего клиента?            |

Полезный способ проектировать API: начать с пользовательского сценария и выписать его наблюдаемые результаты.
Для перевода это успешное завершение, ошибка формы, отсутствующий счёт, недостаточный баланс, потеря ответа и повтор.
Далее выбрать HTTP-представление каждого результата. Аннотации Spring появляются после этой договорённости.

Контракт включает и ограничения эксплуатации. Например, хранение ключа идемпотентности не менее 24 часов определяет,
как долго клиент может рассчитывать на защищённый повтор. OpenAPI-схема сама по себе такое поведение не обеспечивает.

## 2. Ресурсы, операции и маршруты

### 2.1. Ресурс — понятие предметной области

Ресурс не обязан соответствовать таблице БД. Перевод — самостоятельный ресурс, даже если его выполнение затрагивает
два счёта, две записи истории и событие. Клиент отправляет одну команду и получает один идентификатор перевода.

Для Wallet Service:

```text
POST /api/v1/clients/{clientId}/accounts   → создать счёт заданного клиента
GET  /api/v1/accounts/{accountId}         → прочитать конкретный счёт
POST /api/v1/transfers                    → создать перевод
GET  /api/v1/transfers/{transferId}       → прочитать результат перевода
GET  /api/v1/accounts/{accountId}/operations → прочитать историю счёта
```

Вложенность уместна для коллекции, принадлежащей клиенту. Адрес конкретного счёта остаётся коротким и самостоятельным.
Если использовать одновременно `/clients/{clientId}/accounts/{accountId}`, потребуется определить результат для случая,
когда клиент и счёт существуют, но не связаны. Не вводи второй адрес без полезного сценария.

Правило «существительные в маршрутах» помогает сохранять единообразие, но не заменяет предметную модель. В требованиях
есть команды `/accounts/{id}/block`, `/unblock`, `/close`. Они обозначают разрешённые переходы и удобны тем, что клиент
не получает право произвольно присваивать любое состояние счёта.

### 2.2. Почему нельзя исправлять баланс через PATCH

Запрос `PATCH /accounts/{id}` с `{"balance":"500.00"}` скрывает причину изменения денег. Невозможно однозначно
определить вид операции, связать два счёта и сохранить согласованную историю. Баланс меняется через денежные операции;
поля `id`, `clientId`, `balance`, `version`, `createdAt` принадлежат серверу.

Аналогично закрытие счёта нельзя заменить удалением: история должна сохраняться, а закрытие имеет условия и аудит.
Не нужен полный набор CRUD только потому, что сущность существует в Java.

### 2.3. Создание и результат

```http
HTTP/1.1 201 Created
Location: /api/v1/transfers/51c8d130-1df0-4f0e-a59e-e0b097b081ac
Content-Type: application/json
X-Correlation-Id: request-001

{
  "id": "51c8d130-1df0-4f0e-a59e-e0b097b081ac",
  "sourceAccountId": "dc3fbc98-b93a-42a6-8d33-2fbbfcb95479",
  "targetAccountId": "f42c2df7-3275-4f30-9bd1-6be0375d3838",
  "amount": "1250.00",
  "currency": "RUB",
  "status": "COMPLETED",
  "createdAt": "2026-10-12T10:00:00Z",
  "completedAt": "2026-10-12T10:00:00Z"
}
```

`Location` даёт адрес результата. Для этого проекта `201` означает, что синхронный перевод уже завершён.
Переход на постановку в очередь с `202` изменил бы обещание API: понадобились бы промежуточные состояния и способ
получить окончательный результат. Это отдельное изменение контракта, даже при прежней форме запроса.

## 3. PUT, PATCH и три состояния поля

### 3.1. PUT: заменить изменяемое представление

Представим учебное API настройки профиля клиента:

```http
PUT /api/v1/clients/30ef8c2c-8a0c-49a6-a4ee-e7e4cfa71d30/profile
Content-Type: application/json

{"name":"Михаил"}
```

Сервер трактует тело как новое состояние изменяемого представления профиля. Поля, назначаемые сервером, не становятся
доступными для записи. Для обязательного `name` отсутствие — ошибка. Для необязательных полей нужно явно определить
сброс к значению по умолчанию или очистку; сохранение всех пропущенных полей фактически превращает метод в частичное
обновление.

Повтор идентичного PUT имеет тот же предполагаемый эффект. Это не обещает одинаковых HTTP-ответов или отсутствия
технических записей аудита. Создание по выбранному клиентом URI возможно, если API это разрешает; в нашем учебном
расширении PUT разрешён только для существующего профиля.

### 3.2. PATCH: применить документ изменений

PATCH не задаёт формат документа автоматически. Два распространённых варианта:

| Формат             | Content-Type                          | Как описывает изменение                            |
| ------------------ | ------------------------------------- | -------------------------------------------------- |
| JSON Merge Patch   | `application/merge-patch+json`        | Объект с заменяемыми или удаляемыми свойствами     |
| JSON Patch         | `application/json-patch+json`         | Последовательность операций по путям в документе   |

PATCH должен применяться целиком: ошибка в одной части не должна оставить половину изменений.
Источник: [RFC 5789, применение PATCH](https://www.rfc-editor.org/rfc/rfc5789.html#section-2).

JSON Merge Patch на примере профиля с необязательным `displayNote`:

```json
{"name":"Михаил", "displayNote":null}
```

Здесь `name` заменяется, а `displayNote` удаляется. Отсутствующее свойство сохраняет прежнее значение; массив
заменяется целиком. Поэтому формат неудобен, если нужно отличать удаление поля от хранения JSON `null`.
Источник: [RFC 7396](https://www.rfc-editor.org/rfc/rfc7396.html).

JSON Patch описывает действия явно:

```json
[
  {"op":"test", "path":"/name", "value":"Миша"},
  {"op":"replace", "path":"/name", "value":"Михаил"}
]
```

Есть операции `add`, `remove`, `replace`, `move`, `copy`, `test`. Путь относится к JSON-документу. Сервер должен
ограничивать доступные пути и проверять итоговое состояние. Добавление в конец массива через `/-` при повторе может
добавить элемент ещё раз. Идемпотентность PATCH зависит от документа изменений.
Источник: [RFC 6902](https://www.rfc-editor.org/rfc/rfc6902.html).

### 3.3. Отсутствие, null и значение

Для частичного обновления эти состояния имеют разный смысл:

| Тело запроса                 | Смысл в учебном Merge Patch для имени                 |
| ---------------------------- | ----------------------------------------------------- |
| `{}`                         | Имя не изменяется                                     |
| `{"name":null}`              | Попытка удалить обязательное имя; отказ               |
| `{"name":"Михаил"}`          | Установить новое имя                                  |
| `{"name":""}`                | Передано пустое имя; отказ по правилу длины           |

Обычный `record PatchProfileRequest(String name)` после стандартной привязки не позволяет надёжно различить первые
два случая: в обоих может получиться `null`. Нужна информация о присутствии поля: например, разбор `JsonNode` с
`has("name")` и `isNull()`, либо специальный тип с признаком присутствия. `Optional<String>` сам по себе не задаёт
все три состояния и правила сериализации.

В TypeScript похожая проблема проявляется с `name?: string | null`: `JSON.stringify` убирает `undefined`, но сохраняет
`null`. Если клиент собирает обновление из всей формы с начальными пустыми значениями, он может случайно стереть поля.

Разрешение неизвестных полей тоже является частью договора. Для документов изменения полезно отклонять неизвестные
и запрещённые пути, чтобы опечатка `naem` не выглядела успешным обновлением.

## 4. Граница проверки и ошибки

### 4.1. Кто за что отвечает

Frontend проверяет форму ради удобства. HTTP-граница проверяет структуру и формат. Прикладной сервис проверяет доступ
и координирует действие. Доменная модель защищает инварианты. В будущей версии БД дополнительно обеспечивает ограничения
и атомарность. Проверка в React не освобождает сервер от проверок.

Для перевода важно разделить данные, проверяемые без чтения состояния, и правила, зависящие от текущих счетов:

| Условие                                | Где проверяется                                        | Ответ Wallet Service                   |
| -------------------------------------- | ------------------------------------------------------ | -------------------------------------- |
| Некорректный UUID или отсутствует ключ | HTTP-граница                                           | `400 VALIDATION_ERROR`                 |
| Сумма ≤ 0 или точность больше 2 знаков | HTTP-граница; денежные инварианты также в домене       | `400 VALIDATION_ERROR`                 |
| Счета отправителя и получателя равны   | Проверка команды; инвариант прикладного сценария       | `400 VALIDATION_ERROR`                 |
| Нет права на исходный счёт             | Проверка доступа                                       | `403 ACCESS_DENIED`                    |
| Счёт отсутствует                       | Прикладной сервис                                      | `404 ACCOUNT_NOT_FOUND`                |
| Недостаточный баланс                   | Домен внутри защищённого денежного сценария            | `409 INSUFFICIENT_FUNDS`               |
| Счёт заблокирован                      | Домен внутри защищённого денежного сценария            | `409 ACCOUNT_NOT_ACTIVE`               |
| Валюта не совпадает с валютой счёта    | Домен после получения счёта                            | `409 CURRENCY_MISMATCH`                |

Это классификация причин, а не обязательный порядок раскрытия ошибок. Проверка доступа может требовать загрузки
ресурса; сервис не должен раскрывать чужие данные через ответы или сохранённые результаты повторов.

Предварительное чтение баланса и проверка `balance >= amount` ещё не обеспечивают правило: между чтением и записью
может пройти другое списание. Условие должно защищаться в момент изменения состояния. Механизм БД разберём на неделях
транзакций; сейчас фиксируем обещание клиенту.

### 4.2. 400, 409, 422 и 412

`422 Unprocessable Content` подходит для запроса с понятным типом содержимого и корректным синтаксисом, инструкции
которого сервер не может выполнить. В другом API валидный JSON с недопустимыми значениями может получать `422`.
Для Wallet Service согласовано `400 VALIDATION_ERROR`: менять его на `422` только ради иной классификации нельзя.
Источник определения `422`: [RFC 9110, раздел 15.5.21](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.21).

`409` сообщает конфликт с состоянием: например, баланс недостаточен или ключ уже занят другим запросом.
`412 Precondition Failed` сообщает о невыполнении HTTP-условия, например устаревшем `If-Match`. Это разные ситуации.
Таблица принятого контракта приведена в [разделе 8 требований](../../src/main/java/com/example/wallet/technical-requirements.md#8-формат-ошибок).

Клиент выбирает действие по статусу и стабильному `code`, а не по русскому `detail`. Текст можно уточнять и переводить.
Переименование `INSUFFICIENT_FUNDS` ломает код клиента даже при прежнем `409`.

## 5. ETag и защита от потери изменений

### 5.1. Сценарий потери изменения

Два оператора открыли активный счёт версии 7. Первый блокирует его. Второй отправляет изменение, рассчитанное на прежнее
состояние, и может незаметно отменить действие первого. Защита должна сравнить прочитанную клиентом версию с текущей
и применить изменение только при совпадении.

Для учебного расширения команды блокировки:

```http
GET /api/v1/accounts/dc3fbc98-b93a-42a6-8d33-2fbbfcb95479

HTTP/1.1 200 OK
ETag: "account-dc3fbc98-b93a-42a6-8d33-2fbbfcb95479-v7"
```

Клиент сохраняет значение заголовка полностью, включая кавычки, и передаёт его обратно:

```http
POST /api/v1/accounts/dc3fbc98-b93a-42a6-8d33-2fbbfcb95479/block
If-Match: "account-dc3fbc98-b93a-42a6-8d33-2fbbfcb95479-v7"
```

Если версия актуальна, сервер атомарно изменяет состояние и возвращает `200` с новым представлением и ETag версии 8.
Если уже изменена — `412`, без блокировки по устаревшим данным. Если договорились требовать условие, отсутствие
`If-Match` может получать `428 Precondition Required`; это нужно отдельно добавить в контракт.

`If-Match` использует сильное сравнение. Метка с `W/` для этой защиты не подходит.
`If-Match: *` проверяет существование представления, но не подтверждает, что клиент видел его последнюю версию.
Источник: [RFC 9110, If-Match](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1).

### 5.2. ETag не просто номер строки БД

`version` — число, с которым приложение сравнивает состояние при записи. ETag — непрозрачная для клиента метка
представления ресурса. Сервер может построить её на версии, если гарантирует смену метки при каждом изменении
представления и учитывает его варианты. Например, изменение баланса тоже меняет ответ о счёте.

Если ответы различаются по составу, правам, языку или формату, одна версия строки не всегда даёт корректную сильную
метку для всех вариантов. Для учебной схемы достаточно одного фиксированного JSON-представления с версией, меняющейся
при любом его изменении. Клиент не разбирает ETag и не вычисляет следующий самостоятельно.

Упрощённая схема защищённой записи:

```text
получить текущее состояние
проверить доступ и допустимость команды
сопоставить If-Match с текущим представлением
атомарно записать новое состояние при прежней версии
если конкурент выиграл гонку — отклонить устаревшее условие
вернуть новое представление и метку
```

В будущей БД идея последнего шага сравнения выражается так:

```sql
UPDATE account
SET status = :new_status, version = version + 1
WHERE id = :id AND version = :expected_version;
```

Это иллюстрация сравнения и записи, а не полный код команды. Ноль изменённых строк требует выяснить причину;
бизнес-правила, транзакция и доступ остаются обязательными. Отдельный `if` в контроллере без атомарной записи
оставляет промежуток для гонки.

### 5.3. Разные конфликты требуют разных реакций

| Механизм                          | Что предотвращает                                  | Что делает клиент                                |
| --------------------------------- | -------------------------------------------------- | ------------------------------------------------ |
| `If-Match`                        | Изменение по устаревшему представлению             | Читает свежие данные и согласует действие        |
| `Idempotency-Key`                 | Повтор одной денежной команды                      | Повторяет прежнюю команду с прежним ключом       |
| Блокировка/версия в транзакции    | Конкурентное нарушение инвариантов сервиса         | Получает итог после ограниченных повторов        |

Проверка `If-None-Match` при чтении позволяет получить `304`, когда представление не изменилось; это отдельный
сценарий условного чтения. Он не защищает запись.

Для проекта `409 CONCURRENT_UPDATE` остаётся итоговым конфликтом внутренних конкурентных операций, который сервис
не смог разрешить допустимыми повторами. Если добавлено и не выполнено клиентское `If-Match`, результат — `412`.
Backend может повторить внутреннюю транзакцию по согласованной стратегии; он не должен молча заменить ожидаемую
клиентом версию новой и выполнить отвергнутое изменение.

<a id="retries"></a>

## 6. Проектирование повторов денежной операции

Механизм нормализации, область ключа и атомарное сохранение уже описаны в
[материале недели 7](../week-07/spring-mvc-and-rest.md#idempotency). Здесь уточняем договорённости, без которых frontend
не сможет правильно использовать этот механизм.

### 6.1. Жизненный цикл команды на клиенте

```text
Пользователь подтвердил перевод
  → сохранить неизменяемое тело и новый ключ
  → отправить
      201                         → завершено; сохранить id перевода
      сетевой обрыв / тайм-аут     → результат неизвестен; сохранить ключ и тело
      определённый бизнес-отказ   → показать причину
  → повтор неизвестного результата с тем же ключом и телом
```

Отмена `fetch` или истечение времени ожидания не доказывают отмену серверной транзакции. Повтор после такого случая
нельзя отправлять с новым ключом. Если пользователь хочет изменить получателя или сумму, сначала нужно выяснить исход
прежней операции: изменение формы не отменяет перевод, который мог уже завершиться.

Хранение только ключа недостаточно: клиент должен помнить точную логическую команду. Если перезагрузка страницы входит
в сценарий восстановления, требуется подходящее локальное хранение команды; его срок и очистка согласуются отдельно.
Ключ не является токеном доступа, и повтор проходит обычную проверку доступа.

### 6.2. Решения, которые нужно зафиксировать

Для практики недели 8 принимаем следующую учебную политику. Это уточнения к ТЗ, которые затем следует перенести в ADR:

| Вопрос                            | Учебное решение                                                            |
| --------------------------------- | -------------------------------------------------------------------------- |
| Допустимый ключ                   | 1–128 символов: латинские буквы, цифры, `_`, `-`; можно UUID               |
| Сумма на HTTP-границе             | Строка с ровно двумя десятичными знаками; максимальная длина 20            |
| Описание                          | Необязательно; отсутствие и `null` равнозначны, пустая строка отлична      |
| Неизвестные поля денежной команды | Отклонять с `400`; не игнорировать случайное новое поле                    |
| Завершённый бизнес-отказ          | Сохранить статус и тело; тот же ключ повторяет отказ                       |
| Ошибка входа или доступа          | Отказ до резервирования; результат денежной команды не сохранять           |
| Временный внутренний сбой         | Не фиксировать как завершённый результат при гарантированном откате        |
| Запрос ещё выполняется            | В однопроцессной практике дождаться под общим замком завершения            |
| Успешный повтор                   | Сохранённые `201`, тело и `Location`; новая денежная операция не создаётся |
| Корреляция                        | Заголовок отражает текущий HTTP-запрос; сохранённое тело не изменяется     |

Если сохранённая ошибка содержит `correlationId`, при повторе в теле остаётся идентификатор первого запроса, а заголовок
показывает текущий. Это нужно описать для поддержки. Отпечаток команды не включает ключ, JWT и идентификатор корреляции.

Правило хранения бизнес-отказов означает: если первый запрос получил `409 INSUFFICIENT_FUNDS`, пополнение счёта не
превратит повтор с тем же ключом в успешный перевод. Новое осознанное действие получает новый ключ. Можно выбрать иную
политику, но нельзя оставлять её неявной.

При сбое с неизвестным исходом транзакции нельзя просто удалить ключ: требуется выяснение результата. Именно поэтому
денежные изменения и сохранённый результат в итоговой версии должны фиксироваться согласованно в БД.

Срок защиты — не менее 24 часов по ТЗ. После истечения срока клиент не должен считать старый повтор безопасным:
запись могла быть удалена. Нужен отдельный сценарий сверки результата, а не бесконечный автоматический повтор.

### 6.3. Ограничения учебной реализации

Для in-memory версии допустим общий замок на все денежные изменения. При этом изменения обоих счетов, перевод,
две записи истории и результат команды должны фиксироваться как единое действие. Замок обеспечивает взаимное
исключение, но не откат: сначала подготовь результат и проверь условия, затем примени изменения без ожидаемых отказов.
Если применение может прерваться, нужен механизм восстановления. Не вызывай внешние системы в этом участке.

После перезапуска карта результатов теряется. Такая практика изучает наблюдаемое поведение API; устойчивость после
сбоев и работа нескольких экземпляров сервиса требуют этапа PostgreSQL и транзакций.

<a id="compatibility"></a>

## 7. Совместимость и версии

### 7.1. Совместимость определяется поведением старого клиента

Для входа сервер должен продолжать принимать ранее допустимые команды. Для выхода прежний клиент должен продолжать
понимать результаты. Проверять нужно оба направления.

| Изменение                              | Влияние на прежний клиент                                              |
| -------------------------------------- | ---------------------------------------------------------------------- |
| Новое необязательное поле запроса      | Обычно совместимо, если прежнее поведение сохраняется                  |
| Новое обязательное поле запроса        | Ломает прежние запросы                                                 |
| Новое поле ответа                      | Обычно совместимо при терпимом разборе; строгий клиент может сломаться |
| Удаление или переименование поля       | Ломает чтение/отправку этого поля                                      |
| `amount: string` → `amount: number`    | Меняет тип и точность; несовместимо                                    |
| Новый вариант `status`                 | Может сломать исчерпывающий `switch` и сгенерированный клиент          |
| `201` → `202` для перевода             | Меняет момент завершения и сценарий интерфейса                         |
| `400` → `422` при прежнем коде         | Может сломать маршрутизацию ошибок                                     |
| Уменьшение предела размера страницы    | Делает прежние допустимые запросы ошибочными                           |
| Новая обязательность `If-Match`        | Ломает команды клиентов, которые не отправляли условие                 |

«Добавление поля всегда безопасно» — слишком сильное утверждение. Полезно договориться: клиент терпим к новым полям
ответа, но неизвестный статус отображает безопасно и не разрешает действия, смысл которых не понимает.

Ужесточение проверки тоже может ломать контракт. В текущем коде перевода `amount` привязывается к `BigDecimal`;
одна такая привязка не гарантирует отклонение JSON-числа или строки с одним десятичным знаком. Пример OpenAPI ниже
выбирает строгую строковую форму. Её фактическое соблюдение нужно проверить; если API уже использовали внешние клиенты
с другой формой, понадобится миграция вместо внезапного отказа.

### 7.2. Как вводить новую версию

ТЗ уже выбирает версию в пути: `/api/v1`. Продолжаем этот подход. `info.version` в OpenAPI обозначает версию описания
API и не переключает маршрутизацию. Версия Maven-проекта и номер API тоже не обязаны совпадать.

Небольшое совместимое изменение обычно остаётся в `v1`. Для несовместимого перехода:

1. Описать конкретное несовместимое поведение и предложить совместимый вариант, если он возможен.
2. Подготовить `v2` и клиент, сохранив поддержку `v1` на период перехода.
3. Перевести потребителей и проверить использование старой версии по наблюдаемости.
4. Объявить срок завершения поддержки и только затем удалить `v1`.

Не нужно копировать всю бизнес-логику в новый пакет версии: разные HTTP-DTO и преобразования могут вызывать один
прикладной сервис. Обратная совместимость контролируется на публичной границе.

Для двух совместимых релизов полезен порядок «сначала backend, принимающий старое и новое, затем frontend».
Если сначала выпустить frontend, отправляющий новое поле строгому старому серверу, запросы будут отклонены.
Отдельно проверь сочетание старого клиента с новым сервером: пользователи могут долго держать открытую вкладку.

<a id="openapi"></a>

## 8. OpenAPI до реализации

### 8.1. Описание как проверяемая договорённость

Рабочая последовательность:

```text
сценарии → решения о поведении → OpenAPI → проверка схемы и примеров
         → пробная генерация клиента → реализация → проверка соответствия
```

Для каждой операции нужны уникальный и стабильный `operationId`, параметры и заголовки, схемы, типы содержимого,
успешный результат и ожидаемые отказы. Переименование `operationId` может изменить имя метода сгенерированного клиента,
хотя адрес сервера останется прежним.

В [примере контракта переводов](contracts/transfers.openapi.yaml) используется OpenAPI 3.0.3 как явно выбранная версия
формата. Это небольшой самостоятельный контракт для `POST /transfers` и `GET /transfers/{transferId}`, а не полное
описание Wallet Service. При выполнении заданий расширь его остальными маршрутами.

Для схем этой версии `required` у объекта определяет обязательные свойства, `nullable: true` разрешает `null`.
Отсутствие свойства в `required` не означает разрешение `null`. `default` в описании не реализует установку значения
в приложении. Источник: [OpenAPI 3.0.3](https://spec.openapis.org/oas/v3.0.3.html).

Для денег используем `type: string`, образец `1250.00` и ограничение формата. Регулярное выражение ограничивает запись,
но бизнес-условие «строго больше нуля» всё равно нужно реализовать: строковое `minimum` не заменяет проверку числа.
Идентификаторы — строки с `format: uuid`, время — `format: date-time` с договорённостью выдавать UTC.

В примере отдельно описаны JSON успешного ответа, `application/problem+json` ошибки, `Location`, корреляция и
`Idempotency-Key`. В описаниях зафиксированы повторы и хранение результатов: это поведение не выражается только типами.

### 8.2. Источник истины

Если сначала согласовывается YAML, он становится источником публичного контракта. Контроллеры должны ему соответствовать.
Если описание формируется из аннотаций, нужно проверять получаемый результат и изменения схемы при ревью.
Одновременное ручное редактирование двух независимых описаний быстро приводит к расхождениям.

Текущий `pom.xml` не содержит библиотеки генерации OpenAPI из Spring-кода. Для изучения контрактного подхода она
не нужна: схема и клиент могут генерироваться отдельно. Добавление Swagger UI — удобство просмотра, а не доказательство
правильного поведения API.

Минимальные проверки: описание корректно; клиент генерируется; фактические статусы, заголовки и тела совпадают со схемой;
новое описание не ломает прежние сценарии. Тест, использующий те же DTO, что и контроллер, способен не заметить
несовместимость с независимо заданным контрактом.

## 9. TypeScript-клиент и поведение интерфейса

### 9.1. Генерация

Для практики выбери `typescript-fetch` в OpenAPI Generator. Используй заранее скачанный JAR с зафиксированной версией;
замени путь в примере на фактический. Команды выполняются из корня репозитория в PowerShell:

```powershell
java -jar C:/tools/openapi-generator-cli.jar validate -i lerning-materials/week-08/contracts/transfers.openapi.yaml
java -jar C:/tools/openapi-generator-cli.jar generate -i lerning-materials/week-08/contracts/transfers.openapi.yaml -g typescript-fetch -o clients/wallet-typescript
```

Генератор — отдельный инструмент; версия Java проекта не выбирает его версию. Зафиксируй версию JAR и параметры
генерации в инструкции для воспроизводимости. Обновление генератора — отдельное изменение: оно может изменить методы
и преобразование данных. Документация: [команды](https://openapi-generator.tech/docs/usage/) и
[typescript-fetch](https://openapi-generator.tech/docs/generators/typescript-fetch/).

Сгенерированные файлы не редактируй вручную. Авторизация, понятные сообщения и управление жизненным циклом команды
располагаются в обёртке. Проверь созданные сигнатуры и путь `Raw` для доступа к статусу и заголовкам: точный код зависит
от зафиксированной версии генератора. В особенности проверь преобразование `date-time` и доступ к `Location`/ETag.

Генерация типов не гарантирует проверку произвольного JSON во время выполнения. TypeScript не проверяет входной ответ
сам по себе; преобразователи генератора также не следует считать полной проверкой всех ограничений схемы.

### 9.2. Что должна делать обёртка

| Результат                        | Реакция клиента                                                         |
| -------------------------------- | ----------------------------------------------------------------------- |
| `201`                            | Показать завершение, сохранить id, обновить балансы и историю           |
| `400 VALIDATION_ERROR`           | Показать ошибки полей; исправить команду до нового действия             |
| `404 ACCOUNT_NOT_FOUND`          | Обновить выбор счетов; объяснить, что ресурс недоступен                 |
| `409 INSUFFICIENT_FUNDS`         | Показать отказ и перечитать баланс; не повторять автоматически          |
| `409 IDEMPOTENCY_KEY_REUSED`     | Остановить повтор; выяснить расхождение сохранённой команды             |
| `409 CONCURRENT_UPDATE`          | Показать конфликт; повторять только по согласованной политике           |
| `412` при условной записи        | Перечитать ресурс и предложить подтвердить действие по новым данным     |
| `422` в альтернативном API       | Показать семантическую ошибку; для нашего API такой статус не ожидается |
| Нет ответа / `5xx`               | Считать исход денежной команды неопределённым; сохранить тело и ключ    |

Для неизвестного `code` нужен общий понятный отказ с идентификатором корреляции. Не делай любой `409` поводом для
автоматического повтора: недостаточный баланс, чужое тело под ключом и конкурентность требуют разных действий.
Повторы временных сбоев должны быть ограничены по числу и времени и использовать прежний ключ.

В React создание команды относится к подтверждению пользователем, а не к рендеру компонента или автоматически
перезапускаемому эффекту. Закрытие диалога не должно забывать перевод с неизвестным исходом.

Если клиент работает на другом origin, потребуется настройка CORS: разрешить отправку `Idempotency-Key` и `If-Match`,
а для чтения JavaScript-кодом открыть `Location`, `ETag`, `X-Correlation-Id` через `Access-Control-Expose-Headers`.
Иначе сервер может корректно вернуть заголовок, но браузер не позволит прочитать его из кода. Настройка безопасности
и CORS подробно изучается позже; здесь это зависимость будущего клиентского сценария.

## 10. Порядок изучения и самопроверка

На 7–10 часов этой недели:

1. Разбери разделы 1–5 и вручную проследи два конкурентных изменения одного ресурса.
2. Прочитай договорённости повторов и совместимости; составь собственную матрицу ошибок.
3. Изучи пример OpenAPI и проверь, что можешь восстановить поведение перевода без чтения Java-кода.
4. Выполни [задания недели 8](../../src/main/java/com/example/exercises/week_8/questions.md), начиная с контракта.
5. Открой описание API рабочего проекта и найди его решения по повторам, версиям и конфликтам.

Проверь себя:

- Почему перевод — отдельный ресурс, а баланс нельзя менять обычным редактированием счёта?
- В чём разница отсутствующего поля и `null` в Merge Patch и как это сохранить при привязке к Java?
- Почему PATCH с добавлением в массив может не быть идемпотентным?
- Что изменится для интерфейса, если перевод начнёт возвращать `202` вместо `201`?
- Почему два запроса с разными ключами идемпотентности всё равно могут нарушить баланс?
- Почему проверка ETag только в контроллере не защищает от гонки?
- Что делать после тайм-аута перевода и почему нельзя сразу выдать новый ключ?
- Почему `422` допустим в другом API, но не должен внезапно заменить `400` в нашем?
- Может ли добавление нового значения перечисления сломать старый TypeScript-клиент?
- Почему валидный OpenAPI ещё не доказывает соответствие работающего сервиса контракту?

После недели ты должен уметь объяснить решение в контракте через конкретный сценарий клиента и проверить его
наблюдаемые последствия. PostgreSQL, устойчивые записи идемпотентности, транзакции и блокировки будут следующими шагами.
