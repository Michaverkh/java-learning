# Технические требования: Wallet Service

[← Вернуться к учебному плану](../../java-backend-learning-plan.md)

## 1. Назначение

`Wallet Service` — учебный backend-сервис для управления клиентами и их
кошельками. Сервис должен позволять создавать кошельки, пополнять их, списывать
средства, переводить средства между кошельками и получать историю операций.

Проект нужен для последовательной практики Java и Spring Backend: от доменной
модели без фреймворков до production-like приложения с базой данных,
безопасностью, событиями, наблюдаемостью и CI.

Основной архитектурный стиль — модульный монолит. Разделение на микросервисы в
рамках проекта не требуется.

## 2. Границы проекта

### Входит в проект

- регистрация клиента;
- создание и просмотр кошельков клиента;
- пополнение и списание средств;
- перевод между кошельками;
- история операций с пагинацией;
- защита денежных операций от повторного выполнения;
- защита от отрицательного баланса и конкурентного списания;
- JWT-аутентификация и проверка прав доступа;
- аудит значимых действий;
- публикация событий о завершённых операциях;
- метрики, трассировка и структурированные логи;
- документирование REST API через OpenAPI.

### Не входит в проект

- выпуск банковских карт;
- комиссии, проценты, кредиты и овердрафт;
- обмен валют;
- перевод во внешние банки или платёжные системы;
- собственный authorization server;
- персональные данные, требующие полноценного KYC;
- web- или mobile-интерфейс;
- гарантированная доступность уровня реального банковского сервиса;
- разделение приложения на микросервисы.

## 3. Термины и допущения

- **Клиент** — владелец одного или нескольких кошельков.
- **Кошелёк** — счёт с уникальным идентификатором, валютой, статусом и балансом.
- **Операция** — пополнение, списание или перевод.
- **Ledger entry** — неизменяемая запись об изменении баланса кошелька.
- **Идемпотентный запрос** — повторный запрос с тем же ключом и телом, который
  возвращает прежний результат и не изменяет баланс повторно.
- Денежные суммы передаются как десятичные числа с двумя знаками после запятой.
- В первой версии поддерживается только валюта `RUB`, но валюта хранится явно.
- Время хранится в UTC и передаётся в формате ISO 8601.
- Публичные идентификаторы сущностей имеют формат UUID.

## 4. Роли и права

### `CUSTOMER`

- просматривает только собственные кошельки и операции;
- переводит средства только со своего кошелька;
- не может самостоятельно пополнять или списывать средства административной
  операцией.

### `OPERATOR`

- создаёт клиентов и кошельки;
- выполняет пополнение и административное списание;
- блокирует и разблокирует кошельки;
- просматривает клиентов, кошельки и операции для поддержки.

Для локальной разработки до внедрения Spring Security допускаются временные
тестовые заголовки с идентификатором клиента и ролью. В финальной версии сервис
работает как OAuth 2.0 Resource Server и валидирует JWT, выданный внешним
authorization server.

## 5. Доменная модель

### Client

- `id` — UUID;
- `externalId` — уникальный идентификатор клиента во внешней системе;
- `name` — отображаемое имя;
- `status` — `ACTIVE` или `BLOCKED`;
- `createdAt`, `updatedAt`.

### Account

- `id` — UUID;
- `clientId` — владелец;
- `currency` — `RUB`;
- `balance` — текущий баланс;
- `status` — `ACTIVE`, `BLOCKED` или `CLOSED`;
- `version` — версия для optimistic locking;
- `createdAt`, `updatedAt`.

### Transfer

- `id` — UUID;
- `sourceAccountId`;
- `targetAccountId`;
- `amount`;
- `currency`;
- `status` — `COMPLETED`;
- `description` — необязательное назначение перевода;
- `createdAt`, `completedAt`.

Сервис выполняет перевод синхронно и атомарно. Неуспешная попытка не создаёт
`Transfer` со статусом `COMPLETED`, но должна быть видна в техническом аудите.

### LedgerEntry

- `id` — UUID;
- `accountId`;
- `operationId` — идентификатор пополнения, списания или перевода;
- `operationType` — `DEPOSIT`, `WITHDRAWAL`, `TRANSFER_IN` или `TRANSFER_OUT`;
- `amount` — знаковое изменение баланса;
- `balanceAfter` — баланс после операции;
- `createdAt`.

Ledger entries после создания нельзя изменять или удалять через приложение.

### IdempotencyRecord

- `key` — значение заголовка `Idempotency-Key`;
- `operationType`;
- `requestHash` — отпечаток нормализованного запроса;
- `responseStatus`;
- `responseBody`;
- `createdAt`, `expiresAt`.

### OutboxEvent

- `id` — UUID события;
- `aggregateType`, `aggregateId`;
- `eventType`;
- `payload`;
- `createdAt`, `publishedAt`;
- `attempts`.

## 6. Бизнес-правила и инварианты

1. Сумма операции должна быть больше `0.00` и иметь не более двух знаков после
   запятой.
2. Баланс кошелька не может стать отрицательным.
3. Исходный и целевой кошельки перевода должны различаться.
4. Оба кошелька перевода должны существовать, иметь статус `ACTIVE` и одинаковую
   валюту.
5. Клиент со статусом `BLOCKED` не может инициировать перевод.
6. Кошелёк со статусом `CLOSED` нельзя разблокировать или использовать в новых
   операциях.
7. Закрыть можно только кошелёк с нулевым балансом.
8. Пополнение, списание, перевод, ledger entries и outbox event фиксируются в
   одной транзакции базы данных.
9. Перевод создаёт ровно две ledger entries: отрицательную для отправителя и
   положительную для получателя.
10. Сумма изменений балансов для одного перевода равна нулю.
11. Сохранённый баланс кошелька должен совпадать с результатом его ledger.
12. При конкурентных операциях сервис не должен допускать lost update,
    отрицательный баланс или частично выполненный перевод.
13. При блокировке двух кошельков сервис использует стабильный порядок по
    идентификатору, чтобы снизить риск deadlock.

## 7. REST API

Базовый путь API — `/api/v1`. Точные схемы запросов и ответов фиксируются в
OpenAPI и считаются частью контракта.

### Клиенты и кошельки

| Метод  | Endpoint                               | Назначение                                  | Роль       |
|---     |---                                     |---                                          |---         |
| `POST` | `/clients`                             | Создать клиента                             | `OPERATOR` |
| `GET`  | `/clients/{clientId}`                  | Получить клиента                            | `OPERATOR` |
| `POST` | `/clients/{clientId}/accounts`         | Создать кошелёк                             | `OPERATOR` |
| `GET`  | `/accounts/{accountId}`                | Получить кошелёк и текущий баланс           | обе        |
| `GET`  | `/clients/{clientId}/accounts`         | Получить кошельки клиента                   | обе        |
| `POST` | `/accounts/{accountId}/block`          | Заблокировать кошелёк                       | `OPERATOR` |
| `POST` | `/accounts/{accountId}/unblock`        | Разблокировать кошелёк                      | `OPERATOR` |
| `POST` | `/accounts/{accountId}/close`          | Закрыть кошелёк с нулевым балансом          | `OPERATOR` |

### Денежные операции

| Метод  | Endpoint                               | Назначение                                  | Роль       |
|---     |---                                     |---                                          |---         |
| `POST` | `/accounts/{accountId}/deposits`       | Пополнить кошелёк                           | `OPERATOR` |
| `POST` | `/accounts/{accountId}/withdrawals`    | Списать средства                            | `OPERATOR` |
| `POST` | `/transfers`                           | Перевести средства между кошельками         | обе        |
| `GET`  | `/transfers/{transferId}`              | Получить перевод                            | обе        |
| `GET`  | `/accounts/{accountId}/operations`     | Получить историю операций                   | обе        |

Все `POST`-запросы денежных операций требуют заголовок `Idempotency-Key`.
Идентификатор корреляции принимается в `X-Correlation-Id`; если заголовок
отсутствует, сервис генерирует его самостоятельно и возвращает в ответе.

Пример запроса перевода:

```http
POST /api/v1/transfers
Authorization: Bearer <token>
Idempotency-Key: 01J1WALLETEXAMPLE
Content-Type: application/json

{
  "sourceAccountId": "dc3fbc98-b93a-42a6-8d33-2fbbfcb95479",
  "targetAccountId": "f42c2df7-3275-4f30-9bd1-6be0375d3838",
  "amount": "1250.00",
  "currency": "RUB",
  "description": "Учебный перевод"
}
```

Успешное создание клиента, кошелька или денежной операции возвращает `201
Created`. Успешная команда изменения статуса возвращает `200 OK`. Запросы чтения
возвращают `200 OK`.

История операций поддерживает:

- `page` и `size`, причём `size` не превышает 100;
- сортировку по времени от новых операций к старым;
- фильтры `operationType`, `dateFrom` и `dateTo`;
- стабильную сортировку по `createdAt` и `id`.

## 8. Формат ошибок

Все ошибки возвращаются как `application/problem+json` в формате RFC 9457.
Ответ содержит:

- `type`;
- `title`;
- `status`;
- `detail`;
- `instance`;
- `code` — стабильный машинный код;
- `correlationId`;
- `errors` — ошибки отдельных полей для невалидного запроса.

Минимальный набор кодов:

| HTTP-статус | Код                         | Условие                                      |
|---          |---                          |---                                           |
| `400`       | `VALIDATION_ERROR`          | Некорректный формат или значение поля        |
| `401`       | `UNAUTHENTICATED`           | JWT отсутствует или невалиден                |
| `403`       | `ACCESS_DENIED`             | Нет доступа к ресурсу или операции           |
| `404`       | `CLIENT_NOT_FOUND`          | Клиент не найден                             |
| `404`       | `ACCOUNT_NOT_FOUND`         | Кошелёк не найден                            |
| `404`       | `TRANSFER_NOT_FOUND`        | Перевод не найден                            |
| `409`       | `INSUFFICIENT_FUNDS`        | Недостаточно средств                         |
| `409`       | `ACCOUNT_NOT_ACTIVE`        | Кошелёк нельзя использовать                  |
| `409`       | `CURRENCY_MISMATCH`         | Валюты операции и кошелька не совпадают      |
| `409`       | `IDEMPOTENCY_KEY_REUSED`    | Ключ повторно использован с другим запросом  |
| `409`       | `CONCURRENT_UPDATE`         | Конфликт не удалось устранить повторами      |

Внутренние исключения, SQL и stack trace клиенту не возвращаются.

## 9. Идемпотентность

1. Ключ идемпотентности уникален в пределах типа операции и авторизованного
   субъекта.
2. Первый запрос сохраняет отпечаток запроса и итоговый HTTP-ответ.
3. Повтор с тем же ключом и тем же нормализованным телом возвращает сохранённый
   статус и тело без новой денежной операции.
4. Повтор с тем же ключом, но другим телом возвращает `409
   IDEMPOTENCY_KEY_REUSED`.
5. Одновременные запросы с одним ключом должны приводить ровно к одному изменению
   баланса.
6. Записи хранятся не менее 24 часов. Удаление просроченных записей выполняется
   отдельной фоновой задачей.

## 10. Хранение данных и транзакции

- Основная СУБД — PostgreSQL.
- Схема создаётся и изменяется только миграциями Flyway.
- Минимальные таблицы: `client`, `account`, `transfer`, `ledger_entry`,
  `idempotency_record`, `outbox_event`, `audit_log`.
- Ограничения `NOT NULL`, `UNIQUE`, `FOREIGN KEY` и `CHECK` дублируют критичные
  инварианты на уровне базы данных.
- Для денег используется `numeric(19, 2)`, в Java — `BigDecimal`. `double` и
  `float` для денежных расчётов запрещены.
- Денежные операции имеют явно определённые transaction boundaries.
- Стратегия optimistic или pessimistic locking выбирается после конкурентного
  теста и фиксируется в ADR.
- Повтор транзакции разрешён только для заранее определённых временных конфликтов
  и выполняется ограниченное число раз.

## 11. События и outbox

После успешной операции сервис формирует одно из событий:

- `MoneyDeposited`;
- `MoneyWithdrawn`;
- `TransferCompleted`.

Событие содержит `eventId`, `eventType`, `occurredAt`, `correlationId`,
идентификаторы затронутых сущностей, сумму и валюту. Секреты, JWT и персональные
данные в payload не включаются.

Событие сначала записывается в `outbox_event` в транзакции денежной операции.
Фоновый publisher отправляет его в брокер и отмечает время публикации. Повторная
доставка допустима, поэтому consumer обязан обрабатывать событие идемпотентно.
После исчерпания попыток событие переводится в состояние, доступное для
диагностики и повторной отправки.

Конкретный брокер выбирается по технологиям рабочего проекта. Для локального
MVP разрешён in-memory consumer, но запись в outbox и контракт события должны
оставаться тестируемыми.

## 12. Безопасность

- Все endpoints, кроме health probes и OpenAPI в dev-профиле, требуют
  аутентификацию.
- JWT проверяется стандартными средствами Spring Security Resource Server.
- Проверяются подпись, `exp`, `iss` и `aud`.
- Права определяются ролями и принадлежностью кошелька клиенту.
- Сервис не хранит пароли и не выпускает токены.
- Токены, секреты и полные тела денежных запросов не записываются в логи.
- Конфигурация и секреты передаются через environment variables или внешний
  secret storage и не коммитятся в репозиторий.

## 13. Аудит и наблюдаемость

Аудит фиксирует:

- субъект и роль;
- тип действия;
- идентификаторы затронутых сущностей;
- результат `SUCCESS` или `FAILURE`;
- время, correlation ID и техническую причину отказа.

Обязательная наблюдаемость:

- Spring Boot Actuator;
- liveness и readiness probes;
- структурированные JSON-логи;
- correlation ID и trace ID во всех логах операции;
- метрики количества успешных и неуспешных операций;
- latency денежных операций;
- количество конфликтов блокировок, повторов и непубликованных outbox events;
- distributed trace для входящего HTTP-запроса, транзакции и публикации события.

## 14. Архитектурные ограничения

Приложение разделяется как минимум на модули или явно изолированные packages:

```text
wallet-service
├── clients
├── accounts
├── transfers
├── ledger
├── security
├── outbox
└── shared
```

- Доменная логика не размещается в controllers и repositories.
- Модули общаются через публичные application services и доменные контракты.
- `shared` не должен становиться хранилищем случайной бизнес-логики.
- Persistence entities не передаются напрямую через REST API.
- Зависимости направлены от инфраструктуры к application/domain contracts.
- Решения о блокировках, идемпотентности и границах модулей фиксируются в ADR.

## 15. Тестирование

### Unit-тесты

- все бизнес-инварианты;
- денежные расчёты и сравнение `BigDecimal`;
- переходы статусов;
- проверка прав;
- формирование событий.

### Integration-тесты с PostgreSQL в Testcontainers

- применение миграций на чистой базе;
- REST API пополнения, списания и перевода;
- rollback всех изменений при ошибке;
- уникальность idempotency key;
- повтор идемпотентного запроса;
- два конкурентных списания при недостаточном общем балансе;
- встречные конкурентные переводы без deadlock или нарушения ledger;
- согласованность `account.balance` и ledger;
- запись outbox event в одной транзакции с операцией;
- авторизация и запрет доступа к чужому кошельку.

Критичный concurrency test должен доказывать, что из двух одновременных списаний
по `80.00` с начального баланса `100.00` успешно выполняется ровно одно, а
итоговый баланс равен `20.00`.

## 16. Эксплуатация и поставка

- Приложение собирается Maven-командой из чистого checkout.
- Поддерживаются профили `local`, `test` и `prod`.
- Локальное окружение запускается через Docker Compose.
- Docker image запускается от непривилегированного пользователя.
- CI выполняет компиляцию, unit- и integration-тесты и проверку миграций.
- README содержит команды запуска, описание архитектуры, примеры API и принятые
  решения.

Целевые учебные показатели, не являющиеся production SLA:

- endpoint чтения отвечает не дольше 500 мс на p95 при локальном тестовом
  профиле;
- денежная операция отвечает не дольше 1 с на p95 без учёта холодного старта;
- сервис корректно завершает работу, переставая принимать новые запросы;
- повторный запуск не приводит к повторному применению операций или миграций.

## 18. Критерии готовности

Wallet Service считается завершённым, если:

1. все перечисленные endpoints реализованы и описаны в OpenAPI;
2. бизнес-инварианты защищены и приложением, и ограничениями БД, где это
   возможно;
3. повтор запроса не дублирует денежную операцию;
4. конкурентные тесты не воспроизводят отрицательный баланс, lost update или
   частичный перевод;
5. ledger остаётся согласованным с балансами;
6. доступ к чужим данным запрещён;
7. событие не теряется между фиксацией операции и публикацией;
8. unit- и integration-тесты проходят в CI;
9. приложение собирается и запускается по инструкции из README;
10. логи, метрики и traces позволяют найти и проследить операцию по correlation
    ID.
