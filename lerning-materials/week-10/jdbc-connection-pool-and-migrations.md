## 1. JDBC и роли компонентов

**JDBC** — стандартный API Java для работы с реляционными БД. Сам JDBC не знает протокол PostgreSQL: конкретную
реализацию даёт PostgreSQL JDBC Driver. Приложение обычно обращается к интерфейсам из `java.sql`, поэтому его код не
привязан к классам драйвера.

```text
JdbcTemplate
    │ берёт соединение
DataSource
    │ выдаёт свободное физическое соединение
HikariCP
    │ использует сетевое соединение и протокол PostgreSQL
PostgreSQL JDBC Driver
    │ TCP
PostgreSQL
```

| Компонент | Ответственность | Не делает |
|---|---|---|
| JDBC Driver | Переводит вызовы Java в протокол PostgreSQL и обратно | Не управляет размером пула приложения |
| `Connection` | Один сеанс приложения с БД | Не является «подключением навсегда» для одного HTTP-запроса |
| `DataSource` | Даёт кодy `Connection` | Не описывает таблицы и запросы |
| HikariCP | Хранит и переиспользует ограниченное число физических соединений | Не является пулом потоков и не ускоряет медленный SQL |
| `JdbcTemplate` | Выполняет JDBC-операцию, закрывает полученные ресурсы, переводит исключения | Не заменяет модель данных и бизнес-логику |
| Flyway | Версионирует и применяет изменения схемы | Не откатывает произвольные production-изменения автоматически |

В Node.js драйвер PostgreSQL и его пул часто вызываются прямо из кода (`pool.query(...)`). В Spring Boot те же роли
обычно скрыты за `DataSource` и `JdbcTemplate`; скрытие не отменяет необходимость понимать лимиты подключений и SQL.

### 1.1. Что такое пул приложения

**Пул приложения** — набор заранее созданных и переиспользуемых ограниченных ресурсов, которыми владеет приложение.
В контексте JDBC под этим обычно имеют в виду **пул соединений с БД**: HikariCP поддерживает несколько физических
сетевых соединений с PostgreSQL и временно выдаёт их выполняющимся операциям.

Когда запросу требуется БД, он берёт свободное соединение из пула, выполняет SQL и возвращает соединение обратно.
Следующему запросу не нужно снова устанавливать TCP-соединение и проходить аутентификацию. Число соединений ограничено:
если свободных нет, новый запрос ждёт ограниченное время, а затем получает ошибку таймаута.

Пул соединений не равен пулу потоков:

| Пул | Что хранит | Что ограничивает |
|---|---|---|
| Пул соединений | Соединения с PostgreSQL | Сколько операций одновременно обращаются к БД |
| Пул потоков | Потоки JVM | Сколько задач одновременно исполняет приложение |

Например, 100 HTTP-потоков могут обрабатывать запросы, но при пуле из 8 соединений лишь 8 из них одновременно
выполняют SQL. Остальные либо делают работу без БД, либо ждут свободное соединение. Увеличение числа потоков не
увеличивает лимит PostgreSQL, а увеличение пула не ускоряет один медленный запрос.

### 1.2. Что такое `DataSource`

`DataSource` — интерфейс JDBC (`javax.sql.DataSource`), через который код получает `Connection`. Это точка доступа к
соединениям с БД, а не сама БД и не конкретный пул. Главный метод выглядит так:

```java
Connection connection = dataSource.getConnection();
```

Код зависит от интерфейса `DataSource`, поэтому ему не нужно знать, как именно создаётся соединение. В разработке это
может быть HikariCP, в тесте — `DataSource` Testcontainers-базы, а в другом окружении — источник соединений, которым
управляет сервер приложений. В обычном Spring Boot приложении `DataSource` создаёт автоконфигурация по настройкам
`spring.datasource.*`, а HikariCP реализует его и управляет пулом.

Полученный `Connection` принадлежит вызвавшему коду: его нужно закрыть. Сам `DataSource` в Spring-приложении обычно
принадлежит контейнеру Spring; пользовательский код не закрывает его после каждого запроса.

### 1.3. Что такое соединение

`Connection` представляет сеанс с БД: в нём есть состояние транзакции, настройки сеанса и временные объекты.
Открытие физического соединения требует TCP-рукопожатия, аутентификации и выделения серверных ресурсов. Создавать
его для каждого запроса дорого и опасно при нагрузке, поэтому приложение обычно берёт его из пула.

Нельзя передавать один `Connection` между запросами, класть его в поле singleton-bean или хранить в доменном объекте.
Он не является потокобезопасным объектом общего назначения и его время жизни управляется инфраструктурой.

<a id="resources"></a>

## 2. Жизненный цикл JDBC-ресурсов

При прямом JDBC код, который получил ресурс, обязан его закрыть. Порядок вложенности важен: `ResultSet` зависит от
`PreparedStatement`, тот — от `Connection`.

```java
try (Connection connection = dataSource.getConnection();
     PreparedStatement statement = connection.prepareStatement("""
         select id, balance
         from account
         where id = ?
         """);) {
    statement.setObject(1, accountId);

    try (ResultSet result = statement.executeQuery()) {
        if (!result.next()) {
            return Optional.empty();
        }
        return Optional.of(new AccountBalance(
            result.getObject("id", UUID.class),
            result.getBigDecimal("balance")
        ));
    }
}
```

`close()` для connection, выданного HikariCP, обычно **не закрывает TCP-соединение**: оно возвращает его пулу. Не
закрыть такой объект означает удерживать соединение до исчерпания пула. Когда свободных соединений нет, следующий
поток ждёт `connection-timeout`, после чего HikariCP выбрасывает ошибку.

`JdbcTemplate` берёт на себя этот шаблон для обычных запросов. Поэтому нельзя одновременно использовать
`JdbcTemplate` и вручную закрывать переданный им `Connection`: владельцем ресурса в этом случае является шаблон.

<a id="pool"></a>

## 3. DataSource и HikariCP

`DataSource` — абстракция источника соединений. В Spring Boot при наличии JDBC starter создаётся `DataSource`; если
доступен HikariCP, он является стандартной реализацией. Для PostgreSQL нужны как минимум JDBC starter и драйвер:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-jdbc</artifactId>
</dependency>
<dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <scope>runtime</scope>
</dependency>
```

Версии библиотек, которыми управляет Spring Boot, вручную не указывай без причины: parent POM уже фиксирует
совместимый набор. После добавления starter не создавай `HikariDataSource` вручную, пока стандартной настройки
достаточно: второй `DataSource` меняет условия автоконфигурации и легко приводит к неожиданному запуску.

### 3.1. Размер пула — ограничение параллельности работы с БД

Пул содержит ограниченное число **одновременных** соединений. Если `maximum-pool-size: 10`, максимум десять операций
могут одновременно держать соединение. Двадцатый HTTP-поток не получает «десятое соединение быстрее» — он ждёт.

Размер пула не должен механически совпадать с количеством HTTP-потоков или ядер CPU. Он зависит от лимита PostgreSQL,
числа экземпляров приложения, длительности запросов и других потребителей БД. Например, четыре экземпляра с пулом
20 могут занять до 80 подключений, даже если один экземпляр редко нагружен. Начинай с умеренного значения, измеряй и
учитывай резерв для миграций, административных подключений и тестов.

| Настройка Hikari | Смысл | Типичная ошибка |
|---|---|---|
| `maximum-pool-size` | Верхняя граница выданных соединений | Поднять при медленном SQL вместо его анализа |
| `minimum-idle` | Сколько простаивающих соединений пул стремится держать | Считать это гарантированным числом активных запросов |
| `connection-timeout` | Как долго ждать свободное соединение | Сделать огромным и скрыть утечку или перегрузку |
| `max-lifetime` | Когда пул заменяет старое соединение | Поставить больше лимита инфраструктуры и получать разрывы |
| `idle-timeout` | Когда допускается убрать лишнее простаивающее соединение | Ожидать, что оно применяется к активному соединению |

Пример для локальной среды, не production-рекомендация:

```yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/wallet
    username: wallet_app
    password: ${WALLET_DB_PASSWORD}
    hikari:
      maximum-pool-size: 8
      connection-timeout: 3000
```

Пароль не коммитируется в `application.yml`. Для локального запуска его передают переменной окружения, а в production —
системой управления секретами. `application-prod.yml` внутри JAR не делает секрет безопасным: это уже обсуждалось в
[неделе 6](../week-06/spring-boot-and-configuration.md).

### 3.2. Как диагностировать проблему пула

Сообщение о том, что соединение недоступно после таймаута, — симптом, а не диагноз. Проверь по порядку:

1. Есть ли медленные запросы или блокировки в PostgreSQL.
2. Возвращаются ли соединения пулу: нет ли прямого JDBC без `try-with-resources`.
3. Не удерживается ли connection во время HTTP-вызова, тяжёлого вычисления или ожидания очереди.
4. Достаточен ли лимит PostgreSQL с учётом всех экземпляров приложения.
5. Только затем — разумен ли размер пула.

Не решай это добавлением `@Async`: оно создаёт другую очередь ожидания, но не увеличивает пропускную способность БД.

## 4. Параметры, PreparedStatement и SQL injection

Пользовательское значение нельзя склеивать с SQL-строкой. В уязвимом примере значение становится частью синтаксиса:

```java
String sql = "select id from account where id = '" + accountId + "'";
```

Если вход содержит кавычку и фрагмент SQL, его смысл может измениться. Экранирование вручную ненадёжно. Используй
параметры `PreparedStatement`: SQL и значения передаются отдельно.

```java
String sql = "select id, balance from account where id = ?";
try (PreparedStatement statement = connection.prepareStatement(sql)) {
    statement.setObject(1, accountId);
    try (ResultSet result = statement.executeQuery()) {
        // чтение результата
    }
}
```

Это не просто подстановка строки в `?`. Драйвер передаёт значение как данные нужного типа, поэтому оно не становится
ключевым словом, оператором или кавычкой в запросе. Подготовленный запрос также даёт БД возможность повторно
использовать подготовку, но защита от injection — обязательная причина его применения.

Параметром можно передать **значение**, но не имя таблицы, имя столбца, направление `ORDER BY` или SQL-оператор.
Если API выбирает сортировку, сопоставь допустимое значение с заранее заданным SQL-фрагментом:

```java
String orderBy = switch (sort) {
    case CREATED_AT_ASC -> "created_at asc, id asc";
    case CREATED_AT_DESC -> "created_at desc, id desc";
};
String sql = "select id from ledger_entry where account_id = ? order by " + orderBy;
```

Здесь конкатенация безопасна только потому, что `orderBy` не взят из строки запроса, а получен из закрытого `enum`.
Проверка DTO, права доступа и SQL-параметры дополняют друг друга: параметризация не отвечает на вопрос, имеет ли
пользователь право читать этот счёт.

<a id="jdbc-template"></a>

## 5. JdbcTemplate

`JdbcTemplate` — тонкий слой Spring над JDBC. Он получает connection из `DataSource`, выполняет callback, закрывает
`Statement` и `ResultSet`, возвращает connection пулу и переводит `SQLException` в иерархию `DataAccessException`.
Последнее — unchecked-исключения Spring с более понятными категориями, например нарушение уникальности может стать
`DuplicateKeyException`. Не привязывай бизнес-правило к тексту сообщения PostgreSQL: при необходимости переводи
инфраструктурную ошибку в осмысленное прикладное исключение на границе репозитория.

```java
@Repository
public class JdbcAccountBalanceReader {
    private final JdbcTemplate jdbcTemplate;

    public JdbcAccountBalanceReader(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = jdbcTemplate;
    }

    public Optional<AccountBalance> findById(UUID accountId) {
        return jdbcTemplate.query("""
                select id, balance
                from account
                where id = ?
                """,
            (resultSet, rowNumber) -> new AccountBalance(
                resultSet.getObject("id", UUID.class),
                resultSet.getBigDecimal("balance")
            ),
            accountId
        ).stream().findFirst();
    }
}
```

Для одного объекта можно использовать `queryForObject`, но отсутствие строки — нормальный сценарий поиска, а не
обязательно исключение. Явный список и `Optional` делают это видимым. Для пакетных операций, именованных параметров
и более сложной сборки запросов есть `NamedParameterJdbcTemplate`; это всё ещё JDBC, а не ORM.

Репозиторий хранит SQL и отображение строки в объект. Контроллер не должен вызывать `JdbcTemplate`, а `RowMapper` не
должен проверять лимит перевода или достаточность баланса: это ответственность доменной и прикладной логики.

<a id="configuration"></a>

## 6. Конфигурация PostgreSQL

Для URL PostgreSQL применяется вид `jdbc:postgresql://host:port/database`. Настройки различаются по средам, но их
структура должна оставаться одинаковой:

```yaml
spring:
  datasource:
    url: ${WALLET_DB_URL:jdbc:postgresql://localhost:5432/wallet}
    username: ${WALLET_DB_USERNAME:wallet_app}
    password: ${WALLET_DB_PASSWORD}
  flyway:
    enabled: true
```

Переменные окружения удобны для секретов и адреса, но не являются секретным хранилищем сами по себе: не выводи их в
логи и не передавай через небезопасные каналы. Локальный `test`-профиль в будущих integration-тестах будет направлен
на Testcontainers, а не на общую разработческую базу.

Пользователь приложения получает минимум нужных прав. Не запускай сервис суперпользователем `postgres`. Отдельная
роль владельца миграций и ограниченная роль приложения — полезное production-разделение, но на учебном локальном
окружении можно начать с одного пользователя и явно записать это упрощение.

<a id="flyway"></a>

## 7. Миграции Flyway

**Flyway** — инструмент управления миграциями базы данных. Он хранит изменения схемы в файлах рядом с исходным кодом,
при запуске сравнивает их с историей конкретной базы и применяет только недостающие изменения. Благодаря этому локальная,
тестовая и production-базы получают одну и ту же схему воспроизводимым способом, без ручного выполнения SQL.

Миграция — маленькое неизменяемое изменение схемы. Flyway применяет их в порядке версий и сохраняет факт применения,
контрольную сумму, время и результат в `flyway_schema_history`. При новом запуске уже применённая миграция не должна
выполниться ещё раз.

В Spring Boot 4 добавь starter Flyway и модуль PostgreSQL:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-flyway</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
</dependency>
```

SQL-файлы по умолчанию лежат в `src/main/resources/db/migration`. Имена имеют вид
`V<версия>__<краткое_описание>.sql`; между версией и описанием — два подчёркивания.

```text
src/main/resources/db/migration/
├── V1__create_wallet_tables.sql
├── V2__add_idempotency_records.sql
└── V3__add_transfer_description.sql
```

Первая миграция создаёт минимум из требований: `client`, `account`, `transfer`, `ledger_entry`,
`idempotency_record`, `outbox_event`, `audit_log`, а также критичные `NOT NULL`, `UNIQUE`, `FOREIGN KEY` и `CHECK`.
Схему из SQL-лаборатории недели 9 можно взять как отправную точку, но не копируй лабораторные `DROP TABLE`, seed-данные
и эксперименты в production-миграцию.

Для Spring Boot добавь Flyway вместе с JDBC-доступом. При старте Boot создаёт `DataSource`, затем Flyway применяет
миграции, и только затем компоненты приложения начинают работать со схемой. Если миграция не прошла, запуск должен
остановиться: приложение со старой или наполовину подготовленной схемой опаснее явной ошибки запуска.

### 7.1. Не изменяй применённую версионную миграцию

После применения `V1__create_wallet_tables.sql` в общей среде она становится историческим фактом. Её изменение меняет
контрольную сумму, и Flyway обнаружит расхождение. Правильный путь — новая миграция, например
`V4__add_account_closed_at.sql`. Исключение — личная одноразовая база до передачи миграции другим разработчикам;
даже там проще создать базу заново, чем приучаться переписывать историю.

Ошибку контрольной суммы нельзя «лечить» отключением проверки или массовым `repair` без понимания причины.
`repair` корректирует метаданные Flyway, но не меняет фактическую схему и потому не исправляет несовпадение БД с
ожиданиями приложения.

<a id="rollback"></a>

## 8. Изменение схемы и rollback

Откат миграции — не то же самое, что rollback SQL-транзакции. Некоторые DDL-операции можно выполнить в транзакции,
но возврат уже развернутой схемы часто требует отдельного изменения данных, совместимости кода и ручного решения.
В обычном сценарии Flyway с версионными SQL-миграциями безопасная стратегия — **новая миграция вперёд**, а не правка
или удаление старой.

| Изменение | Риск | Безопасная последовательность |
|---|---|---|
| Добавить nullable столбец | Низкий | Добавить столбец → начать записывать его → позже сделать обязательным |
| Переименовать столбец | Старый код перестанет читать/писать | Добавить новый → читать оба/перенести данные → переключить код → удалить старый отдельной миграцией |
| Сделать `NOT NULL` | В старых строках могут быть `NULL` | Добавить столбец → заполнить существующие данные → добавить ограничение |
| Удалить столбец или таблицу | Потеря данных и несовместимость | Сначала прекратить использование и пройти период совместимости; удалять отдельным релизом |
| Изменить тип денег | Возможны округление и блокировка | Проверить данные, мигрировать поэтапно, иметь резервную копию и план восстановления |

В production откат приложения на старую версию должен, по возможности, продолжать работать с новой схемой. Поэтому
сначала выпускают расширение схемы, потом код, и лишь после исчезновения старого кода — сужение схемы. Это особенно
важно при rolling deployment, когда одновременно живут две версии сервиса.

Перед рискованным изменением нужны резервная копия, проверка на копии данных, план возврата и наблюдение. Flyway Undo
миграции не следует считать универсальным механизмом и в используемой редакции инструмента они могут быть недоступны;
в учебном проекте зафиксируй стратегию «миграции только вперёд».

## 9. Локальный запуск PostgreSQL

В корне проекта создай `compose.yaml`; локальные данные храни в именованном Docker volume, а не в каталоге исходников.
Пароль передай из файла `.env`, который добавлен в `.gitignore`, либо через окружение оболочки.

```yaml
services:
  postgres:
    image: postgres:18
    environment:
      POSTGRES_DB: wallet
      POSTGRES_USER: wallet_app
      POSTGRES_PASSWORD: ${WALLET_DB_PASSWORD}
    ports:
      - "5432:5432"
    volumes:
      - wallet-postgres:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U wallet_app -d wallet"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  wallet-postgres:
```

Запуск из PowerShell:

```powershell
$env:WALLET_DB_PASSWORD = "локальный-пароль"
docker compose up -d
./mvnw spring-boot:run
```

В образе PostgreSQL путь к данным может зависеть от его версии и образа. Перед закреплением версии проверь официальный
образ и его документацию; не меняй путь volume наугад, иначе данные могут оказаться не там, где ожидается. Команда
`docker compose down -v` удаляет именованный volume с локальной БД — применяй её только когда намеренно хочешь начать
с чистой базы.

## 10. Маршрут, практика и самопроверка

### Маршрут на 7–10 часов

1. Добавь PostgreSQL JDBC driver, `spring-boot-starter-jdbc` и Flyway; убедись, что проект собирается.
2. Подними PostgreSQL через Compose и передай пароль только окружением.
3. Перенеси учебную схему в начальные миграции без seed-данных и без `DROP`.
4. Запусти приложение дважды: первый запуск применяет миграции, второй не меняет схему.
5. Реализуй чтение баланса и истории счёта через `JdbcTemplate` с параметрами.
6. Создай отдельную новую миграцию для небольшого изменения схемы; не редактируй первую.
7. Искусственно передай неверный SQL в новой локальной миграции, прочитай ошибку, затем восстанови чистую личную БД
   или корректно добавь следующую миграцию — в зависимости от того, где ошибка успела быть применена.

Полные задания и критерии находятся в [практике недели](../../src/main/java/com/example/exercises/week_10/questions.md).
