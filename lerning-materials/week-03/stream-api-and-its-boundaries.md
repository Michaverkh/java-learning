# Stream API и границы его применения

[← Вернуться к учебному плану](../java-backend-learning-plan.md)

Stream API позволяет описать обработку последовательности: выбрать записи, преобразовать их и получить результат. Для
Wallet Service это удобно при подготовке истории и расчёте оборотов по уже загруженным данным. Для выполнения самого
перевода важнее явно показать проверки, изменение состояния и границу транзакции.

Материал рассчитан на Java 21. Синтаксис лямбд, функциональные интерфейсы и ссылки на методы уже разобраны
в [предыдущем разделе](lambda-expressions-and-functional-interfaces.md), коллекции и порядок элементов —
в [Collections Framework](collections-framework.md), `Optional` —
в [разделе о типах](../week-02/type-design-nullability-and-generics.md). Здесь сосредоточимся на обработке данных.

## 1. Модель: источник → преобразования → результат

```java
List<UUID> accountIds = entries.stream()
        .filter(entry -> entry.amount().signum() < 0)
        .map(LedgerEntry::accountId)
        .distinct()
        .toList();
```

Читаем по шагам:

1. `entries.stream()` создаёт поток элементов списка.
2. `filter` оставляет записи с отрицательным изменением баланса.
3. `map` извлекает идентификатор счёта из каждой записи.
4. `distinct` убирает повторяющиеся идентификаторы.
5. `toList` запускает обработку и собирает результат.

Здесь **поток элементов** (`Stream`) не означает поток исполнения (`Thread`). Вызов `stream()` сам по себе не запускает
фоновую задачу. Обычная последовательная цепочка выполняется синхронно при терминальной операции. Это также не
`InputStream`, не `Promise` и не подписка на будущие события.

Коллекция хранит элементы, а `Stream` описывает их обход и обработку. У него нет доступа по индексу; результат можно
получить как список, число, `Optional`, словарь или действие.

### Сравнение с TypeScript

```typescript
const accountIds = [...new Set(
    entries.filter(entry => entry.amount < 0).map(entry => entry.accountId)
)];
```

Это аналогия формы обработки; денежную арифметику из Java не следует переносить на JavaScript `number` без отдельного
решения.

У обычного массива JavaScript `filter` сразу обходит массив и создаёт новый массив, затем `map` обходит результат. В
Java промежуточные операции задают отложенные шаги. Простая цепочка `filter → map` может обрабатывать элементы по
одному, без промежуточного списка между шагами. Но сортировка и некоторые другие операции требуют накопления данных.

## 2. Модель данных для примеров

Фрагменты ниже предполагают следующие объявления и переменную `List<LedgerEntry> entries`. Типы — учебная проекция
из [требований Wallet Service](../projects/wallet-service/technical-requirements.md), а не новая обязательная реализация
существующих классов проекта.

```java
import java.math.BigDecimal;
import java.time.Instant;
import java.util.*;
import java.util.function.Function;
import java.util.stream.*;

enum OperationType {DEPOSIT, WITHDRAWAL, TRANSFER_IN, TRANSFER_OUT}

record LedgerEntry(
        UUID id,
        UUID accountId,
        UUID operationId,
        OperationType operationType,
        BigDecimal amount,
        BigDecimal balanceAfter,
        Instant createdAt
) {
}
```

В примерах все обязательные поля заполнены, суммы имеют два знака после запятой, все счета в `RUB`.
`amount` — **знаковое изменение**: поступление положительно, расход отрицателен. Перевод создаёт две записи с одним
`operationId`. Комиссии в проект не входят.

## 3. Создание, ленивость и одноразовость

### Источники

```java
Stream<LedgerEntry> fromList = entries.stream();
Stream<String> fromValues = Stream.of("DEPOSIT", "WITHDRAWAL");
Stream<String> fromArray = Arrays.stream(new String[]{"RUB", "USD"});
Stream<LedgerEntry> empty = Stream.empty();
Stream<String> zeroOrOne = Stream.ofNullable(null); // пустой поток
IntStream indexes = IntStream.range(0, entries.size()); // правая граница исключена
Stream<Integer> firstFive = Stream.iterate(1, n -> n + 1).limit(5);
```

У `Map` сначала выбирают представление: `entrySet().stream()`, `keySet().stream()` или `values().stream()`. У
`Optional<T>` есть `stream()`: ноль или один элемент.

`iterate(seed, next)` и `generate(supplier)` могут создавать бесконечные потоки. Ограничение должно позволять завершить
обработку: `iterate(...).sorted().limit(5)` не поможет, потому что сортировка бесконечного источника не закончится.

### Когда исполняется лямбда

```java
Stream<Integer> pipeline = Stream.of(1, 2, 3, 4)
        .filter(n -> {
            System.out.println("filter " + n);
            return n % 2 == 0;
        })
        .map(n -> {
            System.out.println("map " + n);
            return n * 10;
        });

// До этой строки ничего не напечатано.
Optional<Integer> first = pipeline.findFirst();
```

Для этой последовательной цепочки увидишь `filter 1`, `filter 2`, `map 2`; результат — `Optional[20]`. Числа 3 и 4 не
нужны: `findFirst` прекращает поиск после первого результата. Печать здесь служит только учебному наблюдению;
обязательные действия так размещать нельзя.

Ленивость не означает, что вообще всё откладывается: выражение, получающее исходный список, и аргументы вызовов
вычисляются обычным образом. Откладывается обработка элементов.

### Повторный обход требует нового потока

```java
Stream<LedgerEntry> stream = entries.stream();
long count = stream.count();
// stream.toList(); // повторное использование запрещено, обычно IllegalStateException

long anotherCount = entries.stream().count();
List<LedgerEntry> copy = entries.stream().toList();
```

Нельзя и строить две независимые ветки от одного `Stream`. Храни исходные данные или функцию создания нового потока. Не
храни использованный поток в поле сервиса как переиспользуемый запрос.

Поток из списка не является снимком данных: создание `stream()` не копирует список и его элементы. Во время обработки не
меняй источник; для обычных коллекций это может привести к ошибке или некорректному результату.

## 4. Промежуточные и терминальные операции

| Операция                            | Категория     | Назначение                                        |
|-------------------------------------|---------------|---------------------------------------------------|
| `filter(predicate)`                 | промежуточная | оставить подходящие элементы                      |
| `map(function)`                     | промежуточная | преобразовать каждый элемент                      |
| `flatMap(function)`                 | промежуточная | объединить вложенные потоки                       |
| `distinct()`                        | промежуточная | убрать повторы по `equals`                        |
| `sorted(comparator)`                | промежуточная | задать порядок                                    |
| `limit(n)`, `skip(n)`               | промежуточная | ограничить число элементов, пропустить первые     |
| `takeWhile`, `dropWhile`            | промежуточная | взять или пропустить начальный подходящий участок |
| `toList()`, `collect(...)`          | терминальная  | собрать результат                                 |
| `reduce(...)`                       | терминальная  | объединить элементы в значение                    |
| `count()`, `min`, `max`             | терминальная  | посчитать или найти крайнее значение              |
| `findFirst()`, `findAny()`          | терминальная  | найти элемент                                     |
| `anyMatch`, `allMatch`, `noneMatch` | терминальная  | проверить условие                                 |
| `forEach`, `forEachOrdered`         | терминальная  | выполнить действия                                |

Промежуточная операция возвращает поток, поэтому цепочку можно продолжить. Терминальная завершает цепочку. Не каждая
терминальная операция обходит все элементы:
поиск и проверки условий могут закончиться раньше.

`takeWhile(n -> n < 3)` для последовательности `1, 2, 4, 1` даст `1, 2`, а `filter(n -> n < 3)` даст `1, 2, 1`.
`takeWhile` работает с начальным участком, поэтому для понятного результата здесь нужен определённый порядок источника.

### `filter` и `map`: следи за типом

```java
List<BigDecimal> expenses = entries.stream()       // Stream<LedgerEntry>
        .filter(e -> e.amount().signum() < 0)       // Stream<LedgerEntry>
        .map(LedgerEntry::amount)                  // Stream<BigDecimal>
        .map(BigDecimal::abs)                     // Stream<BigDecimal>
        .toList();                                // List<BigDecimal>
```

После извлечения суммы вызвать `LedgerEntry::accountId` уже нельзя: в потоке больше нет записей. Если дальнейшему
расчёту нужны несколько полей, сохрани запись до этого шага или создай промежуточный `record`.

### `flatMap`: один элемент даёт несколько

```java
List<List<LedgerEntry>> batches = List.of(entries, List.of());

List<LedgerEntry> flattened = batches.stream() // Stream<List<LedgerEntry>>
        .flatMap(List::stream)                // Stream<LedgerEntry>
        .toList();
```

`map(List::stream)` дал бы `Stream<Stream<LedgerEntry>>`: сами вложенные потоки стали бы элементами.
`flatMap` включает их содержимое в общую последовательность. Пустой вложенный поток добавляет ноль элементов. Аналогично
`optionalValues.stream().flatMap(Optional::stream)` убирает пустые `Optional` и извлекает присутствующие значения.

### Поиск и проверки

```java
boolean hasExpenses = entries.stream().anyMatch(e -> e.amount().signum() < 0);
boolean allNonZero = entries.stream().allMatch(e -> e.amount().signum() != 0);
Optional<LedgerEntry> largest = entries.stream()
        .max(Comparator.comparing(e -> e.amount().abs()));
```

Для пустого потока `anyMatch` даёт `false`, `allMatch` и `noneMatch` — `true`. Поэтому `allMatch` сам по себе не
доказывает, что записи вообще существуют.
`findFirst`, `findAny`, `min`, `max` возвращают пустой `Optional`, если элементов нет.

`findFirst` учитывает порядок источника, если он определён. `findAny` допускает любой подходящий элемент:
не используй его, когда бизнес-правило требует самую раннюю запись.

## 5. `reduce`: получить одно значение

Посчитаем исходящий оборот одного счёта положительным числом:

```java
BigDecimal outgoing = entries.stream()
        .filter(e -> e.accountId().equals(accountId)) // UUID accountId задан вызывающим кодом
        .map(LedgerEntry::amount)
        .filter(amount -> amount.signum() < 0)
        .map(BigDecimal::abs)
        .reduce(new BigDecimal("0.00"), BigDecimal::add);
```

Первый аргумент — нейтральное значение: прибавление нуля не меняет денежную величину. Второй — правило объединения двух
значений. Для сумм `100.00` и `50.00` результат `150.00`; для пустой последовательности — `0.00`.

Без начального значения `reduce(BigDecimal::add)` возвращает `Optional<BigDecimal>`:
для пустой последовательности нечего возвращать.

### Почему нельзя передать произвольную формулу

Операция объединения должна быть ассоциативной: группировка не меняет результат. Сложение подходит:
`(a + b) + c = a + (b + c)`. Вычитание не подходит:
`(10 - 3) - 2 = 5`, а `10 - (3 - 2) = 9`. Это необходимо для корректного объединения частичных результатов при
параллельном выполнении.

Начальное значение должно быть нейтральным для объединения. `reduce(100, Integer::sum)` не является корректным способом
прибавить 100 к сумме для произвольного режима выполнения: частичные расчёты могут начаться каждый со 100. Сначала сложи
с нулём, потом прибавь 100 один раз.

У `reduce` есть форма с тремя аргументами: начальное значение, накопление элемента и объединение частичных результатов.
Например, `reduce(0, (sum, text) -> sum + text.length(), Integer::sum)`
преобразует строки в общий размер. Правила накопления и объединения должны быть согласованы. Обычно отдельный `map` или
`mapToInt` делает такой расчёт понятнее.

Для денег используй `BigDecimal`. Сложение здесь выполняется без промежуточного округления; округление на каждом шаге
может сделать результат зависимым от группировки вычислений. Не переводи суммы в `double` ради `sum()`.

### Примитивные потоки

```java
int totalLength = Stream.of("DEPOSIT", "WITHDRAWAL")
        .mapToInt(String::length)
        .sum();
```

`IntStream`, `LongStream`, `DoubleStream` предоставляют `sum`, `average`, `summaryStatistics`
и избегают объектных обёрток для элементов. `boxed()` возвращает поток объектов-обёрток.
`count()` любого потока возвращает `long`; `average()` примитивного потока может вернуть пустой `OptionalDouble`. Для
`BigDecimal` отдельного стандартного потока нет, поэтому подходит `reduce`.

## 6. `collect`: собрать структуру результата

`reduce` удобен для объединения значений, а `collect` — для накопления в контейнере:
списке, множестве, словаре. `Collector` описывает создание контейнера, добавление элементов, объединение частичных
контейнеров и, при необходимости, окончательное преобразование.

### Какой список получится

```java
List<LedgerEntry> readOnly = entries.stream().toList();
List<LedgerEntry> mutable = entries.stream()
        .collect(Collectors.toCollection(ArrayList::new));
```

`Stream.toList()` возвращает неизменяемый по структуре список: `add`, `remove`, `set` запрещены. Это не глубокая копия:
если элементы изменяемы, их внутреннее состояние не защищено. У `Collectors.toList()` нет гарантии конкретной реализации
и изменяемости — не строй на этом контракт метода.
`Collectors.toUnmodifiableList()` явно запрещает изменения и не принимает `null`;
`Stream.toList()` допускает `null`, если они были в потоке. Для доменных данных лучше исключить их на входной границе.

### Группировка по счёту

```java
Map<UUID, List<LedgerEntry>> byAccount = entries.stream()
        .collect(Collectors.groupingBy(LedgerEntry::accountId));
```

Классификатор `LedgerEntry::accountId` выбирает ключ. Для каждого ключа коллектор собирает отдельный список. Типичный
смысл: «для каждого счёта получить его записи». Порядок ключей по умолчанию не гарантирован.

Второй коллектор задаёт, **что считать внутри каждой группы**:

```java
Map<UUID, Long> counts = entries.stream()
        .collect(Collectors.groupingBy(
                LedgerEntry::accountId,
                Collectors.counting()
        ));

Map<UUID, BigDecimal> netChanges = entries.stream()
        .collect(Collectors.groupingBy(
                LedgerEntry::accountId,
                Collectors.reducing(
                        new BigDecimal("0.00"),
                        LedgerEntry::amount,
                        BigDecimal::add
                )
        ));
```

`netChanges` — чистое изменение баланса за выбранный набор записей, а не оборот и не обязательно текущий баланс. Сумма
`+1000.00`, `-250.00`, `-100.00` равна `650.00`, входящий оборот — `1000.00`, исходящий — `350.00`. Чтобы восстановить
баланс, нужна полная история от известного начального баланса. Счёт без записей в результат `groupingBy` не попадёт.

### `toMap`: что делать с повторяющимся ключом

```java
Map<UUID, LedgerEntry> byId = entries.stream()
        .collect(Collectors.toMap(LedgerEntry::id, Function.identity()));
```

Если два элемента имеют одинаковый ключ, эта форма бросит `IllegalStateException`. Для уникальных идентификаторов это
полезный сигнал о нарушении ожиданий. Не добавляй `(first, second) -> first` только ради подавления ошибки: так теряются
данные.

Для осмысленного объединения задай явное правило:

```java
Map<UUID, BigDecimal> netByAccount = entries.stream()
        .collect(Collectors.toMap(
                LedgerEntry::accountId,
                LedgerEntry::amount,
                BigDecimal::add
        ));
```

Повторяющийся счёт здесь ожидаем: суммы объединяются. Если важен порядок первого появления ключей, четвёртым аргументом
можно передать `LinkedHashMap::new` для упорядоченного последовательного источника.

### Другие полезные коллекторы

| Коллектор                   | Когда пригодится                                   |
|-----------------------------|----------------------------------------------------|
| `toSet()`                   | уникальные значения, без гарантии порядка          |
| `mapping(f, downstream)`    | преобразовать элементы внутри группы перед сборкой |
| `partitioningBy(predicate)` | разделить на две группы с ключами `true` и `false` |
| `joining(", ")`             | соединить строки с разделителем                    |
| `counting()`                | посчитать элементы внутри группы                   |
| `reducing(zero, f, op)`     | преобразовать и объединить значения внутри группы  |

Например, типы операций каждого счёта:

```java
Map<UUID, Set<OperationType>> types = entries.stream()
        .collect(Collectors.groupingBy(
                LedgerEntry::accountId,
                Collectors.mapping(LedgerEntry::operationType, Collectors.toSet())
        ));
```

Для начала достаточно этих вариантов. Если вложенные коллекторы перестали читаться как понятный расчёт, вынеси этап в
именованный метод или используй цикл.

## 7. Порядок и стоимость обработки

Для истории из требований проекта нужны новые записи сначала и стабильный порядок при совпадении времени:

```java
Comparator<LedgerEntry> newestFirst = Comparator
        .comparing(LedgerEntry::createdAt)
        .thenComparing(LedgerEntry::id)
        .reversed(); // и время, и id по убыванию — выбранное правило разрешения равенства

List<LedgerEntry> page = entries.stream()
        .filter(e -> e.accountId().equals(accountId))
        .sorted(newestFirst)
        .skip((long) pageNumber * pageSize)
        .limit(pageSize)
        .toList();
```

Предполагаются `pageNumber >= 0` и `1 <= pageSize <= 100`, проверенные до цепочки. Для будущего SQL-запроса следует
сохранить те же направления сортировки.

`sorted().limit(10)` выбирает первые десять после сортировки всего набора, а `limit(10).sorted()` сортирует только
первые десять исходных элементов. Это разные задачи. Фильтр перед сортировкой сокращает объём сортируемых данных, если
такое перемещение сохраняет смысл запроса.

`filter` и `map` обычно требуют линейного прохода без накопления всей последовательности.
`sorted` для произвольного конечного набора обычно требует `O(n log n)` времени и буферизации,
`distinct` — хранения информации об уже встреченных значениях, а итоговый список — памяти под результат. Ленивость не
гарантирует постоянный расход памяти или ускорение по сравнению с циклом.

`distinct()` сравнивает элементы целиком через `equals`: две разные ledger entries одного счёта останутся двумя. Для
уникальных счетов сначала сделай `map(LedgerEntry::accountId)`. У `BigDecimal` различие масштаба влияет на `equals`,
поэтому `1.0` и `1.00` не схлопнутся при обычном `distinct()`.

## 8. Побочные эффекты: почему результат важнее количества вызовов

Требования к лямбдам внутри цепочки: не менять источник и не зависеть от изменяющегося состояния обхода. Определение
чистой функции уже было в теме лямбд; здесь важны последствия для выполнения Stream API.

### Не собирай результат через внешнюю коллекцию

```java
// Плохая форма: скрытое накопление во внешнем объекте.
List<UUID> ids = new ArrayList<>();
entries.

stream().

forEach(e ->ids.

add(e.id()));

// Результат выражен прямо.
List<UUID> result = entries.stream().map(LedgerEntry::id).toList();
```

Первый вариант работает последовательно, но усложняет контракт и станет небезопасным при параллельном добавлении в
`ArrayList`. Изменение отдельного внутреннего контейнера в `collect` предусмотрено механизмом накопления:
обычный коллектор может создать независимые контейнеры для частей данных и затем объединить их. Изменять один общий
список из лямбды — другое поведение.

Не используй изменяемый список как начальное значение `reduce` с `add`: для такого накопления есть `collect`.

### `peek` не подходит для обязательного аудита

```java
long count = Stream.of("a", "b", "c")
        .peek(System.out::println)
        .count();
```

Реализация может получить размер источника без обхода и не вызвать `peek` вообще. Оптимизации могут пропускать и другие
промежуточные шаги, если результат от них не зависит. Поэтому запись аудита, изменение баланса или обязательная проверка
внутри `peek` ненадёжны.
`peek` полезен как вспомогательное средство наблюдения с учётом этих ограничений.

`forEach` предназначен для действий, но не делает их атомарными. Если третье действие завершилось исключением, первые
два уже могли выполниться. Переход на цикл также не создаёт откат — его обеспечивает отдельный механизм транзакции.

### `null` и исключения

`map` не удаляет `null` автоматически. Последующий вызов метода может бросить `NullPointerException`, а `findFirst` не
может вернуть `Optional` с найденным `null`. Фильтрация `Objects::nonNull` допустима, если пропуск отсутствующих
значений предусмотрен контрактом; для повреждённой денежной записи молчаливое удаление обычно скрывает проблему данных.

Исключение из лямбды прерывает обработку. Stream API не является механизмом повторных попыток или сбора всех ошибок. Для
обработки каждой строки с отдельной диагностикой часто удобнее цикл; ограничения checked-исключений описаны в предыдущей
теме.

## 9. Границы применения в backend

### Запросы к базе данных

Цепочка `repository.findAll().stream().filter(...).limit(100)` не превращается автоматически в SQL с фильтром и лимитом.
Если `findAll` вернул все записи, они уже загружены. При большой истории фильтрацию, сортировку, пагинацию и подходящие
агрегаты следует выражать запросом к БД. В Java удобно преобразовать полученную страницу в DTO.

Вызов репозитория внутри `map` для каждой записи может породить множество отдельных запросов. Скрытая загрузка связанных
объектов ORM тоже может дать такой эффект. Stream API его не устраняет; это отдельная тема разделов о БД и Hibernate.

### Ресурсы нужно закрывать

Поток из коллекции обычно не требует закрытия. Поток строк файла держит ресурс:

```java
// Внутри метода, объявляющего throws IOException.
try(Stream<String> lines = java.nio.file.Files.lines(path)){
long nonBlank = lines.filter(line -> !line.isBlank()).count();
}
```

`path` здесь — `java.nio.file.Path`. Терминальная операция не заменяет `close()`; блок `try` закрывает поток и при
исключении. Подробно `try-with-resources` будет в неделе 4. Для потока, возвращённого репозиторием, проверь его
контракт: он может удерживать курсор и соединение с БД.

### `parallelStream()` — отдельное инженерное решение

Параллельный поток разбивает вычисление на части. Накладные расходы на разбиение и объединение могут превысить выигрыш.
Он уместен как кандидат для большого объёма независимых вычислений на процессоре, если ускорение подтверждено измерением
на характерных данных.

Для переводов и HTTP/SQL-вызовов это плохой способ просто «сделать быстрее»:

- несколько действий могут выполниться одновременно и в другом порядке;
- общие изменяемые объекты требуют отдельной защиты;
- контекст, привязанный к потоку исполнения, нельзя считать автоматически перенесённым;
- стандартное выполнение в JDK обычно использует общий `ForkJoinPool`, где блокирующие вызовы конкурируют за работников;
- вызов остаётся синхронным для вызывающего кода: результат терминальной операции нужно дождаться.

`forEach` не гарантирует порядок параллельных действий. `forEachOrdered` сохраняет порядок источника, если он определён,
но не создаёт транзакцию и может ограничить выигрыш от параллельности. При этом параллельный `toList()` сохраняет
порядок упорядоченного источника: параллельность не означает обязательное перемешивание результата.

### Когда выбирать цикл

| Задача                                                   | Подходящий исходный выбор                      |
|----------------------------------------------------------|------------------------------------------------|
| Отобрать записи и получить DTO                           | последовательный Stream API                    |
| Сгруппировать уже загруженные записи                     | `groupingBy` или понятный цикл                 |
| Найти один элемент или проверить наличие                 | `findFirst` / `anyMatch`                       |
| Проверять шаги и выполнять перевод                       | именованные методы с явной последовательностью |
| Нужны предыдущий элемент, несколько выходов, диагностика | цикл                                           |
| Получить страницу из миллионов записей                   | запрос к БД                                    |
| Обработать каждую ошибку отдельно и продолжить           | обычно цикл                                    |

Сравни один расчёт в двух формах:

```java
BigDecimal byStream = entries.stream()
```

добавляются зависимость от предыдущего баланса, номер ошибочной записи и несколько ветвей, цикл обычно растёт понятнее.
Не обходи это ограничение через внешние счётчики и массивы из одного элемента.

### Задание 3. Проверка пар перевода

Реализуй `TransferPairValidator` из пакета
`com.example.exercises.week_3.streamApi.task_3`. Метод
`validate(List<LedgerEntry> entries)` получает уже загруженные записи ledger и возвращает
`Map<UUID, Set<TransferPairViolation>>`: ключ — `operationId` подозрительной операции, значение — все обнаруженные
нарушения. Для корректного перевода запись в результате отсутствует.

В анализ включай только записи типов `TRANSFER_IN` и `TRANSFER_OUT`. Записи `DEPOSIT` и
`WITHDRAWAL` игнорируй: даже если у них совпадает `operationId`, они не являются частями перевода. Сначала сгруппируй
выбранные записи по `operationId`, затем проверь каждую группу независимо.

Корректная группа перевода обязана удовлетворять всем условиям:

| Проверка             | Условие корректности                                                                  | Нарушение при несоблюдении                       |
|----------------------|---------------------------------------------------------------------------------------|--------------------------------------------------|
| Количество записей   | В группе ровно две записи                                                             | `WRONG_ENTRY_COUNT`                              |
| Направления          | Ровно одна `TRANSFER_OUT` и ровно одна `TRANSFER_IN`                                  | `MISSING_TRANSFER_OUT` или `MISSING_TRANSFER_IN` |
| Счета                | `accountId` исходящей и входящей записей различаются                                  | `SAME_ACCOUNT`                                   |
| Знак исходящей суммы | У `TRANSFER_OUT` значение `amount` строго меньше нуля                                 | `INVALID_TRANSFER_OUT_AMOUNT_SIGN`               |
| Знак входящей суммы  | У `TRANSFER_IN` значение `amount` строго больше нуля                                  | `INVALID_TRANSFER_IN_AMOUNT_SIGN`                |
| Сумма изменений      | Сумма всех `amount` в группе равна нулю; сравнивай через `compareTo(BigDecimal.ZERO)` | `AMOUNTS_DO_NOT_BALANCE`                         |

Проверки независимы: для одной операции верни **все** применимые нарушения, а не только первое. Например, две исходящие
записи должны получить как минимум `WRONG_ENTRY_COUNT` и
`MISSING_TRANSFER_IN`. Не пытайся проверить разные счета, если в группе нельзя однозначно выбрать одну исходящую и одну
входящую запись; в таком случае это нарушение не добавляй.

Используй `EnumSet<TransferPairViolation>` для накопления причин, а в результате можешь вернуть неизменяемое множество.
Порядок операций в возвращаемом `Map` не важен. Метод не должен изменять входной список и сами записи. Для пустого
списка верни пустой `Map`; `null` для списка или элемента списка не допускай и отклоняй через `Objects.requireNonNull`.

Создай отдельные проверочные наборы и убедись, что:

1. корректная пара T1 (`TRANSFER_OUT -250.00` для A и `TRANSFER_IN 250.00` для B) не попадает в результат;
2. потерянная входящая запись даёт `WRONG_ENTRY_COUNT` и `MISSING_TRANSFER_IN`;
3. две исходящие записи с одним `operationId` дают `WRONG_ENTRY_COUNT` и `MISSING_TRANSFER_IN`;
4. пара записей для одного счёта даёт `SAME_ACCOUNT`;
5. сумма `-250.00` и `200.00` даёт `AMOUNTS_DO_NOT_BALANCE`;
6. суммы `-250.00` и `250.000` считаются сбалансированными: у `BigDecimal` важна числовая величина, а не scale;
7. `DEPOSIT` и `WITHDRAWAL` не влияют на результат.

Одной проверки нулевой суммы недостаточно: четыре записи тоже могут дать ноль. Это проверка уже загруженных данных для
диагностики; она не заменяет атомарную запись перевода, транзакцию и ограничения хранилища.

### Задание 4. Крупные расходы

Реализуй `LargeExpenseFinder` из пакета
`com.example.exercises.week_3.streamApi.task_4`. Он получает уже загруженные записи ledger и выделяет крупные расходы.
Для упражнения порог фиксирован: `200.00` RUB. Методы, которые нужно реализовать:

```java
List<UUID> findIds(List<LedgerEntry> entries);

boolean hasAny(List<LedgerEntry> entries);
```

Запись считается крупным расходом, только если одновременно выполняются оба условия:

1. `amount` строго меньше нуля;
2. модуль `amount` больше или равен `200.00`.

То есть `-200.00` подходит, `-200.01` подходит, а `-199.99`, `0.00` и `250.00` — нет. Сравнивай денежные значения через
`compareTo`, а знак определяй через `signum`. Не используй `double`
и не сравнивай `BigDecimal` через `equals`: например, `new BigDecimal("-200.0")` и
`new BigDecimal("-200.00")` должны дать одинаковый результат.

`findIds` возвращает `id` всех подходящих **записей** в том же порядке, в котором они встретились во входном списке. Не
удаляй повторяющиеся идентификаторы дополнительно: контракт метода говорит о записях, а не о множестве идентификаторов.
На исходном наборе из задания 1 результат содержит единственный идентификатор исходящей записи T1 счёта A. Пустой
входной список даёт пустой список.

Тип `OperationType` не используй как критерий отбора. В ledger знак `amount` является источником истины для изменения
баланса; это позволяет обнаружить и странные загруженные данные, например отрицательную запись с типом `DEPOSIT`. В
реальном сервисе такую запись следовало бы отдельно валидировать, но в этом упражнении она всё равно считается расходом.

`hasAny` должен отвечать, есть ли хотя бы одна такая запись, не создавая промежуточный или итоговый список и не вызывая
`findIds`. Подбери терминальную операцию, которая может завершить обход сразу после первого подходящего элемента. Для
проверки удобно подготовить список, где крупный расход находится первым, и убедиться отладчиком, что остальные элементы
не обрабатываются.

Оба метода не должны изменять входной список и его элементы. `entries`, каждая запись и её обязательные поля не могут
быть `null`: на границе метода отклони `null` через `Objects.requireNonNull`. Возвращаемый из `findIds` список сделай
неизменяемым по структуре. Стартовые типы и пустой каркас класса находятся в
`src/com/example/exercises/week_3/streamApi/task_4`.

Это учебный фильтр для анализа, а не полноценное правило выявления мошенничества: здесь не учитываются валюта, частота
операций, получатель, баланс и история клиента.

## Итог

Stream API хорошо выражает преобразование данных: **выбрать → преобразовать → собрать или посчитать**. Читаемая цепочка
описывает результат и не зависит от скрытого изменяемого состояния. Для последовательности бизнес-действий, сложного
управления обходом и диагностики выбирай явные методы и циклы.
