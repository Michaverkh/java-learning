# Collections Framework в Java

[← Вернуться к учебному плану](../java-backend-learning-plan.md)

Collections Framework — это набор интерфейсов, реализаций и алгоритмов для хранения и обработки групп объектов. Главный
навык здесь — не запомнить все классы из `java.util`, а уметь выбрать структуру данных по требуемому поведению.

Например, история операций кошелька требует порядка и допускает несколько похожих элементов — подходит `List`. Быстрая
проверка уже обработанного ключа идемпотентности требует уникальности — подходит `Set`. Поиск счёта по идентификатору
требует соответствия «ключ → значение» — подходит `Map`. Очередь событий для последовательной обработки требует
добавления в конец и извлечения из начала — подходит `Queue` или `Deque`.

## Что уже разобрано

В этом разделе не повторяются:

- generics, инвариантность, wildcards и PECS — они разобраны в
  [«Проектировании типов в Java»](../week-02/type-design-nullability-and-generics.md#8-инвариантность-и-wildcards);
- полный контракт `equals/hashCode` — он разобран в
  [«Объектно-ориентированном программировании»](../week-02/object-oriented-programming.md#13-идентичность--equals-и-hashcode);
- различие между `final`-ссылкой и неизменяемым объектом — оно разобрано в
  [разделе про mutable и immutable objects](../week-02/object-oriented-programming.md#14-mutable-и-immutable-objects).

Здесь важно понять, как эти правила влияют именно на коллекции.

## Что нужно понять

После изучения темы ты должен уметь:

1. выбирать между `List`, `Set`, `Map`, `Queue` и `Deque` по требуемому поведению;
2. объявлять переменную через интерфейс, а реализацию выбирать отдельно;
3. объяснять основные свойства и стоимость операций `ArrayList`, `HashMap`, `HashSet` и `ArrayDeque`;
4. понимать, почему корректные и стабильные `equals/hashCode` необходимы для hash-based коллекций;
5. отличать изменяемую, неизменяемую и недоступную для изменения через конкретную ссылку коллекцию;
6. использовать `Comparable` для естественного порядка и `Comparator` для порядка конкретной операции;
7. не полагаться на порядок обхода там, где контракт коллекции его не гарантирует;
8. выбирать коллекции для типичных задач Java backend и Wallet Service.

## 1. Карта Collections Framework

Упрощённая схема основных интерфейсов:

```text
Iterable<E>
└── Collection<E>
    ├── List<E>
    ├── Set<E>
    └── Queue<E>
        └── Deque<E>

Map<K, V> — отдельная ветка, не наследует Collection
```

`Collection<E>` описывает группу отдельных элементов. `Map<K, V>` описывает пары ключей и значений, поэтому не является
подтипом `Collection`.

В именах generic-параметров обычно используются:

- `E` — element;
- `K` — key;
- `V` — value.

### Интерфейс задаёт требуемое поведение

Обычно поле, параметр и возвращаемое значение объявляются через наиболее подходящий интерфейс:

```java
List<LedgerEntry> entries = new ArrayList<>();
Set<String> processedKeys = new HashSet<>();
Map<AccountId, Account> accountsById = new HashMap<>();
Deque<OutboxEvent> events = new ArrayDeque<>();
```

Левая часть фиксирует контракт, который нужен клиентскому коду. Правая часть выбирает конкретные характеристики хранения.

Это позволяет заменить реализацию без изменения пользователей коллекции:

```java
Map<AccountId, Account> accountsById = new LinkedHashMap<>();
```

Код, использующий только операции `Map`, продолжит компилироваться. При этом появится гарантированный порядок обхода по
порядку добавления элементов.

### Не выбирай самый общий интерфейс автоматически

`Collection<E>` подходит, только если клиенту действительно не нужны особенности более точного контракта. Если метод
обещает упорядоченный результат с доступом по индексу, возвращай `List<E>`. Если обещает уникальность — `Set<E>`.

```java
public List<LedgerEntry> history(AccountId accountId) {
    // Порядок истории является частью контракта.
}
```

Слишком общий тип скрывает полезные гарантии. Слишком конкретный тип, например `ArrayList`, без необходимости связывает
клиентский код с деталями реализации.

## 2. `List`: последовательность с индексами и повторениями

`List<E>` хранит элементы в определённом порядке:

- каждому элементу соответствует индекс от `0` до `size() - 1`;
- одинаковые элементы могут встречаться несколько раз;
- порядок обхода совпадает с порядком элементов списка;
- большинство реализаций допускает `null`, но использование `null` как элемента часто усложняет контракт приложения.

```java
List<String> operationTypes = new ArrayList<>();
operationTypes.add("DEPOSIT");
operationTypes.add("WITHDRAWAL");
operationTypes.add("DEPOSIT");

System.out.println(operationTypes.get(0)); // DEPOSIT
System.out.println(operationTypes.size()); // 3
```

Повторный `DEPOSIT` сохраняется: `List` не обеспечивает уникальность.

### Основные операции

```java
List<AccountId> accountIds = new ArrayList<>();

accountIds.add(primaryId);
accountIds.add(secondaryId);
accountIds.add(1, reserveId);

AccountId first = accountIds.get(0);
accountIds.set(0, replacementId);
accountIds.remove(reserveId);

boolean contains = accountIds.contains(primaryId);
int count = accountIds.size();
```

Разберём стоимость каждой строки для `ArrayList`. Здесь `n` — количество элементов в списке непосредственно перед
операцией. Предполагается, что `AccountId.equals` работает за `O(1)`, например сравнивает фиксированное количество полей.

```java
List<AccountId> accountIds = new ArrayList<>();
```

Создание пустого `ArrayList` занимает `O(1)`: создаётся сам объект списка, но `n` элементов не копируются. В актуальных
реализациях JDK внутренний массив для конструктора без аргументов может быть создан только при первом добавлении, однако
это деталь реализации, а не часть контракта `List`.

```java
accountIds.add(primaryId);
accountIds.add(secondaryId);
```

Каждый `add(value)` добавляет элемент в конец:

- обычно — `O(1)`, потому что ссылка записывается в следующую свободную ячейку внутреннего массива;
- в отдельном случае — `O(n)`, если ёмкости не хватило: создаётся больший массив и существующие ссылки копируются;
- для длинной последовательности добавлений — амортизированное `O(1)` на одну операцию.

Амортизированная оценка не утверждает, что каждое отдельное добавление имеет `O(1)`. Она означает, что редкие дорогие
расширения распределяются по большому количеству дешёвых добавлений.

```java
accountIds.add(1, reserveId);
```

Вставка по индексу имеет `O(n)`: элементы начиная с индекса `1` сдвигаются на одну позицию вправо. В общем случае число
сдвигов равно `n - index`. Если одновременно нужно расширить внутренний массив, копирование также занимает `O(n)` и не
меняет итоговую оценку.

Для конкретного маленького списка с двумя элементами будет сдвинут только один элемент. Но Big O описывает рост затрат
при увеличении входа, поэтому вставка в фиксированную позицию `1` остаётся `O(n)`.

```java
AccountId first = accountIds.get(0);
```

Чтение по индексу занимает `O(1)`: `ArrayList` вычисляет адрес нужной ячейки внутреннего массива и получает ссылку на
объект. Проходить предыдущие элементы не требуется.

```java
accountIds.set(0, replacementId);
```

Замена по индексу также занимает `O(1)`: ссылка в уже существующей ячейке заменяется новой. Размер списка не меняется,
элементы не сдвигаются. Метод возвращает прежний элемент, что также не меняет оценку.

```java
accountIds.remove(reserveId);
```

Здесь вызывается `remove(Object)`, то есть удаление первого равного значения, а не удаление по индексу. Операция состоит
из двух частей:

1. последовательный поиск `reserveId` через `equals` — до `O(n)`;
2. если элемент найден, сдвиг всех элементов после него влево — до `O(n)`.

Сумма `O(n) + O(n)` остаётся `O(n)`: Big O отбрасывает постоянный множитель. Если значение отсутствует, поиск просмотрит
весь список, но сдвига не будет — итог всё равно `O(n)`. Удаление по известному индексу пропустило бы поиск, однако сдвиг
по-прежнему давал бы `O(n)` в общем случае. Удаление последнего элемента по известному индексу — частный случай `O(1)`.

```java
boolean contains = accountIds.contains(primaryId);
```

Проверка наличия имеет `O(n)`: список последовательно вызывает `equals`, пока не найдёт равный элемент или не дойдёт до
конца. В лучшем случае первый элемент совпадёт и фактическая стоимость будет `O(1)`, но обычная оценка худшего случая —
`O(n)`.

```java
int count = accountIds.size();
```

Получение размера занимает `O(1)`: `ArrayList` хранит размер в отдельном поле и не пересчитывает элементы при каждом
вызове.

Итог для примера:

| Выражение                                | Оценка                          | Что определяет стоимость                         |
|------------------------------------------|---------------------------------|--------------------------------------------------|
| `new ArrayList<>()`                      | `O(1)`                          | создание пустого объекта списка                  |
| `add(value)`                             | амортизированно `O(1)`          | иногда расширение массива занимает `O(n)`        |
| `add(index, value)`                      | `O(n)`                          | сдвиг элементов справа от индекса                |
| `get(index)`                             | `O(1)`                          | прямой доступ к ячейке массива                   |
| `set(index, value)`                      | `O(1)`                          | замена ссылки без сдвига                         |
| `remove(value)`                          | `O(n)`                          | линейный поиск и возможный сдвиг                 |
| `contains(value)`                        | `O(n)`                          | линейный поиск через `equals`                    |
| `size()`                                 | `O(1)`                          | чтение сохранённого значения размера             |

У `remove` есть перегрузки:

```java
List<Integer> numbers = new ArrayList<>(List.of(10, 20, 30));

numbers.remove(1);                  // удаляет элемент по индексу 1: число 20
numbers.remove(Integer.valueOf(1)); // пытается удалить значение 1
```

Для `List<Integer>` это частый источник ошибок: primitive `int` выбирает перегрузку `remove(int index)`.

### `ArrayList`: основной список общего назначения

`ArrayList<E>` хранит ссылки на элементы во внутреннем массиве. Когда места не хватает, создаётся массив большего размера,
а элементы копируются. Точный коэффициент роста является деталью реализации JDK и не должен использоваться как часть
логики приложения.

Основные характеристики:

| Операция                              | Типичная стоимость | Причина                                                        |
|---------------------------------------|--------------------|----------------------------------------------------------------|
| `get(index)`, `set(index, value)`     | `O(1)`             | прямой доступ к ячейке внутреннего массива                     |
| `add(value)` в конец                  | амортизированно `O(1)` | иногда требуется расширить и скопировать массив              |
| `add(index, value)`                   | `O(n)`             | последующие элементы нужно сдвинуть                            |
| `remove(index)`                       | `O(n)`             | последующие элементы нужно сдвинуть                            |
| `contains(value)`, `indexOf(value)`   | `O(n)`             | требуется последовательный поиск через `equals`                |
| обход всех элементов                 | `O(n)`             | каждый элемент посещается один раз                             |

Амортизированное `O(1)` означает: отдельное добавление иногда дорогое из-за расширения массива, но средняя стоимость
длинной последовательности добавлений остаётся постоянной.

Если примерный размер известен заранее, можно передать начальную ёмкость:

```java
List<LedgerEntry> entries = new ArrayList<>(expectedEntryCount);
```

Это может уменьшить число расширений, но не меняет логический размер списка: сразу после конструктора `size()` равен `0`.
Не стоит угадывать capacity повсеместно — такая оптимизация полезна только при понятном размере или после измерений.

### Почему `LinkedList` редко является вариантом по умолчанию

`LinkedList<E>` реализует и `List`, и `Deque`, но доступ по индексу требует прохода по узлам и стоит `O(n)`. Каждый элемент
также требует отдельного узла со ссылками, что увеличивает расход памяти и ухудшает локальность данных.

Теоретическое `O(1)` для вставки рядом с уже найденным узлом редко помогает обычному backend-коду: сначала нужную позицию
обычно приходится искать. Для списка общего назначения выбирай `ArrayList`, а для очереди с операциями на концах —
`ArrayDeque`.

### Представление части списка

`subList(from, to)` обычно возвращает представление диапазона исходного списка, а не независимую копию:

```java
List<String> all = new ArrayList<>(List.of("a", "b", "c", "d"));
List<String> page = all.subList(1, 3);

page.set(0, "B");
System.out.println(all); // [a, B, c, d]
```

Изменения видны через обе ссылки. Если нужен независимый снимок, создай копию:

```java
List<String> snapshot = List.copyOf(all.subList(1, 3));
```

## 3. `Set`: множество уникальных элементов

`Set<E>` не допускает двух элементов, равных с точки зрения `equals`:

```java
Set<String> roles = new HashSet<>();

roles.add("CUSTOMER"); // true
roles.add("OPERATOR"); // true
roles.add("CUSTOMER"); // false: равный элемент уже существует
```

Возвращаемое значение `add` сообщает, изменилось ли множество. Это часто удобнее, чем отдельная проверка через `contains`.

### Когда нужен `Set`

Используй `Set`, если уникальность является частью смысла данных:

- набор разрешений пользователя;
- идентификаторы затронутых счетов;
- уже обработанные ключи или события;
- исключённые категории операций.

Не используй `Set` только ради ускорения `contains`, если порядок и повторения имеют бизнес-смысл. Сначала определяется
контракт данных, затем выбирается реализация.

### `HashSet`

`HashSet<E>` использует hash-based хранение и обычно обеспечивает:

| Операция                     | Ожидаемая стоимость |
|------------------------------|---------------------|
| `add`, `contains`, `remove`  | `O(1)`              |
| обход всех элементов        | `O(n + capacity)`   |

`O(1)` здесь ожидаемое, а не безусловное худшее время. Оно зависит от распределения hash-кодов и внутренних конфликтов.
Обход зависит не только от числа элементов `n`, но и от ёмкости внутренней hash-таблицы. Точная обработка конфликтов
является деталью реализации JDK.

`HashSet` не гарантирует порядок обхода. Наблюдаемый сегодня порядок может измениться после добавления элемента, изменения
размера таблицы или обновления JDK:

```java
Set<String> statuses = new HashSet<>();
statuses.add("ACTIVE");
statuses.add("BLOCKED");
statuses.add("CLOSED");

// Нельзя считать порядок вывода частью контракта.
System.out.println(statuses);
```

Если порядок важен, выбери другую реализацию:

- `LinkedHashSet` — порядок добавления;
- `TreeSet` — порядок, определяемый сравнением элементов;
- `EnumSet` — эффективное множество значений одного `enum`.

### `EnumSet`

Для набора enum-значений предпочитай `EnumSet` обычному `HashSet`:

```java
EnumSet<AccountStatus> usableStatuses =
        EnumSet.of(AccountStatus.ACTIVE, AccountStatus.BLOCKED);
```

`EnumSet` компактен и специально оптимизирован под закрытый набор значений одного enum-типа. Он не допускает `null`.

## 4. `Map`: соответствие ключей и значений

`Map<K, V>` хранит пары «ключ → значение»:

- ключ уникален;
- разные ключи могут ссылаться на равные значения;
- повторный `put` для равного ключа заменяет прежнее значение;
- `Map` не является `Collection`.

```java
Map<AccountId, Account> accounts = new HashMap<>();

accounts.put(primary.id(), primary);
accounts.put(reserve.id(), reserve);

Account account = accounts.get(primary.id());
```

### Основные операции

```java
boolean exists = accounts.containsKey(accountId);
Account found = accounts.get(accountId);
Account removed = accounts.remove(accountId);
int count = accounts.size();
```

`get` возвращает `null` и при отсутствии ключа, и когда ключ явно связан с `null`. Поэтому для backend-кода часто проще не
хранить `null`-значения вообще и определить однозначный контракт.

Если различие всё же важно, используется `containsKey`:

```java
if (accounts.containsKey(accountId)) {
    Account value = accounts.get(accountId); // value всё ещё может быть null
}
```

### `putIfAbsent`, `computeIfAbsent` и `merge`

`Map` умеет выразить распространённые составные операции без ручного ветвления.

Добавить значение, только если ключ отсутствует:

```java
accounts.putIfAbsent(account.id(), account);
```

Создать список при первом обращении к ключу:

```java
Map<AccountId, List<LedgerEntry>> entriesByAccount = new HashMap<>();

entriesByAccount
        .computeIfAbsent(entry.accountId(), ignored -> new ArrayList<>())
        .add(entry);
```

Увеличить счётчик:

```java
Map<OperationType, Integer> counts = new HashMap<>();

counts.merge(entry.operationType(), 1, Integer::sum);
```

Эти методы делают намерение яснее. Но для обычного `HashMap` они сами по себе не превращают многошаговую бизнес-операцию в
потокобезопасную — конкурентные коллекции рассматриваются в неделе 14.

### Обход `Map`

Если нужны и ключ, и значение, обходи `entrySet`:

```java
for (Map.Entry<AccountId, Account> entry : accounts.entrySet()) {
    AccountId id = entry.getKey();
    Account value = entry.getValue();
}
```

Обход ключей с последующим `get` обычно делает лишний поиск:

```java
for (AccountId id : accounts.keySet()) {
    Account value = accounts.get(id);
}
```

Остальные представления:

- `keySet()` — множество ключей;
- `values()` — коллекция значений, в которой возможны повторения;
- `entrySet()` — множество пар `Map.Entry<K, V>`.

Это связанные с `Map` представления, а не независимые копии. Удаление через поддерживаемую операцию представления может
изменить исходную `Map`.

### `HashMap`

`HashMap<K, V>` — основная реализация словаря общего назначения. Она использует `hashCode` для выбора области поиска, а
`equals` — для нахождения нужного ключа среди возможных конфликтов.

Ожидаемая стоимость основных операций:

| Операция                                | Ожидаемая стоимость |
|-----------------------------------------|---------------------|
| `get`, `put`, `containsKey`, `remove`   | `O(1)`              |
| обход всех пар                          | `O(n + capacity)`   |

`HashMap`:

- допускает один `null`-ключ и `null`-значения, но прикладному коду не обязательно пользоваться этой возможностью;
- не гарантирует порядок обхода;
- не является потокобезопасной;
- зависит от корректности `equals/hashCode` ключей.

### Другие полезные реализации `Map`

| Реализация       | Когда нужна                                                        |
|------------------|---------------------------------------------------------------------|
| `HashMap`        | быстрый поиск без требований к порядку                              |
| `LinkedHashMap`  | нужен предсказуемый порядок добавления                              |
| `TreeMap`        | ключи должны обходиться в отсортированном порядке                   |
| `EnumMap`        | все ключи принадлежат одному enum-типу                              |

Если API обещает стабильную сортировку операций по `createdAt` и `id`, не следует случайно полагаться на порядок
`HashMap`. Сортировка должна быть выражена явно через `Comparator`, а нужный результат обычно возвращается как `List`.

## 5. Как работают `HashMap` и `HashSet`

Упрощённый поиск значения в `HashMap` выглядит так:

1. у ключа вызывается `hashCode`;
2. hash преобразуется в индекс внутренней таблицы;
3. среди записей в соответствующей области ищется равный ключ через `equals`;
4. при совпадении возвращается связанное значение.

`HashSet` концептуально использует тот же механизм: хранимый элемент играет роль ключа. Поэтому правила ключей `HashMap`
одновременно являются правилами элементов `HashSet`.

### Равные объекты обязаны иметь одинаковый hash-код

```java
AccountId first = new AccountId(uuid);
AccountId second = new AccountId(uuid);

Map<AccountId, Account> accounts = new HashMap<>();
accounts.put(first, account);

System.out.println(accounts.get(second));
```

Поиск должен найти значение, если `first.equals(second)`. Для этого их `hashCode` тоже обязаны совпадать. Полный контракт
разобран в материале недели 2; здесь важно следствие: нарушение контракта ломает семантику `HashMap` и `HashSet`.

### Ключ нельзя изменять так, чтобы менялись `equals/hashCode`

Опасный пример:

```java
final class MutableAccountKey {
    private String value;

    // equals/hashCode зависят от value
    // value можно изменить
}
```

```java
MutableAccountKey key = new MutableAccountKey("A-1");
Map<MutableAccountKey, Account> accounts = new HashMap<>();

accounts.put(key, account);
key.setValue("A-2");

Account found = accounts.get(key); // результат больше не соответствует ожиданиям
```

Запись размещалась с прежним hash-кодом. После изменения ключ направляет поиск в другое место. Поэтому ключами должны быть
объекты со стабильным равенством: строки, UUID, enum или корректно спроектированные immutable value objects вроде
`AccountId`.

### Хороший hash-код не означает уникальный hash-код

Разные объекты могут иметь одинаковый `hashCode`. Это называется конфликтом hash-кодов и является нормальной ситуацией.
`HashMap` использует `equals`, чтобы различить такие ключи.

Нельзя считать hash-код уникальным идентификатором, сохранять его вместо исходного ключа или использовать как
криптографический отпечаток запроса.

## 6. `Queue` и `Deque`: обработка элементов по очереди

`Queue<E>` обычно моделирует порядок FIFO: first in, first out. Элемент добавляется в хвост и извлекается из головы.
Однако сам интерфейс не требует FIFO: например, `PriorityQueue` выдаёт элементы по их приоритету.

Для каждой основной операции есть две формы:

| Действие             | С исключением при невозможности | Со специальным результатом |
|----------------------|----------------------------------|----------------------------|
| добавить             | `add(e)`                         | `offer(e)`                 |
| извлечь и удалить    | `remove()`                       | `poll()`                   |
| посмотреть голову    | `element()`                      | `peek()`                   |

Для пустой очереди `remove()` и `element()` выбрасывают исключение, а `poll()` и `peek()` возвращают `null`.

```java
Queue<OutboxEvent> events = new ArrayDeque<>();

events.offer(event1);
events.offer(event2);

OutboxEvent next = events.poll();
OutboxEvent following = events.peek();
```

### `Deque`: операции с обоих концов

`Deque<E>` — double-ended queue. Она может работать как очередь и как стек:

```java
Deque<OutboxEvent> events = new ArrayDeque<>();

events.addLast(event1);
events.addLast(event2);
OutboxEvent next = events.removeFirst();
```

Как стек LIFO:

```java
Deque<Command> undoStack = new ArrayDeque<>();

undoStack.push(command);
Command latest = undoStack.pop();
```

Для нового кода `ArrayDeque` обычно предпочтительнее устаревшего `Stack`.

### `ArrayDeque`

`ArrayDeque<E>` использует циклический массив и эффективно работает с обоими концами:

| Операция                                      | Типичная стоимость |
|-----------------------------------------------|--------------------|
| `addFirst`, `addLast`, `offer`, `push`        | амортизированно `O(1)` |
| `removeFirst`, `removeLast`, `poll`, `pop`    | `O(1)`             |
| поиск произвольного значения                  | `O(n)`             |

`ArrayDeque` не допускает `null`, благодаря чему `poll()` может однозначно использовать `null` как признак пустой очереди.

Локальная `ArrayDeque` подходит для учебного моделирования очереди. Она не заменяет надёжный outbox и брокер сообщений:
содержимое памяти исчезнет при остановке процесса, а конкурентный доступ требует отдельных гарантий.

## 7. Изменяемые и неизменяемые коллекции

В этой теме важно различать три ситуации:

1. коллекцию можно изменять;
2. конкретная ссылка не позволяет изменять коллекцию, но изменения видны из другого места;
3. создан независимый неизменяемый снимок структуры.

### Изменяемая коллекция

```java
List<AccountId> ids = new ArrayList<>();
ids.add(accountId);
ids.remove(accountId);
```

`final` запрещает только переназначение переменной:

```java
final List<AccountId> ids = new ArrayList<>();
ids.add(accountId); // допустимо
```

### Фабричные методы `of`

```java
List<String> currencies = List.of("RUB");
Set<AccountStatus> terminalStatuses = Set.of(AccountStatus.CLOSED);
Map<String, Integer> limits = Map.of("pageSize", 100);
```

Коллекции, созданные через `List.of`, `Set.of` и `Map.of`:

- нельзя изменять структурными операциями;
- не допускают `null`;
- для `Set.of` элементы должны быть уникальны;
- для `Map.of` ключи должны быть уникальны;
- не становятся глубоко неизменяемыми, если их элементы сами изменяемы.

```java
List<Account> accounts = List.of(mutableAccount);
mutableAccount.deposit(amount); // сам Account всё ещё может измениться
```

### `copyOf`: неизменяемый снимок структуры

```java
List<LedgerEntry> internal = new ArrayList<>();
internal.add(entry);

List<LedgerEntry> snapshot = List.copyOf(internal);
internal.clear();

System.out.println(snapshot.size()); // 1
```

`List.copyOf`, `Set.copyOf` и `Map.copyOf` создают неизменяемый результат, не связанный с последующими структурными
изменениями исходной изменяемой коллекции. Копирование остаётся поверхностным: сами элементы не клонируются.

Эта техника подходит для защиты внутреннего состояния:

```java
public final class AccountHistory {
    private final List<LedgerEntry> entries;

    public AccountHistory(List<LedgerEntry> entries) {
        this.entries = List.copyOf(entries);
    }

    public List<LedgerEntry> entries() {
        return entries;
    }
}
```

Внешний код не может изменить структуру списка ни через исходный аргумент после конструктора, ни через результат метода.
Для полной неизменяемости `LedgerEntry` тоже должен быть неизменяемым.

### `Collections.unmodifiableList`: неизменяемое представление

```java
List<String> mutable = new ArrayList<>(List.of("a"));
List<String> view = Collections.unmodifiableList(mutable);

mutable.add("b");
System.out.println(view); // [a, b]
```

Через `view` нельзя вызвать `add`, но представление отражает изменения исходного списка. Это отличается от независимого
снимка через `List.copyOf`.

### `Arrays.asList`: список фиксированного размера

```java
String[] values = {"a", "b"};
List<String> list = Arrays.asList(values);

list.set(0, "A"); // допустимо и изменяет массив
// list.add("c");  // UnsupportedOperationException
```

Это не обычный изменяемый `ArrayList` и не неизменяемый список. Его размер связан с массивом и не может меняться.

### Не полагайся на `UnsupportedOperationException` как на проверку заранее

Интерфейс `List` не выражает на уровне типов, поддерживает ли конкретный объект `add`. Поэтому изменение коллекции,
полученной извне, требует понимания её контракта. Безопаснее явно создавать нужную форму:

```java
List<LedgerEntry> mutableCopy = new ArrayList<>(source);
List<LedgerEntry> immutableCopy = List.copyOf(source);
```

## 8. `Comparable` и `Comparator`

Сортировка требует ответа на вопрос: какой элемент должен идти раньше?

### `Comparable`: естественный порядок самого типа

Тип реализует `Comparable<T>`, если для него существует один очевидный и устойчивый естественный порядок:

```java
public record AccountId(UUID value) implements Comparable<AccountId> {
    @Override
    public int compareTo(AccountId other) {
        return value.compareTo(other.value);
    }
}
```

Теперь список идентификаторов можно сортировать без дополнительного правила:

```java
List<AccountId> ids = new ArrayList<>(sourceIds);
Collections.sort(ids);
```

или:

```java
ids.sort(Comparator.naturalOrder());
```

`compareTo` возвращает:

- отрицательное число, если текущий объект меньше другого;
- `0`, если они равны по порядку;
- положительное число, если текущий объект больше другого.

Не пиши сравнение целых чисел через вычитание:

```java
// Плохо: возможно переполнение int.
return left.priority() - right.priority();

// Хорошо.
return Integer.compare(left.priority(), right.priority());
```

### `Comparator`: порядок конкретной операции

У операции может быть несколько осмысленных порядков. Историю можно сортировать по времени, сумме или типу операции. Это
не повод встраивать все варианты в класс `LedgerEntry`.

```java
Comparator<LedgerEntry> newestFirst =
        Comparator.comparing(LedgerEntry::createdAt)
                .reversed()
                .thenComparing(LedgerEntry::id);
```

Применение:

```java
List<LedgerEntry> result = new ArrayList<>(entries);
result.sort(newestFirst);
```

`List.sort` изменяет исходный список. Если исходный порядок нужно сохранить, сначала создаётся копия.

### Стабильный порядок для пагинации

В требованиях Wallet Service операции сортируются от новых к старым по `createdAt`, а `id` используется как дополнительный
критерий. Он нужен, потому что несколько операций могут иметь одинаковое время:

```java
Comparator<LedgerEntry> historyOrder =
        Comparator.comparing(LedgerEntry::createdAt)
                .reversed()
                .thenComparing(LedgerEntry::id);
```

Без дополнительного критерия элементы с одинаковым временем не имеют полного стабильного порядка. Между запросами они
могут попасть на разные страницы.

### `null` в сортировке

Лучше не допускать `null` в доменных коллекциях. Если входные данные всё же содержат его, политика должна быть явной:

```java
Comparator<String> order = Comparator.nullsLast(String::compareToIgnoreCase);
```

### Согласованность порядка с `equals`

Для sorted collections желательно, чтобы `compare(a, b) == 0` соответствовало `a.equals(b)`. `TreeSet` и `TreeMap`
определяют уникальность через сравнение, а не через `equals`:

```java
Set<BigDecimal> amounts = new TreeSet<>();
amounts.add(new BigDecimal("10.0"));
amounts.add(new BigDecimal("10.00"));
```

`BigDecimal.compareTo` считает эти значения равными по числовой величине, хотя `BigDecimal.equals` учитывает scale. В
`TreeSet` останется один элемент. Это корректное, но важное исключение, которое нужно учитывать для денежных типов.

## 9. Обход коллекций и безопасное удаление

### Enhanced `for`

```java
for (LedgerEntry entry : entries) {
    validate(entry);
}
```

Такой цикл использует `Iterator` и подходит для обычного последовательного обхода.

### `Iterator`

Если элемент нужно удалить во время обхода изменяемой коллекции, используй метод самого iterator:

```java
Iterator<LedgerEntry> iterator = entries.iterator();

while (iterator.hasNext()) {
    LedgerEntry entry = iterator.next();
    if (isExpired(entry)) {
        iterator.remove();
    }
}
```

Изменение списка напрямую во время enhanced `for` обычно приводит к `ConcurrentModificationException`:

```java
for (LedgerEntry entry : entries) {
    if (isExpired(entry)) {
        entries.remove(entry); // ошибка проектирования обхода
    }
}
```

Проще выразить массовое удаление через:

```java
entries.removeIf(this::isExpired);
```

### Fail-fast не является механизмом потокобезопасности

Многие стандартные iterator обнаруживают структурное изменение коллекции и быстро выбрасывают
`ConcurrentModificationException`. Это диагностическое поведение по принципу best effort, а не гарантия обнаружения всех
гонок и не средство синхронизации.

Обычные `ArrayList`, `HashMap`, `HashSet` и `ArrayDeque` не являются потокобезопасными. Конкурентный доступ, concurrent
collections и синхронизация разбираются в неделе 14.

## 10. Как выбрать коллекцию

Начинай с требуемых гарантий, а не с привычного класса.

| Требование                                                    | Обычно выбирать             |
|---------------------------------------------------------------|-----------------------------|
| порядок элементов, повторы и доступ по индексу                | `ArrayList`                 |
| уникальность без требования к порядку                         | `HashSet`                   |
| уникальность с порядком добавления                            | `LinkedHashSet`             |
| уникальные enum-значения                                      | `EnumSet`                   |
| поиск значения по ключу без требования к порядку              | `HashMap`                   |
| поиск по ключу с порядком добавления                          | `LinkedHashMap`             |
| enum-ключи                                                    | `EnumMap`                   |
| отсортированные ключи или элементы                            | `TreeMap` / `TreeSet`       |
| FIFO-очередь или операции на обоих концах                     | `ArrayDeque`                |
| неизменяемый небольшой набор известных значений               | `List.of`, `Set.of`, `Map.of` |
| неизменяемый снимок входной коллекции                         | `List.copyOf` и аналоги     |

Дополнительные вопросы выбора:

1. Допустимы ли повторения?
2. Является ли порядок частью контракта?
3. Нужен ли доступ по индексу?
4. Ищем по значению или по отдельному ключу?
5. Будет ли коллекция изменяться после создания?
6. Кто владеет коллекцией и можно ли безопасно передавать её наружу?
7. Есть ли доказанная потребность в конкурентном доступе?

Не выбирай структуру только по асимптотике одной операции. Для небольших коллекций простота контракта обычно важнее
микрооптимизации. Производительность критичного пути подтверждается измерениями.

## 11. Сопоставление с TypeScript и JavaScript

Аналогии помогают начать, но контракты различаются.

| Java                                   | Приблизительная аналогия в TypeScript/JavaScript                              |
|----------------------------------------|--------------------------------------------------------------------------------|
| `List<E>` / `ArrayList<E>`             | обычный `E[]`, но Java `List` — интерфейс с несколькими реализациями           |
| `Set<E>` / `HashSet<E>`                | `Set<E>`                                                                        |
| `Map<K, V>` / `HashMap<K, V>`          | `Map<K, V>`                                                                     |
| `Queue<E>` / `ArrayDeque<E>`           | готового встроенного интерфейса очереди нет; часто используют массив или класс |
| `List.of(...)`                         | ближе к runtime-неизменяемой структуре, а не просто `readonly T[]`              |
| `Comparator<T>`                        | callback вида `(a, b) => number` для `sort`                                    |

### Равенство ключей отличается

Java `HashMap` и `HashSet` используют переопределяемые `equals/hashCode`. JavaScript `Map` и `Set` для объектов в основном
опираются на identity объекта. Два разных Java value objects могут быть одним ключом с точки зрения `HashMap`, если они
логически равны. Два отдельных, одинаково выглядящих объекта JavaScript остаются разными ключами.

### `readonly` и неизменяемая коллекция — не одно и то же

TypeScript `readonly T[]` в первую очередь ограничивает операции на этапе проверки типов. После компиляции это обычный
JavaScript-массив. `List.of` создаёт объект, который отклоняет структурные изменения во время выполнения Java-программы.

В обоих случаях элементы могут оставаться изменяемыми: ни `readonly T[]`, ни `List<T>` сами по себе не дают deep
immutability.

### Java arrays и `List` — разные типы

Java-массив `Account[]` имеет фиксированную длину и специальный синтаксис. `List<Account>` — объект Collections Framework
с операциями добавления и удаления, если реализация их поддерживает. В TypeScript обычный массив одновременно выполняет
обе роли, поэтому это различие требует отдельного внимания.

## 12. Collections Framework в типичном Java backend

Коллекции часто появляются на границах слоёв:

- repository возвращает список найденных сущностей или страницу результатов;
- application service группирует данные по идентификатору;
- domain object защищает внутреннее состояние через `copyOf`;
- DTO содержит упорядоченный список элементов;
- конфигурация хранит отображение кодов в настройки;
- обработчик событий отслеживает множество идентификаторов.

Несколько практических правил:

1. Не возвращай `null` вместо коллекции. Возвращай пустую коллекцию, если отсутствие элементов является нормальным
   результатом.
2. Не раскрывай изменяемую внутреннюю коллекцию доменного объекта.
3. Не обещай порядок, которого не гарантирует выбранная реализация.
4. Не используй JPA lazy collection за пределами понятной transaction boundary без осознания последствий — эта тема будет
   разобрана вместе с JPA.
5. Не загружай в память неограниченную историю операций: на уровне БД и API нужна пагинация.
6. Не используй in-memory `Map` как замену ограничениям уникальности и транзакциям БД в финальном сервисе.

### In-memory repository как учебный этап

До подключения базы данных repository можно реализовать через `HashMap`:

```java
public final class InMemoryAccountRepository implements AccountRepository {
    private final Map<AccountId, Account> accounts = new HashMap<>();

    @Override
    public Optional<Account> findById(AccountId id) {
        return Optional.ofNullable(accounts.get(id));
    }

    @Override
    public void save(Account account) {
        accounts.put(account.id(), account);
    }

    @Override
    public List<Account> findAllByClientId(ClientId clientId) {
        List<Account> result = new ArrayList<>();

        for (Account account : accounts.values()) {
            if (account.clientId().equals(clientId)) {
                result.add(account);
            }
        }

        return List.copyOf(result);
    }
}
```

Такая реализация помогает изучить интерфейсы и коллекции, но имеет ограничения:

- данные исчезают после перезапуска;
- полный проход по `values()` имеет `O(n)`;
- возвращаемые mutable `Account` могут раскрывать состояние repository;
- обычный `HashMap` не решает конкурентный доступ;
- нет транзакций и ограничений базы данных.

Это сознательный учебный этап, а не production persistence.

## 13. Частые ошибки

### Ошибка 1. Везде объявлять конкретную реализацию

```java
public ArrayList<Account> findAccounts() { ... }
```

Если клиенту не нужны специфические методы `ArrayList`, контракт должен возвращать `List<Account>`.

### Ошибка 2. Полагаться на порядок `HashMap` или `HashSet`

Наблюдаемый порядок не является гарантией. Выражай требование через подходящую реализацию или явную сортировку.

### Ошибка 3. Использовать изменяемый ключ `HashMap`

Если поля ключа, участвующие в `equals/hashCode`, изменились после `put`, запись может стать практически недоступной для
нормального поиска.

### Ошибка 4. Считать `final List<T>` неизменяемым списком

`final` запрещает переназначить ссылку, но `add` и `remove` остаются возможными для mutable implementation.

### Ошибка 5. Считать `unmodifiableList` независимой копией

Это представление исходного списка. Изменения через исходную ссылку остаются видны.

### Ошибка 6. Возвращать внутренний `ArrayList`

Клиент сможет нарушить инварианты объекта. Возвращай `List.copyOf` или храни заранее созданный immutable snapshot.

### Ошибка 7. Возвращать `null` вместо пустой коллекции

Клиенту приходится добавлять лишнее ветвление. Нормальный результат «ничего не найдено» обычно выражается через
`List.of()` или другую пустую коллекцию.

### Ошибка 8. Использовать `List` для постоянного поиска по идентификатору

Последовательный `contains` или поиск имеет `O(n)`. Если задача концептуально является индексом «id → объект», используй
`Map`.

### Ошибка 9. Использовать `Map<K, Boolean>` вместо `Set<K>`

Если значения не несут информации, контракт задачи — множество ключей.

### Ошибка 10. Изменять коллекцию напрямую во время enhanced `for`

Для удаления используй `Iterator.remove`, `removeIf` или создай новую коллекцию с нужными элементами.

### Ошибка 11. Путать capacity и size у `ArrayList`

Начальная ёмкость резервирует внутреннее место, но не создаёт элементы и не увеличивает `size()`.

### Ошибка 12. Выбирать `LinkedList` по правилу «вставка всегда `O(1)`»

Эта оценка относится к вставке рядом с уже известным узлом. Поиск позиции и доступ по индексу остаются линейными.

### Ошибка 13. Хранить `null` без явного контракта

`null` усложняет `get`, `peek`, проверки и фабричные методы immutable collections. В доменной модели обычно лучше выразить
отсутствие иначе.

### Ошибка 14. Использовать `HashMap` для конкурентного кэша

Обычные коллекции не становятся потокобезопасными от того, что лежат в Spring singleton bean. Эта задача относится к Java
concurrency и требует отдельного проектирования.

## 14. Практика для Wallet Service

Задания выполняются на доменной модели без Spring и базы данных. Цель — освоить контракты коллекций, а не заранее решить
задачи persistence и concurrency.

### Задание 1. In-memory repository счетов

Реализуй `InMemoryAccountRepository` на основе `Map<AccountId, Account>`.

Требования:

- `save` добавляет новый счёт или заменяет значение для того же `AccountId`;
- `findById` возвращает `Optional<Account>`;
- `findAllByClientId` возвращает `List<Account>`, а не `null`;
- вызывающий код не может изменить структуру внутренней коллекции repository;
- порядок результата определён явно, например по `AccountId`.

Объясни, почему ключом должен быть immutable `AccountId`, а не изменяемый `Account`.

### Задание 2. Индекс счетов клиента

Добавь индекс:

```java
Map<ClientId, Set<AccountId>> accountIdsByClient
```

Используй `computeIfAbsent` при создании первого счёта клиента. Проверь:

- повторное сохранение того же счёта не дублирует идентификатор;
- наружу не возвращается изменяемый внутренний `Set`;
- пустой результат представлен пустым множеством.

Сравни стоимость поиска счетов клиента с полным проходом по `accounts.values()`.

### Задание 3. История ledger

Реализуй хранилище:

```java
Map<AccountId, List<LedgerEntry>> entriesByAccount
```

Требования:

- новая запись добавляется через `computeIfAbsent`;
- порядок выдачи: `createdAt` по убыванию, затем `id` по возрастанию;
- сортировка результата не меняет внутренний порядок хранения;
- возвращаемый список нельзя изменить;
- неизвестный `AccountId` возвращает пустой список.

Проверь случай, когда две записи имеют одинаковый `createdAt`.

### Задание 4. Уникальные типы операций

По истории счёта собери `Set<OperationType>` без Stream API. Если `OperationType` является enum, используй `EnumSet`.

Ответь:

- почему `List` хуже выражает уникальность;
- почему порядок `HashSet` нельзя показывать клиенту как стабильный контракт;
- когда для результата нужен `List`, отсортированный отдельно.

### Задание 5. Очередь непубликованных событий

Смоделируй локальную очередь `OutboxEvent` через `ArrayDeque`:

- событие добавляется в хвост;
- publisher забирает событие из головы;
- при ошибке событие можно вернуть в начало для учебного повторения;
- пустая очередь обрабатывается без исключения.

Объясни письменно, почему эта структура не заменяет таблицу outbox и брокер в финальном Wallet Service.

### Задание 6. Защита внутреннего состояния

Создай `AccountHistory`, принимающий `List<LedgerEntry>` в конструкторе.

Докажи тестом два свойства:

1. изменение исходного списка после конструктора не меняет историю;
2. список из `entries()` нельзя изменить.

Затем добавь в `LedgerEntry` изменяемое поле и покажи, почему `List.copyOf` не обеспечивает deep immutability. После
эксперимента верни `LedgerEntry` к неизменяемой модели.

### Задание 7. Сравнение структур

Подготовь 10 000 учебных счетов и реализуй поиск по `AccountId` двумя способами:

- последовательным проходом по `List<Account>`;
- через `Map<AccountId, Account>`.

Сначала объясни асимптотику. Затем измерь много повторных поисков через JMH, если уже знаком с ним, либо ограничься
грубым учебным измерением и явно укажи его недостатки. Не делай production-выводов по одному запуску `nanoTime`.

## Краткий итог

- `List` выражает упорядоченную последовательность с повторениями; основной вариант — `ArrayList`.
- `Set` выражает уникальность; `HashSet` не гарантирует порядок.
- `Map` выражает соответствие уникальных ключей значениям и не является `Collection`.
- `Queue` и `Deque` выражают порядок обработки; основной вариант для операций на концах — `ArrayDeque`.
- Hash-based коллекции требуют корректных и стабильных `equals/hashCode`.
- `HashMap` и `HashSet` дают ожидаемое, а не безусловное худшее `O(1)` для основных операций.
- `List.copyOf` создаёт неизменяемый снимок структуры, но не копирует сами элементы глубоко.
- `Comparable` задаёт естественный порядок типа, а `Comparator` — порядок конкретной операции.
- Порядок, уникальность и изменяемость являются частью контракта данных, а не случайными деталями реализации.
- Обычные коллекции общего назначения не являются потокобезопасными.
