## 1. HTTP semantics: смысл запроса и ответа

HTTP задаёт смысл методов, статусов и заголовков. REST — архитектурный стиль, в котором клиент работает с
представлениями ресурсов через единый интерфейс. JSON по HTTP сам по себе ещё не делает API REST. В Wallet Service
ресурсами служат кошелёк, перевод и история операций; URI идентифицирует ресурс, а метод определяет действие. Сервер не
должен зависеть от того, какой экран клиент открыл перед запросом:
каждый запрос приносит нужные данные и сведения для аутентификации.

Пример: клиент хочет перевести деньги и получить представление созданного перевода.

```http
POST /api/v1/transfers HTTP/1.1
Host: localhost:8080
Content-Type: application/json
Accept: application/json, application/problem+json
Idempotency-Key: training-transfer-001

{
  "sourceAccountId": "dc3fbc98-b93a-42a6-8d33-2fbbfcb95479",
  "targetAccountId": "f42c2df7-3275-4f30-9bd1-6be0375d3838",
  "amount": "1250.00",
  "currency": "RUB",
  "description": "Учебный перевод"
}
```

`Content-Type` описывает тело отправляемого сообщения, `Accept` — допустимые типы ответа. Аутентификацию добавим на
соответствующей неделе; окончательный контракт требует `Authorization: Bearer ...`.

### Безопасность метода и идемпотентность

Безопасный метод не запрашивает изменения предметных данных. Идемпотентный метод при повторении имеет тот же
предполагаемый эффект, что и один вызов. Эти свойства не требуют одинакового тела каждого ответа. Запись технического
лога при чтении допустима; списание денег по `GET` — нарушение смысла метода.

| Метод    | Обычное назначение                   | Безопасный | Идемпотентный по семантике HTTP |
|----------|--------------------------------------|------------|---------------------------------|
| `GET`    | Прочитать представление              | Да         | Да                              |
| `HEAD`   | Получить заголовки без тела ответа   | Да         | Да                              |
| `POST`   | Создать ресурс или выполнить команду | Нет        | Нет                             |
| `PUT`    | Задать полное новое состояние по URI | Нет        | Да                              |
| `PATCH`  | Изменить часть состояния             | Нет        | Не гарантируется                |
| `DELETE` | Удалить связь URI с ресурсом         | Нет        | Да                              |

Первый `DELETE` может вернуть `204`, повторный — `404`; ресурс всё равно остаётся удалённым. Для `PATCH` установка имени
в конкретное значение может быть идемпотентной, а команда «увеличить на 1» — нет. Подробный выбор `PUT` и `PATCH`
оставим неделе 8. В кошельке нельзя моделировать перевод как замену баланса:
это отдельная операция с проверками и записями истории.

HTTP также определяет кэширование и условные запросы. На этой неделе достаточно понимать:
баланс может измениться после чтения, и решение о списании принимает сервер по актуальному состоянию.
`ETag` и условные изменения разберём в следующем разделе плана.

Нормативные определения: [RFC 9110, разделы 9 и 15](https://www.rfc-editor.org/rfc/rfc9110.html), для частичного
изменения — [RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html).

## 2. Spring MVC: путь запроса

Spring MVC работает поверх Servlet API. В обычном приложении сервер принимает соединение, а
`DispatcherServlet` направляет запрос подходящему обработчику. Для понимания ошибки полезна такая цепочка:

```text
HTTP-запрос
  → фильтры Servlet (например, корреляция и позднее безопасность)
  → DispatcherServlet
  → поиск обработчика по пути, методу и типу содержимого
  → преобразование аргументов и проверка ограничений
  → метод контроллера
  → прикладной сервис → доменные объекты и репозитории
  → DTO ответа → HttpMessageConverter → JSON → HTTP-ответ

Ошибка на стадии MVC → обработчик исключения → HTTP-ответ об ошибке
```

`@Controller` может возвращать имя HTML-представления. `@RestController` объединяет `@Controller`
и `@ResponseBody`: результат метода становится телом ответа через преобразователь сообщений. Возвращённая строка в
REST-контроллере — тело, а не имя шаблона.

Маршруты объявляют `@RequestMapping`, `@GetMapping`, `@PostMapping` и другие аннотации. Две регистрации одинакового пути
и метода могут сделать выбор обработчика неоднозначным. Не добавляйте `@EnableWebMvc` для обычного контроллера: в Boot
это меняет режим настройки MVC, а не просто «включает REST».

Типичная аналогия в Express: выбор маршрута → разбор входа → проверка → обработчик → отправка JSON. В Spring многое
происходит до входа в метод: неправильный UUID уже может привести к `400`.

Источник: [методы обработчиков MVC](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods.html).

<a id="layers"></a>

## 3. Controller / service / repository: границы ответственности

| Слой       | Ответственность                                    | Пример в Wallet Service                             |
|------------|----------------------------------------------------|-----------------------------------------------------|
| Controller | HTTP-вход, DTO, вызов сценария, статус и заголовки | Принять JSON перевода и вернуть `201`               |
| Service    | Прикладной сценарий и бизнес-проверки              | Проверить счета, выполнить перевод, записать ledger |
| Repository | Получение и сохранение предметных данных           | Найти счёт по `AccountId`, сохранить перевод        |

Контроллер не должен сам списывать баланс. Репозиторий не должен решать, какой статус HTTP вернуть. Сервис не принимает
`HttpServletRequest` и не возвращает `ResponseEntity`: этот же сценарий должен быть доступен тесту или будущему
обработчику сообщения без имитации HTTP.

В текущем проекте `TransferService.createTransfer(TransferCommand)` возвращает `void`. Для API нужно вернуть созданный
`Transfer` либо отдельный результат сценария с его ID и данными. Нельзя сгенерировать второй ID в контроллере:
`Location` должен указывать именно на сохранённый перевод.

Рекомендуемая группировка продолжает существующую структуру:

```text
com.example.wallet
├── accounts
│   ├── Account, AccountRepository, InMemoryAccountRepository
│   ├── AccountService                         # добавить сценарии счетов
│   └── api
│       ├── AccountController
│       └── AccountResponse, CreateAccountRequest
├── transfers
│   ├── TransferService, TransferCommand, TransferRepository
│   └── api
│       ├── TransferController
│       └── CreateTransferRequest, TransferResponse, TransferMapper
└── api.error
    └── ApiExceptionHandler
```

Контроллеры обычно singleton beans. Не храните текущий запрос, клиента или последний перевод в полях:
параллельные запросы используют один экземпляр. И контейнер Spring, и веб-сервер уже существуют; добавление
`@RestController` не создаёт отдельный сервер для каждого класса.

<a id="dto"></a>

## 4. DTO против entity

DTO (Data Transfer Object) описывает данные на границе API. Доменная сущность описывает предметный объект с
идентичностью и правилами. Позднее появится JPA entity — объект, связанный с хранением в БД; сегодняшний `Account` не
становится JPA entity только потому, что называется сущностью.

Нельзя использовать один объект для всех трёх задач без оценки последствий:

- входная модель кошелька не должна позволять клиенту установить `balance`, `version`, `id` или `createdAt`;
- выходная модель содержит только обещанные контрактом поля;
- изменение схемы хранения не должно автоматически менять JSON;
- позднее связи JPA могут вызвать дополнительные запросы и циклы сериализации.

Для TypeScript это похоже на отдельные `CreateAccountRequest` и `AccountResponse` вместо передачи всего внутреннего
объекта. Однако TypeScript-интерфейс не проверяет пришедший JSON во время выполнения. В Java преобразование и проверка —
тоже отдельные этапы.

Пример выходной модели, каждый `public record` размещается в своём файле:

```java
import java.time.Instant;
import java.util.UUID;

public record AccountResponse(
        UUID id,
        UUID clientId,
        String currency,
        String balance,
        String status,
        Instant createdAt
) {
}
```

`balance` здесь строка десятичного числа: это соответствует примеру денежных полей в требованиях и позволяет JS-клиенту
избежать потери точности `Number`. Зафиксируйте представление в OpenAPI. Внутренний расчёт остаётся на `BigDecimal`, а
строка формируется с двумя знаками после запятой, без округления суммы, нарушающей инвариант.

Преобразование DTO → команда → результат → DTO лучше сначала написать явно. Маппер переносит данные; он не проверяет
остаток и не изменяет счёт. В текущем `Account` есть только признак активности, поэтому для полного контракта нужно
добавить `ACTIVE/BLOCKED/CLOSED` и время создания. Не выдавайте отсутствие этих данных за полноценную реализацию
требований.

<a id="jackson"></a>

## 5. Jackson: преобразование JSON

Сериализация превращает Java-объект в JSON, десериализация — JSON в Java-объект. Jackson выполняет это преобразование
для JSON-преобразователя MVC. Обычно контроллеру достаточно вернуть DTO; вручную вызывать `writeValueAsString` и
возвращать JSON-строку не требуется.

Для Spring Boot 4 основная линия — Jackson 3. При ручной работе `ObjectMapper` находится в
`tools.jackson.databind`, а аннотации вроде `JsonProperty` сохраняют пакет
`com.fasterxml.jackson.annotation`. Не копируйте импорт `com.fasterxml.jackson.databind.ObjectMapper`
из примера Boot 3 без проверки зависимости. Используйте настроенный Boot объект преобразования, если действительно нужно
вручную читать JSON: отдельно созданный экземпляр может иметь другие настройки.
Источник: [поддержка JSON в Boot](https://docs.spring.io/spring-boot/reference/features/json.html).

### Что нужно контролировать в контракте

`record` удобен для DTO: имена компонентов обычно становятся именами JSON-полей, а значения передаются конструктору. Для
обычных классов важны доступные свойства и способ создания объекта. Аннотация `@JsonProperty("sourceAccountId")`
позволяет задать внешнее имя, `@JsonIgnore` — исключить свойство. Эти аннотации не заменяют отдельные входные и выходные
DTO.

| JSON                          | Java                            | Что проверить                                |
|-------------------------------|---------------------------------|----------------------------------------------|
| `"dc3fbc98-…"`                | `UUID`                          | Неверный формат должен дать `400`            |
| `"RUB"`                       | `Currency`                      | Неизвестное значение не принимается          |
| `"1250.00"`                   | `BigDecimal` при преобразовании | Десятичная строка поддерживается настройками |
| `"2026-10-01T09:00:00Z"`      | `Instant`                       | ISO 8601 и UTC в ответе                      |
| отсутствующее поле или `null` | Ссылочный тип                   | Обязательность проверяется отдельно          |
| `[]`                          | `List<OperationResponse>`       | Вложенные типы известны из объявления DTO    |

Вход с `BigDecimal` может принимать и JSON-число, и строку в зависимости от правил преобразования. Если контракт
разрешает только строку строго заданного формата, обычной аннотации `@Digits` недостаточно:
нужны проверка исходного строкового поля либо настроенная десериализация. Для практики выберите и опишите один контракт,
затем проверьте его HTTP-запросами.

JSON `{"amount":"abc"}` не удаётся преобразовать в `BigDecimal`: Bean Validation ещё не запускается. JSON
`{"amount":"-1.00"}` преобразуется, затем нарушает ограничение суммы. Оба ответа могут иметь код `VALIDATION_ERROR`, но
источники ошибок различаются.

Также явно проверьте неизвестные поля, строки вместо чисел, пустую строку и `null`. Поведение зависит от конфигурации
Jackson; не выводите его из одного только Java-типа. Поля ответа — часть совместимости: переименование компонента record
может сломать клиента.

<a id="inputs"></a>

## 6. Request parameters, path variables и body

| Источник         | Аннотация        | Пример                  | Назначение                       |
|------------------|------------------|-------------------------|----------------------------------|
| Сегмент пути     | `@PathVariable`  | `/accounts/{accountId}` | Идентификатор ресурса            |
| Параметр запроса | `@RequestParam`  | `?page=0&size=20`       | Фильтр, сортировка, страница     |
| Тело сообщения   | `@RequestBody`   | JSON команды перевода   | Структурированные входные данные |
| Заголовок        | `@RequestHeader` | `Idempotency-Key: ...`  | Сведения об обработке запроса    |

Имена аргументов задавайте явно: это уменьшает зависимость от сохранения имён параметров при компиляции.
`@RequestParam` и `@RequestHeader` обязательны по умолчанию; `required = false` разрешает отсутствие.
`defaultValue` задаёт значение при отсутствии или пустом значении параметра. Строковое значение `abc`
не заменяется значением по умолчанию для `int`, а приводит к ошибке преобразования.

Учебный фрагмент метода внутри будущего `AccountController`; `service.history` и типы результата нужно добавить:

```java

@GetMapping("/{accountId}/operations")
public PageResponse<OperationResponse> history(
        @PathVariable("accountId") UUID accountId,
        @RequestParam(name = "page", defaultValue = "0") @Min(0) int page,
        @RequestParam(name = "size", defaultValue = "20") @Min(1) @Max(100) int size,
        @RequestParam(name = "operationType", required = false) OperationType operationType,
        @RequestParam(name = "dateFrom", required = false)
        @DateTimeFormat(iso = DateTimeFormat.ISO.DATE_TIME) Instant dateFrom,
        @RequestParam(name = "dateTo", required = false)
        @DateTimeFormat(iso = DateTimeFormat.ISO.DATE_TIME) Instant dateTo
) {
    return service.history(accountId, page, size, operationType, dateFrom, dateTo);
}
```

Аннотации ограничений импортируются из `jakarta.validation.constraints`, `DateTimeFormat` — из
`org.springframework.format.annotation`, HTTP-аннотации — из `org.springframework.web.bind.annotation`. Формат дат здесь
относится к параметрам URI, а не к настройкам JSON Jackson. В URL знак `+` в часовом смещении нужно кодировать как
`%2B`; проще передавать UTC с `Z`.

Не получайте владельца из произвольного `clientId` в теле перевода: право на списание определяется аутентифицированным
субъектом и проверкой доступа. UUID в пути сам по себе не является разрешением. Данные формы
`application/x-www-form-urlencoded` и JSON-тело — разные способы передачи данных. Для денежных команд используем JSON;
чтение не требует тела `GET`.

Источники: [параметры запроса](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/requestparam.html),
[тело запроса](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/requestbody.html).

### Минимальная граница перевода

Модель запроса:

```java
import com.example.wallet.shared.money.Currency;
import jakarta.validation.constraints.*;

import java.math.BigDecimal;
import java.util.UUID;

public record CreateTransferRequest(
        @NotNull UUID sourceAccountId,
        @NotNull UUID targetAccountId,
        @NotNull @DecimalMin(value = "0.00", inclusive = false)
        @Digits(integer = 17, fraction = 2) BigDecimal amount,
        @NotNull Currency currency,
        @Size(max = 500) String description
) {
}
```

Максимальная длина описания `500` — учебное решение, которого пока нет в требованиях:
внесите его в OpenAPI. Ограничение `17` целых разрядов соответствует будущему `numeric(19, 2)`.

Следующий фрагмент показывает первый проход без хранения результатов идемпотентности. Он **не готов для денежных
запросов с повторами**; раздел 12 описывает, как заменить прямой вызов сервиса. Чтобы использовать его, измените сервис
на возврат `Transfer`, добавьте `TransferMapper.toResponse`
и DTO `TransferResponse` с плоскими UUID, строкой суммы, валютой, статусом и временем.

```java
import com.example.wallet.accounts.AccountId;
import com.example.wallet.transfers.Transfer;
import com.example.wallet.transfers.TransferCommand;
import com.example.wallet.transfers.TransferService;
import jakarta.validation.Valid;
import org.springframework.http.MediaType;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import java.net.URI;

@RestController
@RequestMapping("/api/v1/transfers")
public class TransferController {
    private final TransferService service;

    public TransferController(TransferService service) {
        this.service = service;
    }

    @PostMapping(consumes = MediaType.APPLICATION_JSON_VALUE,
            produces = MediaType.APPLICATION_JSON_VALUE)
    public ResponseEntity<TransferResponse> create(
            @RequestHeader("Idempotency-Key") String key,
            @Valid @RequestBody CreateTransferRequest request
    ) {
        // Временная проверка до добавления механизма идемпотентности.
        if (key.isBlank() || key.length() > 128) {
            throw new InvalidRequestException("Некорректный Idempotency-Key");
        }
        TransferCommand command = new TransferCommand(
                new AccountId(request.sourceAccountId().toString()),
                new AccountId(request.targetAccountId().toString()),
                request.amount(), request.currency(), request.description());
        Transfer transfer = service.createTransfer(command);
        TransferResponse response = TransferMapper.toResponse(transfer);
        return ResponseEntity.created(
                URI.create("/api/v1/transfers/" + response.id())
        ).body(response);
    }
}
```

`InvalidRequestException` — новый предметно понятный тип для ошибки входа; его нужно добавить и обработать как `400`.
Ограничение длины ключа `128` тоже является выбранным учебным контрактом. Контроллер задаёт относительный URI созданного
ресурса в `Location`, а не адрес текущего POST. Маршрут `GET /api/v1/transfers/{transferId}` должен позволять прочитать
этот ресурс. В финальном варианте повтор возвращает сохранённый ответ, поэтому безусловная сборка нового `201`
после каждого вызова сервиса уже не подходит.

Источник аннотаций
маршрутизации: [Mapping Requests](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-requestmapping.html).

<a id="statuses"></a>

## 7. HTTP status codes: ответ сообщает результат

Выбор статуса связывает смысл HTTP с контрактом проекта. Таблица ниже — принятые решения Wallet Service; для
бизнес-отказов другой API может использовать иной согласованный контракт.

| Статус | Когда применять                                 | Пример                                           |
|--------|-------------------------------------------------|--------------------------------------------------|
| `200`  | Успешное чтение или команда с результатом       | Кошелёк получен, статус изменён                  |
| `201`  | Ресурс создан                                   | Новый счёт или перевод, заголовок `Location`     |
| `204`  | Успех без тела                                  | Возможен в других API для удаления               |
| `400`  | Некорректный вход                               | UUID, JSON, сумма, параметры страницы            |
| `401`  | Нет действительной аутентификации               | JWT отсутствует или отклонён                     |
| `403`  | Аутентификация есть, права отсутствуют          | Чтение чужого кошелька                           |
| `404`  | Ресурс не найден                                | `ACCOUNT_NOT_FOUND`                              |
| `405`  | Метод для найденного маршрута не поддерживается | `PUT` на маршрут только для `GET`                |
| `406`  | Нельзя выдать допустимое клиентом представление | Запрошен неподдерживаемый тип ответа             |
| `409`  | Операция конфликтует с текущим состоянием       | Недостаточный остаток, повтор ключа с иным телом |
| `415`  | Тип входного содержимого не поддерживается      | XML вместо предусмотренного JSON                 |
| `500`  | Неожиданная внутренняя ошибка                   | Непредусмотренный сбой приложения                |
| `503`  | Временно невозможно обслужить запрос            | Временная недоступность зависимости              |

У `204` нет тела. Для Wallet Service изменение статуса счёта по требованиям возвращает `200`, а успешная синхронная
денежная операция — `201`, поэтому `202 Accepted` здесь не нужен:
он означал бы принятие запроса, обработка которого ещё не завершилась.
`401` также предполагает соответствующий `WWW-Authenticate`; позднее это настроит слой безопасности. Ответ `200` с полем
`success: false` мешает клиенту и инфраструктуре правильно распознать отказ.

`ResponseEntity<T>` позволяет задать статус, заголовки и тело. Для статического статуса подходит
`@ResponseStatus`, но `201` с динамическим `Location` удобнее выразить через `ResponseEntity`. Различайте `404` из-за
неверного URL и `404` из-за отсутствующего счёта: статус один, причина и код разные.

Источник: [ResponseEntity](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/responseentity.html).

<a id="validation"></a>

## 8. Validation: проверка формы и бизнес-инвариантов

Зависимость Validation содержит реализацию Jakarta Bean Validation. Аннотация ограничения описывает правило, а MVC с
`@Valid` запускает проверку принятого DTO. Это не отменяет проверки сервиса при вызове из другого входа.

| Ограничение   | Значение                                  | Важная граница                        |
|---------------|-------------------------------------------|---------------------------------------|
| `@NotNull`    | Значение обязательно                      | Пустую строку не запрещает            |
| `@NotBlank`   | Строка содержит непробельный символ       | Применяется к строкам                 |
| `@Size`       | Длина строки или размер коллекции         | Само по себе обычно допускает `null`  |
| `@DecimalMin` | Нижняя граница десятичного числа          | Обязательность задаёт `@NotNull`      |
| `@Digits`     | Допустимое число целых и дробных разрядов | Не проверяет исходный формат JSON     |
| `@Min/@Max`   | Числовая граница                          | Удобны для `page` и `size`            |
| `@Valid`      | Проверить вложенный объект                | Само по себе не является ограничением |

`@Valid @RequestBody CreateTransferRequest` проверяет ограничения DTO до вызова метода. Для вложенного `AddressRequest`
нужна `@Valid` на соответствующем компоненте; обязательность вложенного объекта задаётся отдельно. Для взаимосвязанных
полей можно написать ограничение на уровне класса, например «исходный и целевой UUID различаются». Простые проверки
взаимосвязи допустимо сначала выполнять в сценарии с отдельным исключением некорректного входа.

### Три разных группы ошибок

1. **Преобразование:** `accountId=abc`, обрыв JSON, неизвестная валюта. DTO или аргумент не удалось создать.
2. **Форма входа:** `amount=-1`, `size=101`, слишком длинное описание. Данные прочитаны, но ограничения нарушены.
3. **Состояние предметной области:** счёт заблокирован, средств недостаточно, клиент не может списывать. Нужны данные
   сервера и проверка в прикладном сценарии; в Wallet Service это `409` или `403`.

Не помещайте запросы к репозиторию в `ConstraintValidator` суммы: проверка доступного остатка должна работать вместе с
защитой от конкурентных изменений. Сегодня достаточный баланс может измениться до записи. Аннотации не дают транзакцию и
не защищают от двух параллельных списаний.

### Какие исключения ловить

Выбор исключения зависит от **уровня проверки, который задаёт сигнатура контроллера**:

- `@Valid @ModelAttribute HistoryRequest request`, где ограничения находятся внутри DTO, — проверка отдельного объекта
  и `MethodArgumentNotValidException` при нарушении ограничения;
- `@RequestParam @Min(0) int page`, где ограничение стоит прямо на аргументе контроллера, — проверка метода
  и `HandlerMethodValidationException` при нарушении ограничения.

`@Valid` сама не является ограничением. Если добавить прямое ограничение к сигнатуре, проверка метода охватывает также
вложенные ограничения DTO с `@Valid`. Ошибки преобразования могут возникнуть раньше этой проверки, а `BindingResult`
меняет способ передачи ошибок контроллеру.

Подробный разбор с примерами двух сигнатур, смешанного случая, ошибок `page=abc` и `page=-1`, структуры исключений и
методов advice: [Два механизма проверки в Spring MVC](validation/mvc-validation-exceptions.md).

Источник: [Validation в Spring MVC](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-validation.html).

<a id="pagination"></a>

## 9. Pagination: история операций

История растёт без верхней границы. Возврат всех записей увеличивает расход памяти, время ответа и нагрузку на клиент.
Пагинация возвращает ограниченную часть результата вместе с данными для навигации.

Контракт учебного API:

```http
GET /api/v1/accounts/{accountId}/operations?page=0&size=20&operationType=TRANSFER_OUT&dateFrom=2026-10-01T00:00:00Z
```

- `page` отсчитывается от нуля; минимум `0`, значение по умолчанию `0`;
- `size` от `1` до `100`, по умолчанию `20`; неверное значение даёт `400`;
- сначала применяются доступ и фильтры, затем сортировка, затем выбор страницы;
- порядок фиксирован: `createdAt DESC, id DESC`, как развитие требования сортировки от новых к старым;
- учебное решение для дат: `dateFrom` включительно, `dateTo` исключительно, оба в UTC;
- при заданных двух датах требуется `dateFrom < dateTo`; этот выбор нужно записать в OpenAPI.

Второе поле сортировки нужно потому, что разные операции могут иметь одинаковое время. Без него одна запись способна
«прыгать» между страницами даже при неизменном наборе данных.

Выходной DTO не обязан совпадать с внутренним типом Spring Data:

```java
import java.util.List;

public record PageResponse<T>(
        List<T> items,
        int page,
        int size,
        long totalElements,
        long totalPages
) {
}
```

Пример ответа, в реальном контракте элементы содержат все обещанные поля операции:

```json
{
  "items": [],
  "page": 4,
  "size": 20,
  "totalElements": 65,
  "totalPages": 4
}
```

Здесь запрос вышел за последнюю существующую страницу: выбранный контракт возвращает `200` и пустой список. Существующий
счёт без операций тоже возвращает `200`, отсутствующий счёт — `404`.
`totalElements` — число после фильтрации, до выделения страницы.
`totalPages = totalElements / size + (totalElements % size == 0 ? 0 : 1)`; для пустой истории — `0`. Смещение считайте в
`long`: `(long) page * size`, иначе возможен переполненный `int`.

Для текущего хранилища допустимо сделать снимок списка, отфильтровать, отсортировать и выделить часть. После подключения
БД фильтры, порядок и ограничение должны выполняться запросом к БД, а не загрузкой всей истории.
`Page` со счётчиком часто требует отдельного подсчёта, `Slice` отвечает лишь на вопрос о следующей части. Spring Data и
его типы подробно изучим после подключения хранения.

Стабильный порядок не означает стабильный снимок между HTTP-запросами: новые операции сдвигают страницы, поэтому
возможны повторы и пропуски. Для растущей истории позднее рассмотрим курсор по паре
`createdAt/id`. Это отдельный контракт, его не нужно выдавать за обычный `page`.

<a id="errors"></a>

## 10. Error response: контракт для человека и программы

Wallet Service требует `application/problem+json` по RFC 9457. Это общий формат описания отказа, который дополняется
полями проекта. Клиенту нужен стабильный `code`, а не разбор русской строки `detail`.

```http
HTTP/1.1 400 Bad Request
Content-Type: application/problem+json
X-Correlation-Id: training-request-42

{
  "type": "urn:wallet:problem:validation",
  "title": "Некорректный запрос",
  "status": 400,
  "detail": "Проверьте поля запроса",
  "instance": "/api/v1/transfers",
  "code": "VALIDATION_ERROR",
  "correlationId": "training-request-42",
  "errors": [
    {"field": "amount", "code": "POSITIVE_AMOUNT_REQUIRED", "message": "Сумма должна быть больше нуля"}
  ]
}
```

`type` идентифицирует вид проблемы; `title` кратко называет этот вид;
`status` совпадает с фактическим статусом HTTP; `detail` описывает конкретный отказ;
`instance` обозначает этот случай проблемы, например URI запроса.
`code`, `correlationId`, `errors` — расширения Wallet Service. URN в примере — выбранный идентификатор, а не
обязательный URI из стандарта. Для ошибок без отдельных полей можно возвращать `errors: []`.

Массив удобнее словаря `field → message`, поскольку одно поле может нарушить несколько ограничений. Не полагайтесь на
порядок сообщений валидатора и не возвращайте исходное отклонённое значение:
оно может содержать приватные данные. Для ошибочного JSON не всегда возможно надёжно назвать поле, поэтому общий
безопасный `detail` с пустым `errors` лучше, чем пересылка текста Jackson.

Идентификатор корреляции связывает ответ с техническими журналами. Его следует установить в фильтре до MVC: принять
ограниченный по длине и допустимым символам `X-Correlation-Id` либо сгенерировать свой, затем поместить в атрибут
запроса и заголовок ответа. При использовании MDC очищайте его в `finally`. Correlation ID не является ключом
идемпотентности: повторы одной операции могут иметь разные ID запросов.

Нормативный формат: [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html).

<a id="advice"></a>

## 11. `@ControllerAdvice`: единая обработка исключений

`@ExceptionHandler` превращает определённое исключение в HTTP-ответ. Его можно объявить внутри контроллера, но
одинаковые правила удобнее вынести в `@ControllerAdvice`. `@RestControllerAdvice` добавляет
`@ResponseBody`, поэтому подходит для JSON API. Доменные исключения при этом остаются независимыми от HTTP.
Источник: [Controller Advice](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-advice.html).

### Один доменный отказ

Ниже — пример будущего обработчика. Нужно добавить `InsufficientFundsException` и выбрасывать его из сценария вместо
общего `IllegalStateException`. Атрибут `correlationId` устанавливает упомянутый выше фильтр.

```java
import jakarta.servlet.http.HttpServletRequest;
import org.springframework.http.HttpStatus;
import org.springframework.http.MediaType;
import org.springframework.http.ProblemDetail;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

import java.net.URI;
import java.util.List;

@RestControllerAdvice
public class ApiExceptionHandler {
    @ExceptionHandler(InsufficientFundsException.class)
    public ResponseEntity<ProblemDetail> insufficientFunds(
            InsufficientFundsException exception,
            HttpServletRequest request
    ) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
                HttpStatus.CONFLICT, "На исходном счёте недостаточно средств");
        problem.setType(URI.create("urn:wallet:problem:insufficient-funds"));
        problem.setTitle("Перевод невозможен");
        problem.setInstance(URI.create(request.getRequestURI()));
        problem.setProperty("code", "INSUFFICIENT_FUNDS");
        problem.setProperty("correlationId", request.getAttribute("correlationId"));
        problem.setProperty("errors", List.of());
        return ResponseEntity.status(HttpStatus.CONFLICT)
                .contentType(MediaType.APPLICATION_PROBLEM_JSON)
                .body(problem);
    }
}
```

`ProblemDetail` представляет стандартные поля, а `setProperty` добавляет расширения в JSON на верхнем уровне. Сообщение
ответа задано явно: оно не раскрывает баланс и не копирует внутреннее `exception.getMessage()`. Один обработчик не
обеспечивает полный контракт всех ошибок.

### Как покрыть инфраструктурные ошибки MVC

Удобная основа — наследник `ResponseEntityExceptionHandler`. Он предоставляет обработку типовых исключений MVC с
`ProblemDetail`. В собственном классе нужно переопределить нужные методы и дополнить тела ошибками проекта. Для уже
обрабатываемых базовым классом исключений используйте его защищённые методы, а не дублирующие `@ExceptionHandler`,
которые могут создать неоднозначность.

| Источник                                          | Что нужно получить в Wallet Service                      |
|---------------------------------------------------|----------------------------------------------------------|
| `MethodArgumentNotValidException`                 | `400 VALIDATION_ERROR`, ошибки полей DTO                 |
| `HandlerMethodValidationException`                | `400` для входа, ошибки параметров; `500` для результата |
| `HttpMessageNotReadableException`                 | `400 VALIDATION_ERROR`, безопасный текст о теле          |
| `MethodArgumentTypeMismatchException`             | `400 VALIDATION_ERROR`, неверный UUID или параметр       |
| Отсутствующий параметр или обязательный заголовок | `400 VALIDATION_ERROR`                                   |
| Неподдерживаемые метод или тип содержимого        | Сохранить `405/406/415`, добавить расширения             |
| Доменный отказ                                    | Статус и стабильный код из требований                    |
| Непредусмотренное исключение                      | `500`, нейтральное сообщение и ID корреляции             |

Для DTO ошибки полей можно получить через `getBindingResult().getFieldErrors()`, а ошибки всего объекта — через
`getGlobalErrors()`. При проверке метода ошибки сгруппированы по аргументам: учтите параметры запроса, заголовки и
вложенные поля DTO. Их перевод в публичные коды нужно сделать явно, а не публиковать внутреннее имя класса исключения.

Не преобразуйте любой `IllegalArgumentException` в `400` и любой `IllegalStateException` в `409`:
они могут означать дефект сервера. Текущий сервис использует эти общие исключения, поэтому сначала разделите ожидаемые
отказы на типы или на единое доменное исключение с перечислением причин. Для лимита перевода согласуйте новый машинный
код, поскольку минимальная таблица требований его не задаёт.

При расширении базового обработчика сохраняйте переданные заголовки, например `Allow` для `405`. Настройка
`spring.mvc.problemdetails.enabled=true` может включить базовую поддержку проблем в Boot, но сама по себе не добавляет
`code`, корреляцию и ошибки полей вашего контракта. Выберите один согласованный путь обработки, проверьте приоритеты
обработчиков.

`@ControllerAdvice` относится к обработке MVC, а не ко всем исключениям процесса. Ошибки фильтра безопасности могут
возникнуть раньше MVC; для них позднее понадобятся
`AuthenticationEntryPoint` и `AccessDeniedHandler`. Ошибки маршрутизации, контейнера и `/error`
тоже нужно проверить отдельно. Требование «все ошибки в одном формате» проверяется HTTP-запросами, а не только наличием
класса advice.

Источник реализации проблем в
Spring: [Error Responses](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-rest-exceptions.html).

<a id="idempotency"></a>

## 12. Idempotency basics: повтор не должен списать деньги ещё раз

Представьте: перевод завершился, сервер сохранил данные, но соединение оборвалось до ответа. Клиент видит сетевую ошибку
и не знает, выполнен ли запрос. Повтор обычного `POST` может создать второй перевод. Отключение кнопки в React уменьшает
случайные клики, но не решает потерю ответа или повтор из другого клиента.

Для одной логической операции клиент создаёт ключ и сохраняет его до получения определённого результата. Повтор этой
операции использует прежний ключ; новый перевод, даже на ту же сумму, получает новый. Ключ идемпотентности делает
конкретную операцию POST защищённой от дублей по контракту приложения, а не меняет семантику всех POST в HTTP.

### Контракт Wallet Service

Ключ уникален в области `(авторизованный субъект, тип операции, ключ)`. Один и тот же текст ключа у разных субъектов не
должен раскрывать чужой ответ. Сохранённую запись читают только после проверки аутентификации и необходимого доступа.

```text
Запрос → проверка входа и доступа → нормализованная команда → поиск/резервирование ключа
  новый ключ               → выполнить операцию → сохранить результат → вернуть ответ
  тот же ключ и команда    → вернуть сохранённый статус и тело
  тот же ключ, иная команда → 409 IDEMPOTENCY_KEY_REUSED
```

Сравнивается не исходный JSON: порядок свойств и пробелы могут различаться. Нормализованный запрос должен включать оба
счёта, сумму, валюту, описание и значимые данные маршрута (например, счёт для пополнения). Выберите правила для `null`
/отсутствующего описания и суммы
`1250.0`/`1250.00`, затем сформируйте однозначное представление и его криптографический отпечаток. Не используйте Java
`hashCode`: это не подходящий отпечаток для такого контракта. Сначала отклоняйте недопустимую точность, затем
нормализуйте; округлением нельзя «исправлять» вход.

| Сценарий                                      | Ожидаемый результат                               |
|-----------------------------------------------|---------------------------------------------------|
| Новый ключ, корректный перевод                | Один перевод, `201`, две ledger entries           |
| Прежний ключ, та же нормализованная команда   | Тот же статус и тело, балансы не меняются         |
| Прежний ключ, изменена сумма или целевой счёт | `409 IDEMPOTENCY_KEY_REUSED`                      |
| Два одновременных запроса с одним ключом      | Одно изменение балансов, согласованный ответ      |
| Перезапуск приложения в итоговой версии       | Сохранённая защита от повтора продолжает работать |

В требованиях сохраняются статус и тело HTTP-ответа. Дополнительно сохраните или детерминированно восстановите значимые
заголовки, например `Location`. Не возвращайте повтору `200` вместо сохранённого `201`. Если в сохранённом теле ошибки
есть старый `correlationId`, заранее согласуйте политику его повторной выдачи и текущего заголовка корреляции; не
меняйте сохранённое тело незаметно.

### Почему проверки `Map.containsKey` недостаточно

Два запроса могут одновременно увидеть отсутствие ключа. Даже потокобезопасная карта не делает последовательность
«проверить → изменить два счёта → записать историю → сохранить ответ» атомарной. И разные ключи одновременно могут
списывать с одного счёта: идемпотентность не заменяет защиту баланса.

Для учебной однопроцессной версии допустим единый замок вокруг денежного сценария и сохранения результата, если все
денежные изменения проходят через него. Эта версия теряет записи при перезапуске и не работает для нескольких
экземпляров сервиса. Локальные замки на каждый ключ решают только дубли одного ключа, а не конкурирующие списания с
разными ключами.

В итоговом сервисе нужны уникальное ограничение в БД для области ключа и согласованная транзакция, связывающая денежные
изменения, ledger, outbox и результат идемпотентности. После сбоя не должно быть состояния «деньги списаны, запись
защиты потеряна». Подробная реализация — на неделях транзакций и конкурентности.

Не оставляйте неопределённым случай «тот же ключ ещё выполняется»: для учебной версии можно ждать завершения под общим
замком; для БД нужно спроектировать ожидание и ограничение времени. Успешный повтор и конфликт иного тела уже определены
требованиями. Какие бизнес-отказы сохраняются, а какие временные технические сбои можно повторить, зафиксируйте
отдельно. Не записывайте ошибки аутентификации или непарсируемого тела как завершённую денежную операцию.

Записи хранятся не менее 24 часов; после удаления записи прежний ключ больше не гарантирует защиту. Клиенту нужно знать
окно хранения. Идемпотентность не означает абсолютную гарантию «ровно один раз» для любой сети и любого срока — она
работает в выбранной области и при сохранности записи.

Основа этого
раздела — [раздел 9 требований проекта](../../src/main/java/com/example/wallet/technical-requirements.md#9-идемпотентность).

## 13. Практика: HTTP-граница Wallet Service

### Задание 1. Зафиксировать API счетов

Пункт плана «CRUD для счетов» адаптируем к предметным требованиям:
создать, прочитать, получить список и изменить статус. Физическое удаление кошельков и прямую запись баланса не
добавляем: история неизменяема, закрытие возможно только при нулевом остатке.

Реализуйте маршруты создания счёта клиента, чтения счёта и списка счетов, команды `block`, `unblock`, `close`
из требований. Для создания — `201` и `Location`, для чтения и изменения статуса — `200`. Добавьте отдельные DTO; вход
создания не принимает баланс, ID и статус. Клиент должен существовать: расширьте учебную модель клиентов или подготовьте
явные тестовые данные с проверяемым набором клиентов, а не принимайте любой UUID как существующего.

Расширьте состояние счёта до `ACTIVE/BLOCKED/CLOSED`. Проверьте запрет закрытия ненулевого кошелька и запрет возвращения
закрытого счёта в активное состояние. Новые коды таких отказов внесите в контракт. Подготовка начальных остатков
выполняется через учебные данные или сценарий пополнения, а не полем HTTP-запроса.

### Задание 2. Подключить перевод

Добавьте DTO и мапперы, измените возврат `createTransfer`, подключите `POST /api/v1/transfers`
и чтение перевода. Все бизнес-проверки остаются в сценарии. Добавьте проверку ключа и учебное хранение результатов
идемпотентности до проверки повторов. Для создания и возврата результата используйте ID действительно сохранённого
перевода.

Для запросов подготовьте `requests/transfer.json` с телом из раздела 1 и существующими ID. Используйте `curl.exe`, чтобы
в PowerShell не попасть на исторический псевдоним `curl`:

```powershell
curl.exe -i -X POST http://localhost:8080/api/v1/transfers -H "Content-Type: application/json" -H "Accept: application/json, application/problem+json" -H "Idempotency-Key: training-transfer-001" --data-binary "@requests/transfer.json"
```

Повторите команду с тем же файлом, затем с изменённой суммой. Проверьте не только HTTP, но и балансы, количество
переводов и ledger entries. Для возврата исходного ответа потребуется отдельный прикладной сценарий идемпотентности или
результат с сохранёнными HTTP-данными, который контроллер переводит в ответ. Доменный `TransferService` не должен сам
конструировать `ResponseEntity`.

### Задание 3. Проверить все виды входа

Добавьте Bean Validation. Испытайте отсутствующую сумму, отрицательную, нулевую, сумму с тремя дробными знаками,
описание за пределом длины, неизвестную валюту, неверный UUID, повреждённый JSON и пропущенный ключ. Для каждого отказа
покажите, что состояние хранилищ не изменилось. В HTTP-слое необязательно использовать живой сервер: позже `MockMvc`
позволит проверить маршрутизацию, преобразование, ограничения и advice. Прямой вызов метода контроллера этого не
проверяет.

### Задание 4. Сделать единый формат ошибок

Разделите ожидаемые доменные отказы сервиса, реализуйте advice и дополнение ошибок MVC. Добавьте раннюю установку
`X-Correlation-Id` и его возврат в успешных и ошибочных ответах. Проверьте, что статус HTTP совпадает с полем `status`,
тип содержимого — `application/problem+json`, а SQL, трассировки и внутренние имена классов не появляются в теле. Ошибки
несуществующего URL и неподдерживаемого метода проверьте отдельными запросами.

### Задание 5. Добавить историю с пагинацией

Подготовьте больше 20 ledger entries, в том числе записи с одинаковым `createdAt`. Реализуйте `page`, `size`, фильтры
типа и дат и порядок по `createdAt/id`. Проверьте пустую историю, отсутствующий счёт, страницы без пересечения при
неизменном наборе, выход за последнюю страницу, `page=-1`, `size=0`, `size=101`, `page=abc` и некорректный интервал дат.
Разделите неверное преобразование и нарушенное ограничение в реализации обработки ошибок.

### Задание 6. Описать контракт OpenAPI

Добавьте `openapi/wallet-api.yaml`: библиотека генерации для начала необязательна. Опишите реализованные пути,
обязательные заголовки, параметры с границами и значениями по умолчанию, схемы DTO, примеры и все применяемые ответы.
Успех использует `application/json`, ошибки — `application/problem+json`. Для UUID задайте `format: uuid`, для времени —
`date-time`; для строковых денежных значений — согласованный формат двух десятичных знаков. Укажите `Location`,
`X-Correlation-Id`, повтор с прежним ключом и `409` при ином теле. Отдельно опишите временную учебную аутентификацию и
будущую JWT-схему, чтобы документ не обещал несуществующую защиту. Все доступные операции должны совпадать с
фактическими маршрутами.

Источник формата описания: [OpenAPI Specification](https://spec.openapis.org/oas/latest.html).

### Матрица приёмки

| Проверка                                   | HTTP-результат                  | Проверка состояния                                |
|--------------------------------------------|---------------------------------|---------------------------------------------------|
| Создание кошелька существующего клиента    | `201`, `Location`, DTO          | Нулевой баланс, активный статус                   |
| Корректный перевод                         | `201`, DTO перевода             | Один перевод, две ledger entries, сумма сохранена |
| Повтор ключа с тем же телом                | Прежний статус и тело           | Нет дополнительного изменения                     |
| Повтор ключа с иной суммой                 | `409 IDEMPOTENCY_KEY_REUSED`    | Нет дополнительного изменения                     |
| Отсутствующий кошелёк                      | `404 ACCOUNT_NOT_FOUND`         | Нет перевода и ledger entries                     |
| Недостаточный остаток                      | `409 INSUFFICIENT_FUNDS`        | Оба баланса прежние                               |
| Кошелёк неактивен                          | `409 ACCOUNT_NOT_ACTIVE`        | Нет новых денежных записей                        |
| Неверный JSON, сумма или параметр страницы | `400 VALIDATION_ERROR`          | Сервис не выполняет денежную операцию             |
| XML вместо JSON                            | `415`, единый формат ошибки     | Нет операции                                      |
| Пустая история существующего счёта         | `200`, пустой `items`           | Нет изменений                                     |
| Две записи с одинаковым временем           | `200`, устойчивый порядок по ID | Каждая запись учтена на нужной странице           |

Проверку одновременных повторов добавьте только после реализации выбранной синхронизации. Денежные запросы HTTP уже
могут выполняться параллельно, поэтому прежнее допущение сервиса «один поток, хранилища без сбоев» нужно явно ограничить
учебным режимом либо обеспечить общей защитой. До БД и транзакций эта практика демонстрирует HTTP-контракт, а не
завершённую надёжность Wallet Service.

## 14. Самопроверка

1. Почему чтение через `GET` не должно списывать деньги, даже если браузер делает запрос один раз?
2. Чем безопасный метод отличается от идемпотентного? Может ли статус повторного ответа отличаться?
3. Чем `Content-Type` отличается от `Accept`? Откуда берутся `415` и `406`?
4. Что произойдёт до входа в контроллер при неправильном UUID?
5. Почему `@RestController` возвращает DTO через преобразователь сообщений?
6. Почему `TransferService` не должен возвращать `ResponseEntity`?
7. Почему создание DTO ответа не должно генерировать новый ID перевода?
8. Какие поля внутреннего `Account` клиенту нельзя разрешать устанавливать?
9. Чем ошибка Jackson отличается от нарушения `@DecimalMin`?
10. Почему сумма строкой в JSON полезна JS-клиенту, хотя на сервере используется `BigDecimal`?
11. Почему `@Valid` не заменяет проверки бизнес-инвариантов?
12. Когда появится `MethodArgumentNotValidException`, а когда `HandlerMethodValidationException`?
13. Почему проверка результата метода не должна возвращать клиенту `400`?
14. Почему `@ControllerAdvice` не обрабатывает автоматически любой отказ фильтра безопасности?
15. Зачем в ошибке нужны одновременно `code`, `detail` и `correlationId`?
16. Почему сортировки только по времени недостаточно для пагинации?
17. Почему `totalElements` считается до выбора страницы, но после фильтрации?
18. Почему устойчивый порядок не даёт неизменный снимок между двумя HTTP-запросами?
19. Что возвращать при повторе завершённого перевода с тем же ключом и телом?
20. Почему `ConcurrentHashMap` не делает перевод и сохранение ответа атомарными?
21. Почему ключ идемпотентности не заменяет блокировку конкурентных списаний с одного счёта?
22. Как потеря записи идемпотентности после успешного списания может привести к дублю?

## Что оставить на следующие недели

Неделя 8 углубит проектирование ресурсов, `PUT/PATCH`, совместимость API, условные запросы и документацию. Недели
хранения и транзакций дадут PostgreSQL, ограничения, атомарность и защиту конкурентных изменений. Неделя безопасности
заменит временные сведения о клиенте на проверенный JWT и реальные правила доступа. Сейчас результат — понятный
HTTP-контракт поверх существующих сценариев с проверяемыми отказами и явно обозначенными ограничениями учебного
хранилища.
