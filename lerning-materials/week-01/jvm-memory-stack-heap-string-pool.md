# Память JVM: stack, heap, string pool и связь с оперативной памятью

[← Вернуться к учебному плану](../java-backend-learning-plan.md)

## Что нужно понять

После изучения темы ты должен уметь:

1. отличать память процесса от логических областей, которыми управляет JVM;
2. объяснить, где находятся локальные переменные, объекты и ссылки;
3. понимать, почему у каждого потока свой stack, а heap обычно общий;
4. описать жизненный цикл объекта и роль сборщика мусора;
5. предсказывать поведение строковых литералов, `new String(...)` и `intern()`;
6. не путать `-Xmx` с объёмом оперативной памяти, который видит операционная система;
7. по симптому различать `StackOverflowError` и `OutOfMemoryError`.

Эта глава описывает удобную для прикладного разработчика модель HotSpot JVM на Java 21. Спецификация Java не требует,
чтобы конкретная JVM физически размещала данные ровно так. JIT-компилятор и сборщик мусора вправе менять детали, пока
поведение программы остаётся тем же.

## 1. Сначала процесс и оперативная память

Когда выполняется команда `java ...`, операционная система создаёт **процесс**. У процесса есть собственное виртуальное
адресное пространство: большой диапазон адресов, доступный именно этому процессу. Это ещё не означает, что под каждый
адрес сразу занята физическая оперативная память.

Операционная система отображает используемые страницы виртуальной памяти на физические страницы RAM по мере
необходимости. Часть страниц может быть временно выгружена в swap/pagefile. Поэтому «память Java-приложения» — не
отдельный вид памяти: JVM — обычная программа, которая запрашивает память у ОС и управляет ею внутри своего процесса.

Упрощённая картина:

```text
Оперативная память компьютера
        ▲
        │ ОС выделяет и отображает страницы
        │
Процесс Java-приложения
├── heap JVM                    объекты приложения
├── stack главного потока        вызовы main и его методов
├── stack HTTP-потока            вызовы обработки одного запроса
├── metaspace                    метаданные загруженных классов
├── JIT-код, буферы, native code память JVM и библиотек
└── другие области процесса
```

В диспетчере задач или `top` видна память **всего процесса**, а не только heap. Поэтому процесс способен занимать
заметно больше, чем задано `-Xmx`.

### Виртуальная, выделенная и фактически используемая память

Для диагностики полезно не смешивать три уровня:

| Вопрос | Ответ |
|---|---|
| Какой диапазон адресов может использовать процесс? | Виртуальное адресное пространство. |
| Сколько памяти JVM разрешено занять под объекты? | Ограничение heap, например `-Xmx`. |
| Сколько RAM сейчас связано с процессом? | Зависит от реально затронутых страниц, ОС, сборщика мусора, стеков, metaspace и native-памяти. |

`-Xms` задаёт начальный размер heap, `-Xmx` — его верхнюю границу. Они не являются обещанием, что JVM сразу займёт
или постоянно будет удерживать ровно такое количество физической RAM.

```shell
java -Xms256m -Xmx1024m -jar wallet-service.jar
```

В этой команде до 1 ГиБ отведено под управляемый JVM heap. Помимо него процессу нужны память для потоков, классов,
сгенерированного JIT-кода, сетевых буферов, JDBC-драйвера и других нативных частей.

## 2. Stack: память выполнения метода

У каждого Java-потока есть собственный **stack вызовов**. При входе в метод JVM создаёт в нём новый *stack frame*;
при нормальном выходе из метода или выбросе необработанного им исключения frame снимается.

В frame концептуально находятся:

- параметры метода;
- локальные переменные примитивных типов и ссылки;
- промежуточные значения вычислений;
- сведения, куда вернуться после окончания метода.

```java
static void transfer(Account from, Account to, BigDecimal amount) {
    boolean allowed = from.canWithdraw(amount);
    if (allowed) {
        from.withdraw(amount);
        to.deposit(amount);
    }
}
```

Во frame `transfer` лежат ссылки `from`, `to`, `amount` и примитив `allowed`. Сами `Account` и `BigDecimal` — объекты;
для обычной модели они находятся в heap. Переменная-ссылка не содержит полную копию объекта.

```text
stack потока обработки запроса             общий heap

transfer frame
from ───────────────────────────────────► Account { balance: ... }
to   ───────────────────────────────────► Account { balance: ... }
amount ─────────────────────────────────► BigDecimal { ... }
allowed = true
```

### Stack принадлежит потоку

Если сервер одновременно обрабатывает два HTTP-запроса в двух platform threads, у каждого запроса свой набор frames
и локальных переменных. Но обе цепочки вызовов могут иметь ссылки на один `Account` в общем heap. Из этого и возникает
проблема конкурентного доступа: локальные переменные изолированы, mutable object — нет.

```text
thread A stack ──► Account { balance: 1000 } ◄── thread B stack
                              общий heap
```

Само разделение stack не делает операции над общим объектом атомарными. Правила видимости и синхронизации будут
подробно рассмотрены в неделе 14 про concurrency.

### Stack trace — это снимок цепочки frames

```text
java.lang.IllegalStateException: insufficient funds
    at wallet.Account.withdraw(Account.java:42)
    at wallet.TransferService.transfer(TransferService.java:31)
    at wallet.TransferController.create(TransferController.java:18)
```

Верхняя строка после сообщения — место, где создано исключение. Ниже — вызывавшие методы. Это не «дамп всего heap»,
а представление текущего stack конкретного потока.

### Переполнение stack

Бесконечная или слишком глубокая рекурсия создаёт всё новые frames, пока не исчерпает stack данного потока:

```java
static void retryForever() {
    retryForever();
}
```

Результат обычно — `StackOverflowError`. Это отличается от нехватки heap: увеличить `-Xmx` здесь обычно не поможет.
Размер stack platform thread можно настроить опцией `-Xss`, но в прикладном коде прежде нужно устранить бесконтрольную
рекурсию или чрезмерную глубину вызовов.

> Важно: «локальная переменная всегда на stack» — учебное упрощение. JIT может держать значение в регистре процессора,
> убрать ненужную переменную или устранить выделение объекта. Для чтения и проектирования кода достаточно модели
> «локальные данные принадлежат вызову метода, объекты имеют управляемое время жизни».

## 3. Heap: объекты и их общий жизненный цикл

**Heap** — область JVM для объектов и массивов, обычно общая для всех потоков. Типичные примеры:

```java
Account account = new Account(...);       // объект Account
List<LedgerEntry> entries = new ArrayList<>(); // ArrayList и внутренний массив
byte[] payload = new byte[8192];          // массив
```

Оператор `new` создаёт объект, а результатом выражения становится ссылка. Несколько ссылок способны вести к одному
объекту:

```java
Account primary = new Account(...);
Account alias = primary;
```

После этого изменение через `alias` наблюдается через `primary`: создан не второй кошелёк, а вторая ссылка.

### Объект живёт, пока достижим

Освобождением heap управляет **garbage collector (GC)**. Он не ориентируется на текстовую область видимости переменной
и не имеет счётчика «сколько ссылок написано в коде». Он начинает обход от *GC roots* — точек, которые JVM считает
живыми: например, от активных stack frames потоков, статических полей загруженных классов и внутренних ссылок JVM.

Если по цепочке ссылок от корней объект достижим, он нужен программе. Если недостижим, GC может освободить его память
в удобный ему момент.

```java
static Account cached; // ссылка из static field может удерживать объект всё время жизни класса

static void example() {
    Account temporary = new Account(...);
    // после последнего фактического использования temporary объект может стать недостижим
}
```

Следствия:

- окончание метода часто убирает его ссылки из stack, но объект может быть достижим из другого места;
- `null` лишь удаляет одну ссылку; объект не исчезнет, если есть другие;
- `System.gc()` — только просьба JVM, а не способ немедленно очистить память;
- `finalize()` устарел и для управления ресурсами не используется; файл, соединение и транзакцию закрывают явно через
  `try-with-resources`.

### Почему возможен `OutOfMemoryError`

Когда JVM не может выделить место под новый объект в допустимом heap после необходимых попыток GC, возможен
`OutOfMemoryError: Java heap space`. Частая причина в backend-коде — не «GC не сработал», а ненужные живые ссылки:

- кэш без лимита и стратегии вытеснения;
- загрузка всей истории операций вместо пагинации;
- накопление больших ответов, файлов или логов в `List`;
- static map, из которой записи никогда не удаляются;
- listener, удерживающий объекты дольше ожидаемого.

Увеличение `-Xmx` может отсрочить ошибку, но не исправляет утечку. Нужны heap dump и поиск цепочки ссылок, которая
удерживает объект. Не каждый `OutOfMemoryError` означает нехватку heap: бывают также ошибки metaspace или native memory.

## 4. Где находятся классы, static-поля и metaspace

Heap и stack не исчерпывают память JVM. Когда class loader загружает `Account`, JVM хранит сведения о классе:
имя, методы, поля, константный пул class-файла и прочие метаданные. В современной HotSpot эти метаданные располагаются
в **metaspace**, который использует native memory процесса, а не обычный Java heap.

Static-поле относится к классу, а не к экземпляру. Его значение логически живёт вместе с загруженным классом. Если
static-поле хранит ссылку, объект, на который она указывает, остаётся в heap и обычно достижим как от GC root.

```java
public final class CurrencyCatalog {
    private static final Map<String, Currency> BY_CODE = new HashMap<>();
}
```

`BY_CODE` — статическое поле класса; сама `HashMap`, ключи и значения — объекты. Поэтому кэш в static-поле обязан иметь
ограничение и понятный жизненный цикл.

Для повседневной разработки не нужно вручную распределять объекты между областями. Важнее понимать границы: heap —
не вся память процесса, а static cache может удерживать heap-объекты очень долго.

## 5. String pool: общий набор канонических строк

`String` — immutable object: после создания его содержимое нельзя изменить. Это позволяет JVM безопасно переиспользовать
один экземпляр для одинаковых строк. Для этого существует **string pool** — таблица канонических строк.

В современных HotSpot JVM строковый пул находится в heap. Не стоит запоминать старые схемы из учебников, где его
показывают как отдельную «permanent generation»: в Java 8 permanent generation удалена, а для Java 21 это неверная
модель.

### Литералы попадают в пул

Строковые литералы, записанные в коде, JVM канонизирует:

```java
String first = "RUB";
String second = "RUB";

System.out.println(first == second); // true: обычно одна и та же pooled string
```

При загрузке и связывании классов JVM получает запись о литерале из class-файла и находит существующий канонический
экземпляр или создаёт его. Затем обе переменные получают ссылку на него. Это оптимизация памяти и частично скорости,
но не контракт сравнения строк.

### `new String` принудительно создаёт отдельный объект

```java
String pooled = "RUB";
String separate = new String("RUB");

System.out.println(pooled == separate);      // false
System.out.println(pooled.equals(separate)); // true
```

Содержимое одинаково, но identity объектов разная. Для проверки содержания всегда применяй `equals`; безопасный для
`null` шаблон — `"RUB".equals(currency)`.

### Строка, созданная во время выполнения

```java
String prefix = "RU";
String code = prefix + "B";
```

Если compiler способен вычислить выражение целиком из compile-time constants, он обычно превратит его в литерал `"RUB"`.
Но когда значение приходит из аргумента, файла, HTTP-запроса или базы данных, обычная новая строка автоматически не
становится pooled:

```java
String fromRequest = request.currency();
String literal = "RUB";

System.out.println(fromRequest == literal); // не использовать: обычно false, контракт не гарантирует true
```

### `intern()` ищет или добавляет канонический экземпляр

Метод `intern()` возвращает представителя строки из pool:

```java
String fromRequest = new String("RUB");
String canonical = fromRequest.intern();

System.out.println(canonical == "RUB"); // true
```

Если эквивалентная строка уже есть в pool, `intern()` возвращает её ссылку. Иначе текущая строка становится
канонической и возвращается её ссылка. Это не делает `==` подходящим для обычного сравнения: другие источники строки,
будущие изменения кода и отсутствие `intern()` легко нарушат такое предположение.

`intern()` уместен редко: например, после измерений для небольшого, контролируемого множества повторяющихся значений.
Нельзя бездумно интернировать неограниченные пользовательские значения, например UUID, поисковые фразы или тело
запроса: pool будет удерживать много уникальных строк и увеличит расход heap.

### Что именно хранится у `String`

С точки зрения языка строка — объект. Конкретное внутреннее представление (`byte[]`, кодировка, заголовок объекта,
сжатые строки) — деталь версии JVM. В Java 9+ HotSpot может хранить строки Latin-1 компактнее UTF-16, но код не
должен зависеть от этого. Для оценки памяти используют профилировщик, а не формулу из старого учебника.

## 6. Как связать модель с Wallet Service

Представь обработку `POST /transfers`:

```text
HTTP worker stack
TransferController.create(request)
        │ request, service, local variables — ссылки и примитивы данного вызова
        ▼
heap
TransferRequest, Account, BigDecimal, LedgerEntry, списки и JSON-буферы
        │
        ▼
после ответа
локальные ссылки исчезают, но сохранённые сущности, кэш или очередь могут
удерживать связанные объекты
```

Практические выводы:

- не загружай всю историю `LedgerEntry` в `List`: API требует пагинацию, а heap конечен;
- не сохраняй `TransferRequest` или JWT в static-коллекции «для отладки»;
- `String` с валютой сравнивают через `equals`, а для фиксированного набора валют лучше `enum Currency`;
- стек одного запроса не общий с другим, но два запроса могут менять один `Account` в heap — это задача транзакций и
  синхронизации, а не GC;
- закрывай JDBC-ресурсы и HTTP-ответы через `try-with-resources`: GC не является своевременным механизмом закрытия.

## 7. Практика: увидеть ссылки и pool в debugger

Создай и запусти программу:

```java
public class MemoryDemo {
    public static void main(String[] args) {
        String literalFirst = "RUB";
        String literalSecond = "RUB";
        String separate = new String("RUB");
        String runtime = args.length == 0 ? "RUB" : args[0];

        System.out.println(literalFirst == literalSecond);
        System.out.println(literalFirst == separate);
        System.out.println(literalFirst.equals(separate));
        System.out.println(runtime == literalFirst);
        System.out.println(runtime.equals(literalFirst));
    }
}
```

Запусти дважды:

```shell
javac --release 21 MemoryDemo.java
java MemoryDemo
java MemoryDemo RUB
```

Во втором запуске `RUB` приходит как аргумент командной строки, поэтому не следует ожидать от `runtime == literalFirst`
стабильного `true`. Затем:

1. поставь breakpoint перед первым `println`;
2. в IntelliJ IDEA раскрой значения трёх переменных и сравни identity объектов;
3. открой Call Stack: увидишь frame `main`;
4. добавь метод `inspect(String value)` и вызови его, чтобы увидеть второй frame;
5. объясни, почему `literalFirst` и `literalSecond` могут иметь одну identity, а `separate` — нет.

Дополнительное задание: создай `List<String>` из миллиона уникальных строк, измерь поведение с ограниченным `-Xmx`,
после чего удали список из программы. Не фиксируй точный размер, при котором произойдёт ошибка: он зависит от JVM,
платформы и настроек. Зафиксируй только причину: объекты остаются достижимыми через список.

## Краткий итог

- JVM работает внутри процесса ОС и использует виртуальную и физическую память как обычная программа.
- Stack принадлежит отдельному потоку и хранит контекст вызовов; heap обычно общий и хранит объекты и массивы.
- Объект остаётся живым, пока достижим от GC roots; завершение метода само по себе не гарантирует немедленного удаления.
- `-Xmx` ограничивает heap, но не всю память Java-процесса.
- В Java 21 string pool расположен в heap; одинаковые литералы могут ссылаться на один объект.
- Содержание строк сравнивают через `equals`, а не через `==`; `intern()` — узкая оптимизация, а не правило прикладного кода.
