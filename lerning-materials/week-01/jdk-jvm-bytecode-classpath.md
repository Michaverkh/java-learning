# JDK, JVM, bytecode и classpath

[← Вернуться к учебному плану](java-backend-learning-plan.md)

## Главная модель

Java-программа обычно проходит такой путь:

```text
исходный код (.java)
        │
        │ javac
        ▼
байткод (.class)
        │
        │ java запускает JVM
        ▼
Class Loader → проверка байткода → интерпретация/JIT-компиляция
        │
        ▼
машинный код, выполняемый процессором
```

Коротко:

- **JDK** — набор инструментов для разработки Java-программ;
- **JVM** — виртуальная машина, внутри которой выполняется программа;
- **bytecode** — промежуточные инструкции JVM в файлах `.class`;
- **classpath** — список мест, где Java ищет пользовательские классы и библиотеки.

Полезная аналогия для TypeScript-разработчика:

| Java                 | Приблизительная аналогия в TypeScript/Node.js                                           |
|---                   |---                                                                                      |
| `.java`              | `.ts`                                                                                   |
| `javac`              | `tsc`                                                                                   |
| `.class` с байткодом | скомпилированный `.js`, но для JVM, а не текстовый JavaScript                           |
| JVM                  | среда выполнения вроде Node.js/V8, хотя архитектура и формат кода отличаются            |
| classpath            | пути, по которым runtime ищет код и зависимости; отдалённо напоминает module resolution |
| JAR                  | архив с классами и ресурсами, похожий по роли на публикуемый пакет                      |

Аналогия помогает получить первое представление, но не является точным соответствием.

## JDK

**JDK (Java Development Kit)** содержит всё необходимое для разработки:

- компилятор `javac`;
- команду запуска `java`;
- стандартную библиотеку Java;
- JVM;
- инструменты диагностики и упаковки, например `javadoc`, `jar`, `javap`, `jcmd`, `jstack`.

Проверить установленную версию:

```shell
java -version
javac -version
```

Важно различать:

- `java` запускает приложение;
- `javac` компилирует исходный код;
- JDK включает JVM, но JVM не является всем JDK.

Исторически отдельно распространялся **JRE (Java Runtime Environment)** — среда только для запуска. В современной разработке обычно устанавливают JDK, а для доставки приложения при необходимости создают минимальный runtime-образ.

### Что такое `javac`

`javac` (**Java compiler**) — компилятор языка Java, входящий в состав JDK. Он проверяет исходный код и преобразует файлы `.java` в файлы `.class`, содержащие байткод JVM:

```text
Hello.java
    │ javac
    ▼
Hello.class
```

Например, файл `Hello.java`:

```java
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello!");
    }
}
```

Компиляция:

```shell
javac Hello.java
```

После успешной компиляции рядом появится `Hello.class`. Запускается он уже другой командой:

```shell
java Hello
```

Разница между командами:

- `javac` компилирует исходный код;
- `java` запускает JVM, которая загружает и исполняет полученный байткод;
- `javac` создаёт не машинный код конкретного процессора, а переносимый байткод JVM.

Для TypeScript-разработчика ближайшая аналогия — `tsc`, однако результат отличается: `tsc` обычно создаёт текстовый JavaScript, а `javac` — бинарный `.class` для JVM.

Часто каталог для результата задают явно:

```shell
javac -d out src/demo/Hello.java
```

Параметр `-d out` указывает, куда записать скомпилированные `.class`-файлы с учётом структуры их пакетов.

## JVM

**JVM (Java Virtual Machine)** — спецификация виртуальной машины и её конкретная реализация. Например, HotSpot — распространённая реализация JVM.

При запуске приложения JVM:

1. создаёт процесс и настраивает память;
2. загружает необходимые классы;
3. проверяет корректность байткода;
4. выполняет байткод;
5. управляет памятью и сборкой мусора;
6. управляет потоками и взаимодействует с операционной системой.

Одна из причин переносимости Java: один и тот же совместимый байткод можно запускать на JVM для Windows, Linux или macOS. При этом сама JVM является платформозависимой программой.

### Интерпретатор и JIT

JVM может сначала интерпретировать байткод, а часто выполняемые участки затем компилировать в машинный код с помощью **JIT (Just-In-Time compiler)**. Поэтому не совсем верно говорить, что Java «только интерпретируется» или «сразу компилируется в машинный код».

Упрощённо:

```text
bytecode → интерпретация → сбор статистики → JIT → оптимизированный машинный код
```

## Bytecode

**Байткод** — набор инструкций для JVM. Обычно компилятор создаёт один `.class` для каждого объявленного класса, интерфейса, record или enum, а также дополнительные `.class` для некоторых вложенных и анонимных классов.

Пример:

```java
package demo;

public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello, JVM!");
    }
}
```

Если файл лежит в `src/demo/Hello.java`, скомпилировать его можно так:

```shell
javac -d out src/demo/Hello.java
```

Результат:

```text
out/
└── demo/
    └── Hello.class
```

Посмотреть байткод в читаемом виде:

```shell
javap -c -p out/demo/Hello.class
```

В `.class` хранится не исходный Java-код, а структура класса и инструкции JVM. Имена классов и методов обычно остаются доступными, поэтому байткод нередко можно декомпилировать в код, похожий на исходный.

### Совместимость версий

Файл `.class` содержит номер версии формата. Старая JVM не обязана понимать байткод, созданный новым JDK. Типичная ошибка:

```text
UnsupportedClassVersionError
```

Она означает: приложение или библиотека скомпилированы для более новой версии Java, чем версия JVM, на которой их пытаются запустить.

Для компиляции под заданную версию платформы используют, например:

```shell
javac --release 21 -d out src/demo/Hello.java
```

## Classpath

**Classpath** сообщает компилятору и JVM, где искать классы и ресурсы приложения. Его элементами могут быть:

- каталоги с `.class`-файлами;
- JAR-файлы;
- несколько каталогов и JAR-файлов одновременно.

Classpath не является списком имён классов. Это список **корней**, относительно которых ищутся пути, соответствующие полным именам классов.

Для класса:

```java
package demo;

public class Hello { }
```

ожидаемый путь внутри одного из корней classpath:

```text
demo/Hello.class
```

Если файл расположен по пути `out/demo/Hello.class`, в classpath нужно добавить `out`, а не `out/demo` и не сам `Hello.class`.

### Запуск класса

```shell
java -cp out demo.Hello
```

Здесь:

- `-cp out` задаёт корень classpath;
- `demo.Hello` — полное имя класса;
- для запуска у класса должен быть подходящий метод `public static void main(String[] args)`.

Расширенная форма `-classpath` эквивалентна `-cp`.

### Несколько элементов

Разделитель classpath зависит от операционной системы:

- Windows — `;`;
- Linux и macOS — `:`.

Windows:

```shell
java -cp "out;lib/example.jar" demo.Hello
```

Linux/macOS:

```shell
java -cp "out:lib/example.jar" demo.Hello
```

Кавычки полезны, если в пути есть пробелы или shell особым образом обрабатывает символы.

### Compile classpath и runtime classpath

Classpath нужен на двух разных этапах:

1. **Compile classpath** — `javac` ищет классы, необходимые для проверки и компиляции кода.
2. **Runtime classpath** — JVM ищет классы, необходимые во время выполнения.

Пример компиляции с библиотекой:

```shell
javac -cp "lib/example.jar" -d out src/demo/Hello.java
```

Пример запуска:

```shell
java -cp "out;lib/example.jar" demo.Hello
```

Успешная компиляция не гарантирует успешный запуск. Если зависимость была доступна компилятору, но отсутствует в runtime classpath, приложение завершится ошибкой загрузки класса.

Maven и Gradle обычно формируют classpath автоматически из объявленных зависимостей. Понимание механизма всё равно необходимо для разбора конфликтов версий, ошибок запуска, тестовых зависимостей и содержимого JAR.

## Package, import и classpath — не одно и то же

- `package demo;` задаёт полное имя класса и ожидаемую структуру каталогов;
- `import example.Widget;` позволяет использовать короткое имя `Widget` в исходном коде;
- classpath определяет, где компилятор или JVM будут искать `example/Widget.class`.

`import` не загружает библиотеку и не добавляет её в classpath.

## Как JVM находит класс

Упрощённый процесс загрузки:

1. JVM получает полное имя класса, например `demo.Hello`.
2. Class Loader преобразует его в путь `demo/Hello.class`.
3. Ищет этот путь в доступных источниках классов.
4. Загружает байты класса.
5. JVM проверяет, связывает и инициализирует класс.

В Java есть несколько загрузчиков классов. Основные классы платформы и классы приложения загружаются разными загрузчиками. В обычном приложении достаточно понимать общую идею; детали становятся важны в контейнерах, системах плагинов, application servers и при сложных конфликтах зависимостей.

## JAR

**JAR (Java Archive)** — ZIP-архив со скомпилированными классами, ресурсами и служебными метаданными в `META-INF`.

Создать JAR:

```shell
jar --create --file hello.jar -C out .
```

Если в манифесте указан `Main-Class`, исполняемый JAR можно запустить:

```shell
java -jar hello.jar
```

При использовании `-jar` JVM берёт точку входа и настройки classpath из манифеста JAR; обычный аргумент `-cp` в таком запуске не используется для добавления зависимостей. Build-инструменты решают это разными способами: формируют classpath, создают дистрибутив с библиотеками или собирают fat/uber JAR.

## Частые ошибки

### `ClassNotFoundException`

Код явно попытался динамически загрузить класс, но загрузчик не нашёл его. Частая причина — отсутствующий JAR или неверный runtime classpath.

### `NoClassDefFoundError`

Во время выполнения JVM не смогла получить определение класса, которое ранее ожидалось доступным. Возможные причины:

- зависимость отсутствует в runtime classpath;
- не загрузилась транзитивная зависимость;
- завершилась ошибкой статическая инициализация класса.

### `NoSuchMethodError`

Класс найден, но во время выполнения в нём нет метода с ожидаемой сигнатурой. Обычно код компилировался с одной версией библиотеки, а запускается с другой.

### `Could not find or load main class`

Обычно нужно проверить:

- указано ли полное имя класса вместе с package;
- является ли classpath корнем над каталогом package;
- действительно ли `.class` был создан;
- нет ли опечатки или неверного разделителя путей.

## Сквозной пример без Maven и Gradle

Структура:

```text
example/
└── src/
    └── demo/
        └── Hello.java
```

Содержимое `Hello.java`:

```java
package demo;

public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello, JVM!");
    }
}
```

Из каталога `example`:

```shell
javac -d out src/demo/Hello.java
java -cp out demo.Hello
javap -c -p out/demo/Hello.class
jar --create --file hello.jar -C out .
jar --list --file hello.jar
```

Этот пример показывает всю цепочку:

```text
Hello.java
   │ javac
   ▼
out/demo/Hello.class
   │ java -cp out demo.Hello
   ▼
JVM загружает demo/Hello.class и выполняет main
```

## Что важно запомнить

1. JDK нужен для разработки и содержит JVM и инструменты.
2. `javac` превращает `.java` в `.class`.
3. `.class` содержит платформонезависимый байткод JVM.
4. JVM загружает, проверяет и выполняет байткод, в том числе с помощью JIT.
5. Classpath — набор корней каталогов и JAR-файлов для поиска классов и ресурсов.
6. Полное имя `demo.Hello` соответствует пути `demo/Hello.class` внутри корня classpath.
7. Compile classpath и runtime classpath могут отличаться.
8. Большинство ошибок загрузки классов связано с отсутствующей или несовместимой runtime-зависимостью.
