# IoC, DI и Spring Context

[← Вернуться к учебному плану](../java-backend-learning-plan.md) · [Технические требования Wallet Service](../projects/wallet-service/technical-requirements.md)

## Цель

На этой неделе нужно понять, как Spring создаёт объекты приложения, связывает их между собой и управляет их жизнью. После
изучения материала должно быть возможно собрать небольшую часть Wallet Service без Spring, затем перенести создание
объектов в Spring-контейнер и объяснить, почему выбран именно такой способ регистрации каждой зависимости.

Spring на этом этапе не заменяет проектирование. Доменная модель и правила перевода остаются обычным Java-кодом; Spring
отвечает главным образом за сборку объектов и инфраструктурные возможности вокруг них.

## Карта темы

```text
IoC
 └── DI
      ├── constructor injection
      └── зависимости видны в конструкторе

ApplicationContext
 ├── создаёт и хранит beans
 ├── находит компоненты через component scanning
 ├── читает @Configuration и @Bean
 └── управляет lifecycle и scope

Reflection и proxy
 ├── позволяют Spring анализировать классы во время запуска
 └── добавляют инфраструктурное поведение вокруг вызова метода
```

## 1. Инверсия управления и внедрение зависимостей

### Что означает IoC

В обычной программе класс сам выбирает конкретные реализации и создаёт их через `new`. Например, сервис перевода может
сам создать репозиторий и генератор идентификаторов. Такой подход удобен в коротком примере, но класс начинает отвечать
и за бизнес-правила, и за сборку приложения.

```java
public final class TransferService {
    private final InMemoryAccountRepository accountRepository = new InMemoryAccountRepository();
    private final UuidGenerator idGenerator = new UuidGenerator();

    // Правила перевода...
}
```

При таком устройстве трудно заменить хранилище, например на PostgreSQL, или передать тестовый генератор идентификаторов.
Кроме того, `TransferService` жёстко зависит от конкретных классов, а не от контрактов.

**Inversion of Control (IoC)** — принцип, при котором создание объектов и управление их связями передаётся внешнему
механизму. В Spring этим механизмом будет контейнер. Сам принцип не требует Spring: объекты можно собрать вручную в
точке входа программы.

```java
public static void main(String[] args) {
    AccountRepository repository = new InMemoryAccountRepository();
    Clock clock = Clock.systemUTC();
    TransferService transferService = new TransferService(repository, clock);
}
```

Здесь `TransferService` больше не контролирует создание зависимостей. Это уже IoC: внешний код решает, какие объекты
передать сервису.

### DI как частный способ реализовать IoC

**Dependency injection (DI)** — передача объекту зависимостей извне. Зависимость — объект, без которого класс не может
выполнить свою задачу: репозиторий, `Clock`, клиент внешнего сервиса, отправитель событий.

Для учебного Wallet Service зависимости `TransferService` могут быть такими:

| Зависимость | Зачем нужна | Почему это контракт |
|---|---|---|
| `AccountRepository` | найти и сохранить кошельки | позднее in-memory реализацию заменит доступ к БД |
| `TransferRepository` | сохранить перевод | способ хранения не должен менять бизнес-логику |
| `Clock` | записать текущее время | в тесте нужно фиксированное время |
| `UuidGenerator` | создать публичные идентификаторы | в тесте полезны предсказуемые идентификаторы |

Не всякое поле является зависимостью. `BigDecimal.ZERO`, локальная переменная или данные конкретного перевода не
передаются через DI: это значения, а не отдельные сервисы.

### Constructor injection

Предпочтительный способ DI в Java и Spring — передать обязательные зависимости в конструктор.

```java
public final class TransferService {
    private final AccountRepository accountRepository;
    private final TransferRepository transferRepository;
    private final Clock clock;

    public TransferService(
            AccountRepository accountRepository,
            TransferRepository transferRepository,
            Clock clock
    ) {
        this.accountRepository = accountRepository;
        this.transferRepository = transferRepository;
        this.clock = clock;
    }
}
```

Преимущества такого подхода:

- объект нельзя создать в неполном или некорректном состоянии;
- список зависимостей виден в API класса, а не скрыт в полях;
- поля могут быть `final`;
- класс легко создать в unit-тесте без Spring;
- циклическая зависимость становится заметной сразу.

Если у класса один конструктор, в современном Spring аннотация `@Autowired` не нужна: контейнер сам выберет его. Если
конструкторов несколько, выбор следует сделать явным или, что обычно лучше, упростить дизайн класса.

### Почему не field injection

Field injection выглядит так:

```java
@Service
public class TransferService {
    @Autowired
    private AccountRepository accountRepository;
}
```

У этого способа несколько проблем: поле нельзя сделать `final`, зависимость не видна из конструктора, а обычный
unit-тест вынужден использовать reflection или запускать Spring только ради создания класса. Также можно случайно
получить объект без заполненного поля, если создать его через `new`.

Setter injection допустим для редкой необязательной настройки, которую можно безопасно изменить после создания
объекта. Для обязательных зависимостей Wallet Service его использовать не следует.

## 2. Beans и `ApplicationContext`

### Bean

**Bean** — объект, который создаёт, настраивает и хранит Spring-контейнер. Он не является особым видом Java-объекта:
`TransferService`, `Clock` и `DataSource` остаются обычными объектами. Разница только в том, кто отвечает за их
создание и жизненный цикл.

Не нужно делать bean каждый класс. Значения запроса, DTO, доменные сущности `Account` и `Transfer` обычно создаются
прикладным кодом и не должны быть singleton-beans. Bean разумен, когда объект представляет сервис, адаптер,
конфигурацию или инфраструктурную зависимость, которые нужно переиспользовать и связать с другими объектами.

### `ApplicationContext`

`ApplicationContext` — основной Spring-контейнер. При запуске приложения он:

1. получает определения beans из аннотаций и конфигурации;
2. строит граф зависимостей;
3. создаёт beans в нужном порядке;
4. внедряет зависимости через конструкторы;
5. выполняет этапы инициализации;
6. при завершении приложения уничтожает beans, которым это необходимо.

Для наглядности граф маленького модуля переводов можно представить так:

```text
TransferController
        │
        ▼
TransferService ──► AccountRepository ──► InMemoryAccountRepository
        │
        ├──────────► TransferRepository ─► InMemoryTransferRepository
        │
        └──────────► Clock
```

Контейнер знает не только объекты, но и их зависимости. Поэтому он может создать репозитории до `TransferService`, а
его — до контроллера. В прикладном коде не нужно вызывать `context.getBean(...)`: это переносит обязанность сборки
объектов обратно в бизнес-логику. Получение bean из контекста допустимо в инфраструктурной точке входа или редких
интеграционных сценариях, но не в domain/application service.

## 3. Регистрация beans

Spring должен сначала узнать, какие объекты нужно создать. Для этого есть два главных пути: component scanning и
явная Java-конфигурация.

### `@Component` и component scanning

`@Component` помечает класс как кандидат на регистрацию. При component scanning Spring ищет такие классы в пакетах,
которые входят в область сканирования, и создаёт для них определения beans.

```java
@Component
public final class InMemoryAccountRepository implements AccountRepository {
    // ...
}
```

`@Service` и `@Repository` — специализированные варианты `@Component`.

| Аннотация | Когда применять | Практический смысл |
|---|---|---|
| `@Component` | технический компонент без более точной роли | например, `UuidGenerator` |
| `@Service` | application service с бизнес-сценарием | например, `TransferService` |
| `@Repository` | адаптер доступа к данным | например, `InMemoryAccountRepository` |

Для `@Service` и `@Component` разница главным образом семантическая: код легче читать и поддерживать. `@Repository`
также выражает границу persistence-слоя; Spring может применить к нему преобразование исключений доступа к данным.

Корневой класс Spring Boot с `@SpringBootApplication` обычно располагают в верхнем пакете приложения. Эта аннотация
включает component scanning для своего пакета и вложенных пакетов. Например, если главный класс лежит в
`com.example.wallet`, то `com.example.wallet.transfers` будет найден, а `com.example.shared` — нет. Структуру пакетов
стоит проектировать осознанно, а не расширять сканирование на весь `com.example` без причины.

### `@Configuration` и `@Bean`

Иногда исходный класс нельзя аннотировать: он принадлежит JDK или внешней библиотеке. Иногда важен способ создания
объекта. В этих случаях используется класс конфигурации и метод с `@Bean`.

```java
@Configuration
public class TimeConfiguration {

    @Bean
    Clock clock() {
        return Clock.systemUTC();
    }
}
```

У метода `@Bean` могут быть параметры. Spring разрешит их как зависимости, поэтому связывание остаётся явным:

```java
@Configuration
public class TransferConfiguration {

    @Bean
    TransferService transferService(
            AccountRepository accountRepository,
            TransferRepository transferRepository,
            Clock clock
    ) {
        return new TransferService(accountRepository, transferRepository, clock);
    }
}
```

В реальном приложении обычно выбирают один из вариантов, а не регистрируют один и тот же `TransferService` одновременно
через `@Service` и `@Bean`. Иначе контейнер увидит два кандидата одного типа и не сможет однозначно выполнить внедрение.

Практическое правило:

- собственные application services и адаптеры — обычно через `@Service`, `@Repository`, `@Component`;
- классы JDK, внешних библиотек и объекты с нестандартным созданием — через `@Bean` в `@Configuration`;
- если для одного контракта действительно нужны несколько реализаций, выбор оформляется явно через `@Qualifier` или
  `@Primary`; на этой неделе лучше сначала избежать такой сложности.

## 4. Жизненный цикл и scopes

### Жизненный цикл

Упрощённая последовательность для singleton-bean:

```text
создание объекта → constructor injection → инициализация → готов к работе → уничтожение при закрытии контекста
```

Для очистки ресурса можно использовать `@PreDestroy` или указать метод уничтожения у `@Bean`. Это важно для объектов,
которые держат ресурс: соединение, поток обработки, сетевой клиент. Не следует добавлять lifecycle-методы в обычную
доменную модель только потому, что она используется приложением.

```java
@Component
public class ReportExportClient {

    @PreDestroy
    void close() {
        // Освободить ресурс, если клиент действительно владеет им.
    }
}
```

### Scope

Scope определяет, сколько экземпляров bean создаёт контейнер и как долго они существуют.

| Scope | Экземпляры | Типичное применение | Важное ограничение |
|---|---|---|---|
| `singleton` | один на `ApplicationContext` | stateless services, репозитории, клиенты | объект разделён между запросами |
| `prototype` | новый при каждом запросе из контейнера | редкие короткоживущие объекты | контейнер не управляет полным уничтожением экземпляра |
| `request` | один на HTTP-запрос | данные контекста запроса | доступен только в web-приложении |
| `session` | один на HTTP-сессию | состояние пользовательской сессии | обычно не нужен в stateless REST API |

По умолчанию Spring-bean имеет scope `singleton`. Это не паттерн Singleton из учебника в точном смысле: экземпляр один
не на всю JVM, а на один `ApplicationContext`.

В Wallet Service `TransferService` и in-memory репозитории на этапе HTTP API будут singleton-beans. Поэтому у них не
должно быть изменяемого состояния, относящегося к одному запросу: нельзя хранить в поле текущий `clientId`, сумму или
временный результат перевода. Эти значения передаются аргументами методов и хранятся локально. Потокобезопасность
подробнее рассматривается на неделе 14.

## 5. Reflection и proxies: почему Spring может это сделать

### Reflection

Reflection — API Java, с помощью которого программа во время выполнения исследует классы: их аннотации, конструкторы,
методы и типы. Spring применяет reflection при старте, чтобы найти компоненты, выбрать конструктор и создать объект.

Reflection не означает, что бизнес-логику нужно писать через reflection. В Wallet Service она остаётся обычными
вызовами методов, которые компилятор может проверить. Reflection — инфраструктурный инструмент фреймворка.

### Proxy

Proxy — объект-обёртка, который выглядит для вызывающего кода как исходный сервис, но может выполнить дополнительную
работу до и после вызова метода.

```text
Controller → proxy TransferService → настоящий TransferService
                │
                ├─ начать транзакцию
                ├─ вызвать transfer(...)
                ├─ зафиксировать или откатить транзакцию
                └─ вернуть результат или пробросить исключение
```

На неделе 5 это только модель. На неделе 13 она станет практической: Spring обычно реализует `@Transactional` через
proxy. Тем же принципом могут работать безопасность, кэширование и другие сквозные возможности.

Из этого вытекает важное ограничение — **self-invocation**. Если один метод объекта вызывает другой метод того же
объекта через `this`, вызов не проходит через proxy. Следовательно, аннотация инфраструктурного поведения на внутреннем
методе может не сработать ожидаемым образом.

```java
@Service
public class TransferService {

    public void handle(TransferCommand command) {
        execute(command); // Вызов не проходит через Spring proxy.
    }

    @Transactional
    public void execute(TransferCommand command) {
        // На неделе 13 будет видно, почему такая граница транзакции ненадёжна.
    }
}
```

Это не повод бороться с proxy техническими обходами. Обычно лучше определить корректную публичную границу сценария и
поместить аннотацию на метод, который вызывается из другого bean.

## Сквозная практика: собрать модуль переводов

Цель практики — не построить HTTP API и не реализовать транзакции раньше времени. Нужно собрать минимальную доменную
логику перевода, убедиться, что она работает без Spring, и только затем поручить Spring создание объектов.

### Шаг 1. Доменный MVP без Spring

Создайте обычные Java-классы для `Account`, `Transfer` и команды `TransferCommand`. Используйте `BigDecimal`, UUID и
UTC-время. Реализуйте сценарий перевода в `TransferService` с правилами из технических требований:

- сумма больше нуля и содержит не более двух знаков после запятой;
- исходный и целевой кошельки различаются;
- оба кошелька имеют статус `ACTIVE` и валюту `RUB`;
- после списания баланс неотрицательный;
- при успехе создаются две ledger-записи с противоположными знаками;
- сумма изменений балансов одного перевода равна нулю.

Определите контракты `AccountRepository`, `TransferRepository` и при необходимости `LedgerRepository`. Реализуйте
in-memory версии на коллекциях. В отдельной точке сборки создайте все объекты через `new` и передайте зависимости
конструктором.

### Шаг 2. Проверить независимость доменной логики

Напишите unit-тесты без запуска Spring. В тесты передавайте in-memory репозитории, `Clock.fixed(...)` и тестовый
генератор UUID. Проверьте успешный перевод, недостаток средств, несовпадение валюты и перевод в тот же кошелёк.

Критерий: `TransferService` можно создать одной строкой `new`, а ни один его класс не импортирует Spring-аннотацию.

### Шаг 3. Зарегистрировать инфраструктуру Spring

Добавьте Spring Boot в проект на следующем этапе учебного плана или в отдельном модуле. Зарегистрируйте:

- `TransferService` как `@Service`;
- in-memory реализации репозиториев как `@Repository`;
- `Clock.systemUTC()` через `@Bean` в `@Configuration`;
- генератор UUID как `@Component` или через `@Bean`.

Оставьте constructor injection. Не используйте field injection, ручной `getBean(...)` из сервисов и статические
глобальные хранилища.

### Шаг 4. Проверить сборку контекста

Напишите минимальный тест контекста, который получает `TransferService` через constructor injection тестового класса
или проверяет, что приложение запускается. Важно не подменять им unit-тесты бизнес-правил: этот тест подтверждает лишь
правильность регистрации и связывания beans.

### Шаг 5. Исследовать scope

Добавьте временный счётчик создания в один учебный bean и убедитесь, что при обычном singleton-scope он создаётся один
раз за контекст. Затем объясните, почему нельзя хранить в singleton-поле данные одного перевода. После эксперимента
удалите учебный счётчик: он не нужен в прикладном коде.

## Самопроверка

После недели нужно суметь ответить без заученных формулировок:

1. Чем IoC отличается от DI и почему ручная сборка объектов уже является IoC?
2. Почему `TransferService` не должен сам создавать `AccountRepository` через `new`?
3. Почему constructor injection предпочтительнее field injection?
4. Чем `@Service` отличается от `@Repository`, и когда нужен `@Bean`?
5. Что произойдёт, если две реализации одного интерфейса зарегистрированы как beans?
6. Почему singleton-bean не должен хранить состояние HTTP-запроса?
7. Зачем Spring использует reflection, а зачем proxy?
8. Почему вызов метода из того же объекта важен для будущего использования `@Transactional`?

## Что пока не нужно углублять

На этой неделе не требуется изучать AOP API, создавать собственные proxies, настраивать сложные scopes или строить
factory beans. Достаточно понимать причины появления этих механизмов и уметь собрать небольшой модуль приложения
без скрытых зависимостей. Транзакции, безопасность, кэширование и HTTP request scope будут рассмотрены в своих темах.
