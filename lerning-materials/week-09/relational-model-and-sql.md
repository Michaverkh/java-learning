До этого момента данные кошелька можно было хранить в Java-коллекциях. Теперь нужно описать их так, чтобы база могла
хранить связи, отклонять недопустимые значения и отвечать на вопросы сразу по множеству записей.

Главный навык недели — перед написанием SQL определить: **что означает одна строка результата, какие строки должны
попасть в него и какие правила база обязана сохранять при изменении данных**.

«запись журнала изменений баланса». Перевод создаёт две такие записи; пополнение и списание — по одной.

## 1. Реляционная модель и связи

### 1.1. Таблица — множество фактов одного вида

В таблице `account` одна строка описывает один счёт. Столбцы задают свойства: идентификатор, владелец, валюта,
баланс. Схема определяет их типы и ограничения. Строка `ledger_entry` описывает уже другой факт: отдельное изменение
баланса конкретного счёта.

Математическое отношение — множество кортежей. SQL имеет практические отличия: в результате запроса возможны повторы,
существует `NULL`, а порядок строк не задан без `ORDER BY`. Не стоит представлять таблицу как JavaScript-массив,
который навсегда сохраняет порядок добавления.

| Знакомое понятие         | Аналогия в SQL                  | Где аналогия заканчивается                           |
|--------------------------|---------------------------------|------------------------------------------------------|
| Объект с полями          | Строка с именованными столбцами | Связанные объекты обычно находятся в других таблицах |
| Тип TypeScript           | Типы столбцов                   | База проверяет значения при записи                   |
| `filter`                 | `WHERE`                         | SQL использует особые правила для `NULL`             |
| `map`                    | Выражения после `SELECT`        | Можно вычислять значения на основе нескольких таблиц |
| Группировка и `reduce`   | `GROUP BY` и агрегаты           | Расчёт выполняется в базе до передачи результата     |
| Ссылка по идентификатору | Внешний ключ                    | База может запрещать ссылку на отсутствующую строку  |

SQL декларативен: ты задаёшь нужный результат, а СУБД выбирает способ его получения. Запрос не означает, что база
загрузит все строки в память приложения и выполнит цепочку методов массива.

### 1.2. Кратность связей

В нашей модели:

```text
client   1 ─── 0..N account
account  1 ─── 0..N ledger_entry
account  1 ─── 0..N transfer (роль отправителя)
account  1 ─── 0..N transfer (роль получателя)
```

У клиента может не быть счетов. У каждого счёта ровно один существующий клиент: для этого нужны одновременно
`NOT NULL` и внешний ключ на `client`. У перевода два столбца, ссылающихся на одну таблицу `account`, но роли разные.

Связь «один к одному» обычно выражают внешним ключом с `UNIQUE`: одна родительская строка не может встречаться
в дочерней таблице несколько раз. Это ещё не обязывает каждого родителя иметь дочернюю строку.

Для «многие ко многим» нужна промежуточная таблица. Например, в отдельной модели совместного доступа это могли бы быть
`account_access(account_id, client_id)` с составным ключом. В требованиях кошелька один владелец, поэтому такую
таблицу в учебную схему не добавляем.

## 2. Ключи и ограничения

### 2.1. Чем отличаются PK, UNIQUE и FK

**Кандидатный ключ** — минимальный набор столбцов, однозначно определяющий строку. Из возможных ключей выбирают
один первичный — `PRIMARY KEY`, или PK. В `client` это UUID `id`; внешний `external_id` тоже должен быть уникальным,
но не выбран первичным ключом.

UUID — искусственный идентификатор без предметного смысла. `external_id` имеет смысл в интеграции с внешней системой.
Удобно ссылаться на клиента по собственному UUID: изменение внешнего идентификатора тогда не требует переписывать
все ссылки. Формат UUID сам по себе не заменяет ограничение уникальности в таблице.

**Внешний ключ**, `FOREIGN KEY`, или FK, требует существования связанной строки. Он не копирует её поля и
не подгружает объект автоматически. Для чтения полей связанной строки нужен запрос.

| Ограничение                         | Правило учебной модели                               |
|-------------------------------------|------------------------------------------------------|
| `PRIMARY KEY (id)`                  | Идентификатор заполнен и уникален                    |
| `NOT NULL`                          | Значение обязательно                                 |
| `UNIQUE (external_id)`              | Нет двух клиентов с одним внешним идентификатором    |
| `REFERENCES client (id)`            | Владелец счёта существует                            |
| `CHECK (balance >= 0)`              | Числовой баланс неотрицателен                        |
| `UNIQUE (operation_id, account_id)` | Одна операция не создаёт две записи для одного счёта |

Последнее ограничение **не** требует уникальности каждого столбца отдельно. Один перевод встречается в журнале
дважды, но на разных счетах. `UNIQUE(operation_id)` ошибочно запретил бы вторую половину перевода.

В PostgreSQL PK и `UNIQUE` создают уникальные индексы. FK не создаёт индекс на ссылающемся столбце автоматически.
Выбор дополнительных индексов разберём на неделе 12. См. [ограничения PostgreSQL](https://www.postgresql.org/docs/18/ddl-constraints.html).

### 2.2. Что происходит при удалении родителя

В учебной схеме используется `ON DELETE RESTRICT`: нельзя удалить клиента, на которого ссылается счёт, или счёт,
на который ссылается журнал. Для кошелька закрытие счёта означает смену статуса, а не стирание истории.

`CASCADE` удаляет зависимые строки автоматически; `SET NULL` снимает ссылку, если столбец допускает `NULL`.
Выбирать их нужно по смыслу связи. Для неизменяемой финансовой истории каскадное удаление было бы неверным решением.

### 2.3. Ограничение строки и правило денежной операции

Посмотри на два правила:

```sql
CHECK (source_account_id <> target_account_id)
CHECK (status <> 'CLOSED' OR balance = 0)
```

Оба проверяются по значениям одной строки. Второе читается так: «либо счёт не закрыт, либо его баланс равен нулю».
Но оно не запрещает переход из `CLOSED` обратно в `ACTIVE`: для такого решения нужно знать предыдущее состояние.

Теперь правило «у перевода ровно две записи журнала и их сумма равна нулю». Для него нужно проверить несколько строк.
Обычный `CHECK` этой задачи не решает. Наличие FK тоже не означает, что дочерние записи вообще созданы.

Для нашего проекта разделение ответственности выглядит так:

| Правило                                              | Где его обеспечивать                               |
|------------------------------------------------------|----------------------------------------------------|
| Положительная сумма, допустимый статус, разные счета | Ограничения строки плюс проверка входа             |
| Существование владельца и счетов                     | Внешние ключи                                      |
| Счета активны именно в момент выполнения перевода    | Прикладной сервис и защита конкурентного изменения |
| Две согласованные записи, оба баланса и событие      | Одна транзакция и корректная логика записи         |
| Журнал нельзя редактировать через приложение         | Доступные операции репозитория и права роли БД     |
| Повтор денежной команды не меняет баланс             | Полная схема идемпотентности                       |

Транзакция объединяет изменения, но сама не проверяет правильность их сумм. Запрос сверки обнаруживает уже возникшую
ошибку, но сам её не предотвращает. Это разные инструменты.

## 3. Нормализация на практическом уровне

### 3.1. Откуда возникает дублирование

Представим таблицу:

```text
account_id | client_id | client_name | external_id | balance
A1         | C1        | Анна        | customer-anna | 700.00
A3         | C1        | Анна        | customer-anna |   0.00
```

Имя и внешний идентификатор клиента повторяются для каждого счёта. При смене имени легко изменить только одну строку.
При удалении последнего счёта можно потерять сведения о клиенте. А для регистрации клиента без счёта пришлось бы
создавать неполную строку. Это аномалии изменения, удаления и вставки.

Функциональная зависимость `client_id → client_name` означает: одному значению `client_id` соответствует одно имя
в текущем состоянии данных. Она следует из предметной модели, а не из того, что в сегодняшней тестовой выборке
случайно нет повторов.

### 3.2. Первые три нормальные формы

#### Какую проблему решаем

В предыдущем примере имя Анны хранится в каждой строке её счёта. Если изменить имя только в одной строке,
в базе окажутся два разных имени одного клиента. **Нормализация — это организация таблиц, которая помогает
избежать такого дублирования фактов и связанных с ним ошибок.** Обычно мы разделяем одну таблицу на несколько
и связываем их идентификаторами.

**Нормальная форма — набор требований к устройству таблицы.** Фраза «таблица находится в третьей нормальной
форме» означает, что она удовлетворяет соответствующим требованиям, включая требования первых двух форм.
Это не команда SQL и не настройка базы: структуру выбирает разработчик.

Разберём три требования на примерах кошелька. Ниже — намеренно неудачные варианты хранения и их исправления.
Готовую учебную схему из раздела 4 переделывать по этим примерам не требуется: она уже разделена на таблицы.
Короткие идентификаторы `A1`, `C1`, `op-1` используем вместо UUID для читаемости.

#### Первая нормальная форма: отдельная запись для каждого элемента

Допустим, мы решили хранить историю прямо в строке счёта:

| account_id | operation_ids | amounts   |
|------------|---------------|-----------|
| A1         | op-1, op-2    | 1000, -300 |

Одна ячейка содержит список идентификаторов, другая — соответствующий список сумм. Чтобы найти списания,
придётся разбирать строки и сопоставлять элементы двух списков. Если один список изменили, а второй забыли,
связь суммы с операцией потеряется. Обычный внешний ключ также не проверит каждый идентификатор внутри строки.

**Что меняем:** убираем эти списки из `account` и создаём отдельную таблицу `ledger_entry` — журнал изменений
баланса. Каждая её строка описывает одно изменение баланса одного счёта:

| operation_id | account_id | amount |
|--------------|------------|--------|
| op-1         | A1         | 1000   |
| op-2         | A1         | -300   |
| op-2         | A2         | 300    |

Здесь `op-1` — пополнение, `op-2` — перевод. У перевода две строки: списание с `A1` и зачисление на `A2`.
Именно это означает «выносим операции в строки журнала»: сохраняем изменения баланса отдельными записями
в таблице. Это история денежных изменений, а не текстовые логи приложения.

Теперь для поиска списаний достаточно условия `amount < 0`. Для следующего изменения добавляем строку;
структура таблицы остаётся прежней.

**Правило 1NF:** в каждой ячейке одно значение выбранного типа, без вложенной таблицы или списка отдельных
фактов, которые здесь нужно обрабатывать по одному. Столбцы `operation1`, `operation2`, `operation3` тоже
неудачно моделируют историю: для четвёртой операции понадобится новый столбец. Им также предпочитаем отдельные строки.

«Одно значение» определяется смыслом данных: назначение платежа остаётся одним текстом, его не нужно делить
на слова. Наличие массивов и JSON в PostgreSQL не отменяет пользу отдельных строк для связей и ограничений.

#### Вторая нормальная форма: свойства счёта не повторяем в каждой записи журнала

Допустим, после предыдущего шага в журнал добавили ещё и владельца счёта:

| operation_id | account_id | amount | client_id |
|--------------|------------|--------|-----------|
| op-1         | A1         | 1000   | C1        |
| op-2         | A1         | -300   | C1        |
| op-2         | A2         | 300    | C2        |

В нашем примере строку однозначно определяет **пара `(operation_id, account_id)`**. Одного `operation_id`
недостаточно: перевод затрагивает два счёта. Одного `account_id` тоже недостаточно: у счёта много операций.
Такую пару называют составным ключом.

Теперь спросим, какие идентификаторы нужны, чтобы определить остальные значения:

- Для `amount` нужна вся пара: у одной операции суммы на разных счетах отличаются, а у одного счёта разные операции.
- Для `client_id` достаточно только `account_id`: владелец определяется счётом, номер операции здесь ни при чём.

Из-за этого владелец `A1` повторяется в каждой записи его истории. Можно случайно записать `C1` в одной строке
и `C2` в другой, хотя речь об одном счёте.

**Что меняем:** убираем `client_id` из журнала и храним его в таблице `account`, один раз на счёт:

```text
ledger_entry (operation_id, account_id, amount)
account      (id, client_id, ...)
```

Чтобы узнать владельца записи журнала, находим счёт по `account_id`, затем берём его `client_id`.
Здесь имеется в виду владелец счёта как текущее свойство, а не специально сохраняемый исторический снимок.

**Правило 2NF:** таблица уже удовлетворяет 1NF, и каждое поле вне ключей зависит от всего составного ключа,
а не только от его части. Проверять нужно все минимальные наборы столбцов, однозначно определяющие строку;
их называют кандидатными ключами. Если все такие ключи состоят из одного столбца, проблема зависимости
от части ключа не возникает. Добавление отдельного `id` не исправит дублирование владельца в этом примере:
пара `(operation_id, account_id)` всё ещё остаётся кандидатным ключом.

#### Третья нормальная форма: свойства клиента не повторяем в каждом его счёте

Теперь вернёмся к таблице счетов из раздела 3.1:

| account_id | client_id | client_name | balance |
|------------|-----------|-------------|---------|
| A1         | C1        | Анна        | 700     |
| A3         | C1        | Анна        | 0       |

Ключ здесь — `account_id`. Он состоит из одного столбца, поэтому проблемы с частью составного ключа нет.
Но имя всё равно повторяется: оно относится к клиенту, у которого может быть несколько счетов.

Зависимость получается цепочкой: по `account_id` узнаём `client_id`, а по `client_id` — имя клиента.
Именно её сокращённо записывают как `account_id → client_id → client_name`.

**Что меняем:** переносим имя и внешний идентификатор клиента в отдельную таблицу `client`.
В `account` сохраняем только ссылку на владельца:

Таблица `client`:

| id | name | external_id   |
|----|------|---------------|
| C1 | Анна | customer-anna |

Таблица `account`:

| id | client_id | balance |
|----|-----------|---------|
| A1 | C1        | 700     |
| A3 | C1        | 0       |

Теперь изменение имени затрагивает одну строку в `client`. Клиента можно зарегистрировать до открытия счёта,
а удаление счёта не удаляет сведения о клиенте. Повторение `C1` в счетах нормально: это ссылки на один факт,
а не несколько независимых копий имени. Для отображения имени рядом со счётом соединяем таблицы запросом.

**Практическое правило 3NF для таких таблиц:** таблица уже удовлетворяет 2NF; поля, не входящие в ключи,
не должны определяться ключом через другое поле, которое само не является ключом. В нашем примере
`client_id` не является ключом таблицы счетов, но определяет `client_name` — поэтому имя выносим.

Разница между шагами на этих примерах:

| Шаг | Проблема                                      | Что меняем                                           |
|-----|-----------------------------------------------|------------------------------------------------------|
| 1NF | История упакована в списки внутри строки счёта  | Каждое изменение баланса делаем отдельной строкой     |
| 2NF | Владелец счёта повторяется в записях журнала    | Храним владельца в `account`, в журнале — `account_id` |
| 3NF | Имя клиента повторяется в его счетах           | Храним имя в `client`, в счёте — `client_id`           |

Цель этих изменений — дать каждому факту подходящее место хранения и уменьшить число мест,
которые нужно согласованно обновлять. Нормализация сама по себе не обеспечивает правильность денежных переводов:
для этого по-прежнему нужны ограничения и транзакции.

### 3.3. Почему тогда мы храним balance и balance_after

`account.balance` вычисляется из полной истории журнала, если счёт открывается с нуля. Хранить текущее значение
удобно для денежных команд и быстрых проверок. Но теперь два представления одного состояния нужно согласованно менять.

Это осознанное хранение производных данных. Оно не обязательно нарушает 3NF каждой отдельной таблицы: нормальные формы
и согласованность вычисляемых значений — связанные, но разные вопросы.

`balance_after` фиксирует баланс после конкретной операции. Его нельзя незаметно «исправить», перезаписав историю.
При этом текущий порядок `created_at, id` не гарантирует реальный порядок конкурентных денежных операций: UUID
разрешает совпадения при сортировке, но не обозначает последовательность проводок. Для строгой последовательности
потребуется отдельное решение при изучении конкурентности.

## 4. Типы и учебная схема

### 4.1. Выбор типов

| PostgreSQL       | Данные кошелька                | Связь с Java и API                                        |
|------------------|--------------------------------|-----------------------------------------------------------|
| `uuid`           | Идентификаторы                 | `UUID` в Java, строка в JSON                              |
| `numeric(19, 2)` | Сумма и баланс                 | `BigDecimal`; точное десятичное значение                  |
| `text`           | Имя, описание, код статуса     | `String`; допустимые статусы ограничены `CHECK`           |
| `bigint`         | Версия счёта                   | `long`; одна колонка ещё не включает контроль конкуренции |
| `timestamptz`    | Момент создания или завершения | Момент времени; на уровне приложения обычно `Instant`     |

У `numeric(19, 2)` всего 19 десятичных цифр, две после точки: до 17 до точки. При записи `1.239` PostgreSQL округлит
значение до `1.24`. Поэтому этот тип **не заменяет** требование отклонять запрос с избыточной точностью. К моменту
выполнения `CHECK` значение уже приведено к типу столбца. Проверка `scale(amount) <= 2` на таком столбце не обнаружит
исходные три знака. Это нужно проверять до приведения, в нашем сервисе — на входе.

У типа `numeric` есть специальное значение `NaN`. Для полноты учебная схема явно исключает его из денежных столбцов:
обычная проверка положительности в PostgreSQL не является достаточной защитой от `NaN`.
См. [числовые типы](https://www.postgresql.org/docs/18/datatype-numeric.html).

`timestamptz` сохраняет момент времени, а не название исходного часового пояса. Отображение зависит от часового пояса
соединения. В лаборатории явно включён UTC. Для границ интервала используй литералы с `Z` или смещением, например
`'2026-10-01T00:00:00Z'::timestamptz`.
См. [типы даты и времени](https://www.postgresql.org/docs/18/datatype-datetime.html).

### 4.2. Полная схема и её границы

Открой [schema.sql](sql/schema.sql). В нём четыре временные таблицы: `client`, `account`, `transfer`, `ledger_entry`.
Они соответствуют денежному ядру требований. Таблицы идемпотентности, аудита и исходящих событий появятся на своих
этапах плана. Это учебный образец структуры, а не полная миграция готового сервиса.

Обрати внимание на решения:

- `client_id` не уникален: клиент может иметь несколько счетов, в том числе одной валюты;
- все статусы обязательны и ограничены перечислением строк;
- `description` допускает `NULL`;
- во всех таблицах с валютой пока разрешён только `RUB`;
- `version` не увеличивается сама: это поле для будущего алгоритма обновления;
- `updated_at` также не обновляется автоматически от наличия столбца;
- время и UUID в примерах заданы явно, чтобы результат был воспроизводимым.

### 4.3. Почему operation_id не ссылается на transfer

В журнале `operation_id` обозначает не только перевод, но и пополнение либо списание. Внешний ключ
`operation_id REFERENCES transfer(id)` запретил бы эти два вида операций.

В учебной схеме FK для этого поля отсутствует. Это явное ограничение модели: база пока допускает запись
`TRANSFER_IN` со ссылкой на несуществующий перевод. Для проверки таких ошибок нужен отдельный запрос.

При дальнейшем проектировании можно выбрать общую таблицу операций, на которую ссылаются журнал и сведения о
переводе, либо отдельные типизированные связи. Обычный FK не умеет выбирать таблицу назначения по `operation_type`.
Не стоит объявлять ложную связь только ради наличия ограничения.

## 5. DDL и DML

SQL объединяет команды для разных задач. Названия **DDL**, **DML** и **DQL** обозначают группы этих команд
по назначению. Это не отдельные программы и не слова, которые нужно писать перед SQL-запросом.

У таблицы есть **структура** и **содержимое**. Например, структура `account` определяет, что у счёта есть
столбцы `id`, `balance`, `status`, задаёт их типы и ограничения. Содержимое — конкретные строки счетов
с конкретными идентификаторами, балансами и статусами. Таблица может быть пустой, но её структура уже существует.

**DDL — Data Definition Language, «язык определения данных».** Это команды, которые создают, изменяют
и удаляют объекты базы: например, таблицы, их столбцы и ограничения.

| Команда        | Что делает со структурой                  | Пример задачи                                   |
|----------------|-------------------------------------------|-------------------------------------------------|
| `CREATE TABLE` | Создаёт новую таблицу                      | Определить таблицу счетов и её столбцы           |
| `ALTER TABLE`  | Меняет определение существующей таблицы    | Добавить столбец или ограничение `CHECK`         |
| `DROP TABLE`   | Удаляет таблицу вместе с её содержимым      | Удалить больше не нужную экспериментальную таблицу |

Например, добавим необязательную подпись счёта:

```sql
ALTER TABLE account ADD COLUMN label text;
```

После этой команды у таблицы есть новый столбец `label`. Для существующих строк его значение будет `NULL`,
поскольку мы не задали значение по умолчанию. Конкретную подпись конкретному счёту эта команда не назначает.
Это иллюстрация DDL, а не обязательное изменение схемы лаборатории.

**DML — Data Manipulation Language, «язык работы с данными».** Эти команды работают с содержимым таблиц.
В этом разделе под изменением данных будем понимать добавление, обновление и удаление строк:

| Команда  | Что делает со строками                       | Пример задачи                              |
|----------|----------------------------------------------|--------------------------------------------|
| `INSERT` | Добавляет новые строки                       | Сохранить новый счёт                       |
| `UPDATE` | Меняет значения в существующих строках        | Изменить статус определённого счёта         |
| `DELETE` | Удаляет строки, сохраняя определение таблицы  | Удалить тестовую запись, если позволяют связи |

После добавления столбца из примера выше можно записать подпись:

```sql
UPDATE account
SET label = 'На отпуск'
WHERE id = '20000000-0000-0000-0000-000000000001';
```

Здесь структура таблицы остаётся прежней. Меняется значение `label` в строке с указанным `id`.
Если такой строки нет, команда обновит ноль строк; новый счёт она не создаст.
Ограничения таблицы продолжают действовать: DML не позволяет обойти `NOT NULL`, `CHECK` или внешний ключ.

**DQL — Data Query Language, «язык запросов к данным».** Такое название иногда выделяют для чтения через `SELECT`:

```sql
SELECT id, label, balance
FROM account
WHERE status = 'ACTIVE';
```

Этот запрос возвращает выбранные поля активных счетов и не меняет хранимые строки. В некоторых классификациях
`SELECT` относят к DML: работа с данными включает и чтение. Поэтому встретить оба варианта нормально.

Для сравнения с TypeScript: изменение структуры таблицы отдалённо напоминает изменение описания типа объекта,
а изменение строк — изменение самих объектов. Но в базе структура и ограничения реально проверяются при записи,
тогда как типы TypeScript сами по себе не проверяют данные во время выполнения.

Особенно важно различать `DELETE FROM account` и `DROP TABLE account`. Первая команда пытается удалить все
строки, оставляя пустую таблицу со столбцами и ограничениями. Вторая пытается удалить саму таблицу вместе
с данными. Обе команды могут быть отклонены из-за связей или зависимостей.

### 5.1. Создание и изменение структуры

В лабораторной схеме используется такой фрагмент:

```sql
client_id uuid NOT NULL REFERENCES client (id) ON DELETE RESTRICT
```

Это одновременно тип столбца, обязательность значения и связь. Если убрать `NOT NULL`, FK продолжит проверять
заполненные ссылки, но позволит счёт без владельца.

Пример изменения структуры, который можно выполнить в учебной транзакции:

```sql
ALTER TABLE client
ADD CONSTRAINT client_name_not_blank CHECK (length(trim(name)) > 0);
```

Перед добавлением ограничения к существующей таблице нужно учитывать старые данные: пустое имя помешает его созданию.
В приложении такие изменения выполняются миграциями Flyway; лабораторные временные таблицы служат только для упражнений.

### 5.2. Вставка, изменение, удаление

Всегда перечисляй столбцы в `INSERT`: тогда смысл значений не зависит от физического порядка колонок.

```sql
INSERT INTO client (id, external_id, name, status, created_at, updated_at)
VALUES (
    '10000000-0000-0000-0000-000000000004',
    'customer-demo', 'Учебный клиент', 'ACTIVE',
    '2026-10-04T12:00:00Z', '2026-10-04T12:00:00Z'
)
RETURNING id, name;

UPDATE client
SET name = 'Новое имя', updated_at = '2026-10-04T12:05:00Z'
WHERE id = '10000000-0000-0000-0000-000000000004'
RETURNING id, name;

DELETE FROM client
WHERE id = '10000000-0000-0000-0000-000000000004'
RETURNING id;
```

`RETURNING` возвращает затронутые строки. `UPDATE` без совпадений не обязан быть ошибкой: результат — ноль строк.
Без `WHERE` обновление или удаление затронет все строки таблицы. Удалять учебного клиента здесь допустимо, потому что
у него нет счетов. Это демонстрация SQL, а не добавление команды удаления в публичный API.

Не реализуй перевод последовательностью независимых `UPDATE`: между ними может случиться ошибка. SQL-команды записи
нужно будет объединить транзакцией вместе с журналом, идемпотентностью и событием, а также защитить от конкуренции.

## 6. SELECT и порядок обработки

В [seed.sql](sql/seed.sql) заданы три клиента, три счёта, два перевода и семь записей журнала.
Для чтения ниже сокращаем UUID: `A1` — счёт с окончанием `0001`, `A2` — `0002`, `A3` — `0003`.

Следующая таблица — сводка исходного набора данных, а не содержимое `ledger_entry` и не результат запроса
из пункта 6.1. Здесь одна строка означает один счёт. Счёт и текущий баланс берём из `account`, имя владельца —
из `client`, а приход, расход и число записей вычисляем по `ledger_entry`.

| Счёт | Владелец | Приход | Расход | Текущий баланс | Записей журнала |
|------|----------|--------|--------|----------------|-----------------|
| A1   | Анна     | 1000   | 300    | 700            | 3               |
| A2   | Борис    | 400    | 50     | 350            | 4               |
| A3   | Анна     | 0      | 0      | 0              | 0               |

У Веры счетов нет. В приход A2 входят пополнение на 100 и два входящих перевода на 250 и 50.

Для A1 в журнале три суммы: `+1000`, `-250`, `-50`. Приход равен `1000`, расход — `250 + 50 = 300`.
Для A2 четыре суммы: `+100`, `+250`, `-50`, `+50`. Приход — `100 + 250 + 50 = 400`, расход — `50`.
У A3 записей журнала нет, но сам счёт существует, поэтому он тоже показан в сводке.

Ниже запрос, который воспроизводит эту сводку (идентификаторы возвращаются полными UUID).
Он использует соединения и агрегаты, которые подробно разбираются в [разделе 8](#joins)
и [разделе 9](#aggregates); для простого чтения истории в пункте 6.1 они пока не нужны.

```sql
SELECT a.id AS account_id,
       c.name AS owner,
       coalesce(sum(e.amount) FILTER (WHERE e.amount > 0), 0) AS incoming,
       coalesce(-sum(e.amount) FILTER (WHERE e.amount < 0), 0) AS outgoing,
       a.balance AS current_balance,
       count(e.id) AS entry_count
FROM account a
JOIN client c ON c.id = a.client_id
LEFT JOIN ledger_entry e ON e.account_id = a.id
GROUP BY a.id, c.name, a.balance
ORDER BY a.id;
```

Начинаем со счетов, добавляем владельца и записи истории, затем собираем записи каждого счёта в одну итоговую
строку. `LEFT JOIN` сохраняет A3 без истории, `count(e.id)` для него даёт 0, а `coalesce` заменяет отсутствующие
суммы нулями. Текущий баланс здесь читается из `account.balance`, а не рассчитывается этим запросом.

### 6.1. История операций

```sql
SELECT id, operation_type, amount, balance_after, created_at
FROM ledger_entry
WHERE account_id = '20000000-0000-0000-0000-000000000001'
  AND created_at >= '2026-10-01T00:00:00Z'::timestamptz
  AND created_at <  '2026-10-04T00:00:00Z'::timestamptz
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 0;
```

Результат для A1: `-50 / 700`, `-250 / 750`, `+1000 / 1000`, где после косой черты указан баланс после операции.
Второй ключ сортировки обеспечивает однозначный порядок при совпадении времени. Без `ORDER BY` «последних 20» нет.

Интервал `[начало, конец)` включает начало и исключает конец. Соседние интервалы не пересекаются. `BETWEEN`
включает обе границы и для последовательных временных периодов легко приводит к двойному учёту граничной записи.

`LIMIT` ограничивает результат; большой `OFFSET` сам по себе не делает получение глубокой страницы дешёвым.
Кроме того, новые записи между запросами могут сдвигать страницы. Подробное решение — на неделе 12.

### 6.2. Логический порядок

Для изучаемых запросов удобно рассуждать так:

```text
FROM / JOIN → WHERE → GROUP BY → HAVING → оконные вычисления
→ выражения SELECT → DISTINCT → ORDER BY → LIMIT / OFFSET
```

Это модель смысла запроса, а не точный план его физического выполнения.
Она объясняет, почему псевдоним из `SELECT` нельзя использовать в `WHERE` того же уровня:

```sql
-- Так нельзя: signed_amount ещё не определён для WHERE.
SELECT amount AS signed_amount
FROM ledger_entry
WHERE signed_amount < 0;
```

Исправление — `WHERE amount < 0` или внешний запрос. В `ORDER BY` псевдоним результата использовать можно.

`DISTINCT` удаляет одинаковые строки по всем выбранным выражениям. Он полезен, когда нужен именно набор уникальных
значений, но не исправляет неверное соединение. Особенно опасно лечить ошибочную сумму через `SUM(DISTINCT amount)`:
две реальные операции на одинаковую сумму тогда будут посчитаны как одна.

## 7. NULL и трёхзначная логика

`NULL` — отсутствие значения. Это не ноль, не пустая строка и не JavaScript `undefined`.
Сравнение с неизвестным значением обычно даёт `UNKNOWN`, а не `TRUE` или `FALSE`.

| Выражение                           | Результат |
|-------------------------------------|-----------|
| `NULL = NULL`                       | `UNKNOWN` |
| `NULL <> 10`                        | `UNKNOWN` |
| `NULL IS NULL`                      | `TRUE`    |
| `FALSE AND NULL`                    | `FALSE`   |
| `TRUE AND NULL`                     | `UNKNOWN` |
| `TRUE OR NULL`                      | `TRUE`    |
| `NOT NULL` как логическое выражение | `UNKNOWN` |

Последняя строка — отрицание неизвестного логического значения, а не объявление ограничения столбца.
`WHERE` оставляет только строки, где условие равно `TRUE`.

```sql
SELECT id FROM transfer WHERE description IS NULL;
SELECT id FROM transfer WHERE description IS NOT NULL;
```

Первый запрос найдёт перевод на 250, второй — на 50. Условие `description = NULL` не найдёт ни одного.
`description <> 'Возврат за обед'` тоже не вернёт строку с `NULL`. Если нужны все остальные значения, включая отсутствие:

```sql
SELECT id
FROM transfer
WHERE description IS DISTINCT FROM 'Возврат за обед';
```

Для отображения можно использовать `coalesce(description, 'Без назначения')`. Это выбирает первое значение,
отличное от `NULL`; пустая строка при этом останется пустой.
См. [операторы сравнения](https://www.postgresql.org/docs/18/functions-comparison.html).

Есть два важных отличия ограничений от фильтра:

- `CHECK` отвергает `FALSE`, но допускает неизвестный результат. Поэтому `CHECK(amount > 0)` без `NOT NULL`
  разрешит отсутствующую сумму;
- обычный `UNIQUE` в PostgreSQL допускает несколько `NULL`. Для обязательного уникального поля нужны и `UNIQUE`,
  и `NOT NULL`.

Ещё одна ловушка:

```sql
SELECT 42 NOT IN (1, NULL); -- UNKNOWN, а не TRUE
```

Если подзапрос справа от `NOT IN` может вернуть `NULL`, проверка отсутствия совпадений станет неожиданной.
Для поиска счетов без операций ниже используем `NOT EXISTS`.

## 8. JOIN: соединение таблиц и число строк

### 8.1. INNER JOIN

```sql
SELECT a.id, c.name, a.balance
FROM account a
JOIN client c ON c.id = a.client_id
ORDER BY a.id;
```

`a` и `c` — псевдонимы таблиц. `JOIN` без уточнения означает `INNER JOIN`: остаются только совпавшие пары.
Здесь будут три строки, потому что у каждого счёта ровно один существующий владелец. Счета Анны дадут две разные строки.

Теперь соединим счета и журнал:

```sql
SELECT a.id, e.operation_type, e.amount
FROM account a
JOIN ledger_entry e ON e.account_id = a.id
ORDER BY a.id, e.created_at, e.id;
```

Будет семь строк: три для A1 и четыре для A2. A3 исчезнет. `JOIN` возвращает пары совпадений, а не «один объект
со вложенным массивом». Поэтому `SUM(a.balance)` после такого соединения даст `700 × 3 + 350 × 4 = 3500`,
хотя общий баланс счетов равен 1050.

### 8.2. LEFT JOIN и фильтр в ON

```sql
SELECT a.id, e.operation_type, e.amount
FROM account a
LEFT JOIN ledger_entry e
  ON e.account_id = a.id
 AND e.operation_type = 'DEPOSIT'
ORDER BY a.id;
```

Получим три строки: A1 с 1000, A2 со 100 и A3 с `NULL` в полях журнала. `LEFT JOIN` сохраняет все строки слева,
даже если подходящих справа нет.

Если перенести `e.operation_type = 'DEPOSIT'` в `WHERE`, A3 исчезнет: после соединения у него значение `NULL`,
а сравнение не даёт `TRUE`. Условие в `ON` определяет совпадения; `WHERE` фильтрует уже полученные строки.
Это различие разбирается в [табличных выражениях PostgreSQL](https://www.postgresql.org/docs/18/queries-table-expressions.html).

### 8.3. Два соединения одной таблицы

```sql
SELECT t.id, sender.client_id AS sender_client_id,
       recipient.client_id AS recipient_client_id, t.amount
FROM transfer t
JOIN account sender ON sender.id = t.source_account_id
JOIN account recipient ON recipient.id = t.target_account_id
ORDER BY t.created_at, t.id;
```

Два псевдонима выражают две роли. Каждое соединение идёт по уникальному `account.id`, поэтому перевод не размножается.

Если же одновременно присоединить к счёту все его записи журнала и все исходящие переводы, для A1 получится
`3 × 2 = 6` строк. Перед соединением независимых связей «один ко многим» сначала агрегируй каждую сторону до одной
строки на счёт либо используй `EXISTS`, если нужен только факт наличия.

`RIGHT JOIN` сохраняет правую сторону, `FULL JOIN` — обе стороны, `CROSS JOIN` создаёт все пары.
Для повседневных запросов нашего проекта чаще достаточно `INNER JOIN`, `LEFT JOIN` и `EXISTS`.

## 9. Агрегаты и обороты

### 9.1. GROUP BY, COUNT, SUM и HAVING

`GROUP BY` собирает строки с одинаковыми значениями ключей группы. Обычный агрегат возвращает одно значение
на группу. `COUNT(*)` считает строки, `COUNT(column)` — непустые значения столбца; `SUM`, `AVG`, `MIN`, `MAX`
принимают значения для соответствующего расчёта.

```sql
SELECT account_id, count(*) AS entry_count, sum(amount) AS net_change
FROM ledger_entry
WHERE created_at >= '2026-10-01T00:00:00Z'::timestamptz
  AND created_at <  '2026-10-04T00:00:00Z'::timestamptz
GROUP BY account_id
HAVING count(*) >= 4
ORDER BY account_id;
```

`WHERE` отбирает записи периода, затем формируются группы, а `HAVING` отбирает группы. Результат — только A2:
четыре записи и изменение 350. `WHERE count(*) >= 4` на этом уровне запроса недопустим.

В агрегированном результате каждое выбранное поле должно быть либо ключом группы, либо агрегатом, либо однозначно
зависеть от ключа так, чтобы СУБД распознавала эту зависимость. В учебных примерах явно перечисляем нужные поля
в `GROUP BY`, чтобы видеть структуру результата.

### 9.2. Приход и расход, включая пустые счета

```sql
SELECT a.id, a.currency, count(e.id) AS entry_count,
       coalesce(sum(e.amount) FILTER (WHERE e.amount > 0), 0) AS incoming,
       coalesce(-sum(e.amount) FILTER (WHERE e.amount < 0), 0) AS outgoing
FROM account a
LEFT JOIN ledger_entry e ON e.account_id = a.id
GROUP BY a.id, a.currency
ORDER BY a.id;
```

`FILTER` отбирает строки для конкретного агрегата. Расход возвращаем положительной величиной, поэтому перед суммой
отрицательных значений стоит минус. Альтернативная запись прихода:
`SUM(CASE WHEN e.amount > 0 THEN e.amount ELSE 0 END)`.

Для A3 после `LEFT JOIN` есть одна строка с пустыми полями журнала. Поэтому `COUNT(*)` дал бы 1,
а `COUNT(e.id)` правильно даёт 0. `SUM` по пустому набору возвращает `NULL`; `COALESCE` заменяет его нулём.
См. [агрегатные функции](https://www.postgresql.org/docs/18/functions-aggregate.html).

Чтобы считать обороты за период и сохранить пустые счета, добавь ограничения `e.created_at` в `ON`.
Перенос этих условий в `WHERE` снова уберёт счета без подходящих записей.

### 9.3. Что именно означает итоговая сумма

Для A1 приход 1000 и расход 300. Для A2 приход 400 и расход 50. Это обороты **по счетам**, а не объём внешних
денег, поступивших в систему: входящие переводы тоже входят в приход получателя.

На всём наборе:

- внешние пополнения: 1100;
- административные списания: 50;
- сумма успешно выполненных переводов в `transfer`: 300;
- сумма всех знаковых изменений журнала: 1050;
- `SUM(ABS(amount))` только для записей переводов: 600, поскольку каждый перевод отражён с двух сторон.

Сначала дай определение показателю, затем выбирай таблицу и формулу. Термин «оборот» без определения может означать
разные числа. При появлении нескольких валют группируй по валюте; общая сумма RUB и другой валюты не имеет смысла
без явно заданного преобразования.

## 10. Подзапросы, EXISTS и WITH

### 10.1. Проверка наличия без размножения строк

```sql
SELECT a.id
FROM account a
WHERE NOT EXISTS (
    SELECT 1
    FROM ledger_entry e
    WHERE e.account_id = a.id
)
ORDER BY a.id;
```

Это запрос счетов без операций: вернётся A3. Подзапрос связан с внешней строкой через `a.id`.
`EXISTS` проверяет наличие хотя бы одной строки; `SELECT 1` подчёркивает, что её поля нам не нужны.
Замена на `EXISTS` даст A1 и A2, по одному разу независимо от числа операций.

Для клиента без счетов применяется та же конструкция между `client` и `account`; на наборе это Вера.

### 10.2. Именованный промежуточный результат

`WITH` объявляет CTE — именованный результат запроса в пределах одной SQL-команды:

```sql
WITH totals AS (
    SELECT account_id, sum(amount) AS ledger_balance
    FROM ledger_entry
    GROUP BY account_id
)
SELECT a.id, a.balance, coalesce(t.ledger_balance, 0) AS ledger_balance
FROM account a
LEFT JOIN totals t ON t.account_id = a.id
ORDER BY a.id;
```

В `totals` уже одна строка на счёт. Поэтому соединение не повторяет `a.balance`. CTE помогает разделить мысль на
этапы, но само наличие `WITH` не обещает ускорения или отдельной сохранённой таблицы.

Для сверки добавь `WHERE a.balance <> coalesce(t.ledger_balance, 0)`: правильный набор даст ноль строк.
Предпосылка сверки — вся история от нулевого начального баланса доступна в журнале. Если старые записи перенесены
в архив, нужно учитывать начальное сальдо.

## 11. Оконные функции

### 11.1. Сохранить строки и добавить расчёт

[Подробный разбор `row_number()`: нумерация по шагам, `OVER` и два `ORDER BY`](sql/row-number.md).

Агрегация по счёту сворачивает его журнал в одну строку. Оконное вычисление сохраняет каждую запись и добавляет
результат, рассчитанный по связанным строкам. Например, можно показать запись и её порядковый номер внутри счёта.

```sql
SELECT account_id, id, amount,
       row_number() OVER (
           PARTITION BY account_id
           ORDER BY created_at DESC, id DESC
       ) AS position
FROM ledger_entry
ORDER BY account_id, position;
```

`PARTITION BY` начинает нумерацию заново для каждого счёта. `ORDER BY` внутри `OVER` задаёт порядок вычисления,
внешний `ORDER BY` — порядок выдачи результата.

`ROW_NUMBER` даёт разные номера даже при равных значениях сортировки. `RANK` даёт равным значениям одинаковое место
и оставляет пропуски после них; `DENSE_RANK` не оставляет пропусков. Для двух последних равенство определяется всеми
выражениями оконной сортировки: добавление уникального `id` устранит ничьи.

### 11.2. Последняя операция каждого счёта

```sql
WITH numbered AS (
    SELECT e.*, row_number() OVER (
        PARTITION BY account_id ORDER BY created_at DESC, id DESC
    ) AS position
    FROM ledger_entry e
)
SELECT account_id, operation_type, balance_after
FROM numbered
WHERE position = 1
ORDER BY account_id;
```

Внешний запрос нужен, потому что `WHERE` того же уровня выполняется до оконного вычисления.
Получим последнюю запись A1 с балансом 700 и A2 с балансом 350. A3 отсутствует: оконная функция не создаёт
записи для счетов без истории. Чтобы включить A3, соединяй результат с `account` через `LEFT JOIN`.
См. [введение в оконные функции](https://www.postgresql.org/docs/18/tutorial-window.html).

### 11.3. Накопленная сумма и рамка окна

```sql
SELECT account_id, id, amount, balance_after,
       sum(amount) OVER (
           PARTITION BY account_id
           ORDER BY created_at, id
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS calculated_balance
FROM ledger_entry
ORDER BY account_id, created_at, id;
```

Здесь рамка означает «от первой строки счёта до текущей включительно». Для A1 суммы равны 1000, 750, 700;
для A2 — 100, 350, 300, 350. На нашем полном и последовательно заданном наборе они совпадают с `balance_after`.

Без явной рамки при наличии оконного `ORDER BY` стандартное поведение PostgreSQL включает также строки,
равные текущей по значениям сортировки. С одним `created_at` несколько записей одинакового времени могут получить
сразу общий итог. Явные `ROWS` и однозначный порядок делают учебное накопление понятнее.

Если поставить `WHERE created_at >= '2026-10-02T00:00:00Z'` перед этим окном, начальные пополнения исчезнут
из расчёта. Для A1 первая сумма станет -250 вместо 750. Чтобы сначала вычислить баланс по полной истории,
а потом показать период, вынеси расчёт в CTE и фильтруй во внешнем запросе.

Даже тогда сортировка по времени и UUID — лишь принятый порядок отчёта. Для проверки промежуточных балансов при
конкурентных записях нужна зафиксированная последовательность операций по счёту. Сумма всей истории от порядка
не зависит, а промежуточные суммы зависят.

### 11.4. Значение предыдущей строки

```sql
SELECT account_id, id, balance_after,
       lag(balance_after) OVER (
           PARTITION BY account_id ORDER BY created_at, id
       ) AS previous_balance
FROM ledger_entry
ORDER BY account_id, created_at, id;
```

`LAG` даёт значение предыдущей строки, для первой — `NULL`, если не задано другое значение по умолчанию.
На учебном наборе можно проверить `balance_after - previous_balance = amount` со второй записи.
Подстановка нуля вместо отсутствующего предыдущего баланса корректна только при известном нулевом начале истории.

## 12. Модель API и модель хранения

Ответ API может быть собран из нескольких таблиц и вычислений. Таблица не обязана один к одному повторять JSON,
а DTO ответа не обязано содержать все столбцы таблицы.

| Задача API                             | Что делает запрос                                           |
|----------------------------------------|-------------------------------------------------------------|
| Получить счёт                          | Читает нужные поля `account`                                |
| Показать счёт с именем владельца       | Соединяет `account` и `client`                              |
| Получить историю счёта                 | Фильтрует `ledger_entry`, сортирует, ограничивает результат |
| Показать назначение перевода в истории | Дополняет запись журнала данными `transfer`                 |
| Показать обороты                       | Группирует записи за период                                 |

Для истории с назначением перевода:

```sql
SELECT e.id, e.operation_type, e.amount, t.description
FROM ledger_entry e
LEFT JOIN transfer t
  ON t.id = e.operation_id
 AND e.operation_type IN ('TRANSFER_IN', 'TRANSFER_OUT')
WHERE e.account_id = '20000000-0000-0000-0000-000000000001'
ORDER BY e.created_at DESC, e.id DESC;
```

Здесь нужен `LEFT JOIN`: пополнение не имеет строки в `transfer`, но должно оставаться в истории.
У `NULL` в `description` теперь может быть несколько причин: это не перевод, перевод без описания или повреждённая
ссылка на перевод. Для диагностики смотри также `operation_type` и `t.id`.

Фильтр по переданному `account_id` сам по себе не проверяет право пользователя читать этот счёт. В полном сервисе
должна быть проверка владельца или роли. Если список отфильтрован по владельцу и периоду, запрос общего количества
для пагинации должен применять те же условия.

Не загружай все строки через `findAll()` ради фильтрации в Java. База должна возвращать нужный объём данных.
Значения пользователя далее будут передаваться параметрами JDBC, а не конкатенацией SQL. Поля сортировки выбираются
из разрешённого списка: параметр значения не подставляет SQL-имя столбца.

Нужны работающий PostgreSQL и клиент `psql` либо SQL-консоль редактора. Настройка сервера через Docker Compose
будет на неделе 10. Для команд ниже один раз создай учебную базу `wallet_learning` и пользователя
`wallet_student` по инструкции ниже. Если у тебя уже есть отдельная учебная база, можно использовать её имена.

#### Создание учебной базы и пользователя

Эти шаги предполагают, что сервер PostgreSQL уже установлен и запущен. Создание базы не устанавливает сервер.
В PowerShell подключись под администратором PostgreSQL (обычно это роль `postgres`, созданная при установке):

```powershell
psql -X -h localhost -p 5432 -U postgres -d postgres
```

Здесь `-h` — адрес сервера, `-p` — порт, `-U` — пользователь PostgreSQL, `-d` — существующая база для
начального подключения. Если параметры установки отличаются, подставь свои. При запросе пароля введи пароль
администратора PostgreSQL, заданный при установке, а не пароль Windows.

В открывшейся консоли `psql` последовательно выполни:

```sql
CREATE ROLE wallet_student LOGIN;
```

```text
\password wallet_student
```

Команда `\password` попросит дважды ввести новый пароль учебного пользователя. Это команда `psql`,
точка с запятой ей не нужна. Пароль не требуется записывать в SQL-файл.

Затем выполни:

```sql
CREATE DATABASE wallet_learning OWNER wallet_student;
```

В PostgreSQL пользователь — роль с правом `LOGIN`. Роль создаётся на уровне экземпляра PostgreSQL,
а не внутри одной базы. `OWNER` назначает её владельцем новой учебной базы; выдавать ей `SUPERUSER`
для лаборатории не нужно. Подробнее: [CREATE ROLE](https://www.postgresql.org/docs/18/sql-createrole.html).

Выполняй `CREATE DATABASE` отдельно, без `BEGIN`: эта команда не допускается внутри блока транзакции.
В SQL-консоли редактора для неё должна быть включена автоматическая фиксация.
См. [CREATE DATABASE](https://www.postgresql.org/docs/18/sql-createdatabase.html).

Выйди из административного подключения командой `\q`, затем в PowerShell подключись учебным пользователем:

```powershell
psql -X -h localhost -p 5432 -U wallet_student -d wallet_learning
```

Введи заданный ему пароль и проверь подключение:

```sql
SELECT current_user, current_database();
```

Ожидаются `wallet_student` и `wallet_learning`. Теперь можно выполнять интерактивные шаги лаборатории ниже.
Для запуска файла из PowerShell сначала выйди из `psql` через `\q`.

Если что-то не получилось:

- `psql` не распознана как команда: клиент отсутствует в `PATH` или не установлен. На Windows можно запустить
  установленную программу SQL Shell (psql) либо вызвать `psql.exe` полным путём. Например,
  `& 'C:\Program Files\PostgreSQL\18\bin\psql.exe' -X -h localhost -U postgres -d postgres`,
  если PostgreSQL действительно установлен в этой папке; номер версии и путь могут отличаться.
- `connection refused`: проверь, запущен ли сервер и верны ли адрес и порт.
- `password authentication failed`: проверь имя роли и её пароль.
- `already exists`: объект с таким именем уже создан; повторно создавать его не нужно. Проверь владельца базы
  командой `\l wallet_learning` и роль командой `\du wallet_student` в `psql`.

#### Запуск готового скрипта

Из корня репозитория в PowerShell:

```powershell
psql -X -h localhost -U wallet_student -d wallet_learning -f lerning-materials/week-09/sql/laboratory.sql
```

Команды с обратной косой чертой — команды клиента `psql`, не SQL. `\ir` загружает файл относительно текущего скрипта.
`ON_ERROR_STOP` прекращает пакетное выполнение при ошибке. Скрипт создаёт временные таблицы в текущем соединении,
читает их и выполняет `ROLLBACK`. Он не создаёт постоянную схему приложения.

Для самостоятельных запросов открой интерактивное соединение из корня репозитория:

```powershell
psql -X -h localhost -U wallet_student -d wallet_learning
```

Затем внутри `psql`:

```sql
BEGIN;
SET LOCAL search_path = pg_temp;
SET LOCAL TIME ZONE 'UTC';
\i lerning-materials/week-09/sql/schema.sql
\i lerning-materials/week-09/sql/seed.sql
-- Здесь выполняй свои SELECT и задания.
-- В конце:
ROLLBACK;
```

В редакторе SQL выполни `BEGIN`, две команды `SET LOCAL`, содержимое `schema.sql`, `seed.sql` и свои запросы
в **одном соединении**, затем `ROLLBACK`. `ON COMMIT DROP` означает удаление временных таблиц при фиксации:
не запускай создание таблиц по одной команде с автоматической фиксацией.

### 13.2. Как исследовать нарушение ограничения

Внутри уже открытой учебной транзакции:

```sql
SAVEPOINT before_invalid_update;

UPDATE account
SET balance = -1.00
WHERE id = '20000000-0000-0000-0000-000000000001';
-- Ожидаем ошибку account_balance_valid.

ROLLBACK TO SAVEPOINT before_invalid_update;
```

После ошибки PostgreSQL не продолжает обычные команды в той же транзакции до отката. Точка сохранения позволяет
откатить только эксперимент. Выполняй эти шаги интерактивно: скрипт с `ON_ERROR_STOP` остановится на ожидаемой ошибке.

### 13.3. Что проверять в результатах

Первые четыре запроса в `queries.sql` показывают историю, обороты, последние записи и накопленные суммы.
Последние два ищут расхождения текущих балансов и неправильный состав записей переводов; ожидается ноль строк.

Проверка переводов начинается с `transfer` и замечает в том числе перевод вообще без записей. Но она не видит
«осиротевшие» записи журнала со ссылкой на несуществующий перевод. Обратная проверка вынесена в практику.
Ноль строк в одной диагностике не означает выполнение всех бизнес-правил сервиса.

## 14. Маршрут на неделю и самопроверка

1. **Модель и ограничения, 1,5–2 часа.** Прочитай разделы 1–4, нарисуй связи и объясни каждый ключ в `schema.sql`.
2. **Базовый SQL, 1,5–2 часа.** Пройди разделы 5–8; перед запуском каждого запроса предскажи число строк.
3. **Отчёты, 2–3 часа.** Пройди агрегаты и окна, затем выполни [практику](../../src/main/java/com/example/exercises/week_9/questions.md).
4. **Закрепление, 1–2 часа.** Найди в рабочем backend одну таблицу и один запрос; объясни их ограничения и кратность
   соединений без изменения рабочего кода или данных.

Ты освоил неделю, если можешь без подсказки:

- выбрать PK, FK, `UNIQUE`, `NOT NULL` и `CHECK` для денежной модели;
- объяснить, какие аномалии устраняет разделение клиента и счёта;
- предсказать, где `JOIN` размножит строки, а где потеряет пустой счёт;
- различить `WHERE`, `HAVING` и фильтрацию после оконного вычисления;
- посчитать приход и расход с нулевыми значениями для пустых счетов;
- получить последнюю операцию каждого счёта;
- объяснить, почему `NULL`, отсутствие строки и сумма 0 — разные ситуации;
- назвать правила кошелька, которые показанный DDL не обеспечивает.
