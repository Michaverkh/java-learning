# ROW_NUMBER(): порядковый номер строки в результате запроса

[← Пункт 11.1: оконные функции](../relational-model-and-sql.md#windows) ·
[← Учебный план](../../java-backend-learning-plan.md)

## Что это за функция

`row_number()` — встроенная оконная функция SQL. Она присваивает каждой строке порядковый номер:
1, 2, 3 и так далее. Нумерация начинается с 1 внутри каждой группы, заданной в `OVER`.

Это вычисляемое значение результата `SELECT`: функция не добавляет столбец в таблицу, не изменяет записи
и не создаёт постоянный идентификатор. После добавления новых записей номера при следующем запросе могут измениться.
В PostgreSQL возвращаемый тип — `bigint`.

В отличие от `lower(name)`, которая преобразует значение конкретной строки, `row_number()` должна знать положение
строки относительно других строк. Поэтому ей нужна конструкция `OVER`: она задаёт контекст вычисления.
Скобки `()` пустые, потому что передавать значение столбца самой функции не нужно.

## Разбираем выражение из пункта 11.1

```sql
SELECT account_id, id, amount,
       row_number() OVER (
           PARTITION BY account_id
           ORDER BY created_at DESC, id DESC
       ) AS position
FROM ledger_entry
ORDER BY account_id, position;
```

Всё выражение от `row_number()` до `AS position` создаёт один столбец результата.
`position` — его произвольное имя: можно было назвать его `entry_number`.

| Часть выражения                         | Значение                                                      |
|----------------------------------------|---------------------------------------------------------------|
| `row_number()`                         | Вычислить порядковый номер текущей строки                      |
| `OVER (...)`                           | Задать, среди каких строк и в каком порядке считать номер      |
| `PARTITION BY account_id`              | Нумеровать записи каждого счёта отдельно                       |
| `ORDER BY created_at DESC, id DESC`     | Сначала более позднее время; при равенстве — больший `id`       |
| `AS position`                          | Назвать вычисленный столбец `position`                         |

Читать выражение можно так: «Для каждой записи найди её место среди записей того же счёта,
упорядоченных по убыванию времени и идентификатора».

## Пошаговый пример

Для наглядности используем короткие обозначения счетов и целочисленные идентификаторы.
В таблицах проекта используются UUID; принцип нумерации тот же. Все времена ниже относятся к одному дню.

Исходные данные:

| account_id | id | created_at | amount |
|------------|----|------------|--------|
| A1         | 11 | 10:00      | 1000   |
| A2         | 21 | 09:00      | 500    |
| A1         | 12 | 11:00      | -200   |
| A1         | 13 | 11:00      | -50    |
| A2         | 22 | 12:00      | -100   |

**Шаг 1. Разделить строки по `account_id`.** Получатся две независимые группы:

```text
A1: записи 11, 12, 13
A2: записи 21, 22
```

`PARTITION BY` здесь означает логическое разделение строк для вычисления. Оно не создаёт отдельных таблиц
и не относится к физическому секционированию таблицы.

**Шаг 2. Определить порядок внутри каждой группы.** `DESC` означает убывание.
У A1 записи 12 и 13 имеют одинаковое время, поэтому сравниваем `id`: 13 идёт перед 12.

```text
A1: 13 → 12 → 11
A2: 22 → 21
```

**Шаг 3. Присвоить номера, начиная с 1 в каждой группе.**

```text
A1: 13 → номер 1; 12 → номер 2; 11 → номер 3
A2: 22 → номер 1; 21 → номер 2
```

**Шаг 4. Вывести результат в порядке внешнего `ORDER BY account_id, position`.**

| account_id | id | amount | position |
|------------|----|--------|----------|
| A1         | 13 | -50    | 1        |
| A1         | 12 | -200   | 2        |
| A1         | 11 | 1000   | 3        |
| A2         | 22 | -100   | 1        |
| A2         | 21 | 500    | 2        |

Было пять строк, осталось пять. Суммы не складывались, строки не сворачивались.
Это логическое объяснение результата, а не обязательный алгоритм выполнения внутри СУБД.

## Почему ORDER BY указан дважды

Внутри `OVER` сортировка определяет **какой номер получит строка**.
В конце запроса сортировка определяет **в каком порядке пользователь увидит строки**.

Например, заменим только последнюю строку запроса:

```sql
ORDER BY account_id, position DESC;
```

Теперь строки A1 появятся в порядке `11, 12, 13`, а номера рядом с ними будут `3, 2, 1`.
Номера не пересчитываются из-за изменения порядка вывода.

Без внешнего `ORDER BY` гарантированного порядка вывода нет, даже если внутри `OVER` сортировка задана.

## Что будет, если убрать части OVER

Без `PARTITION BY` все строки образуют одну группу:

```sql
row_number() OVER (ORDER BY created_at DESC, id DESC)
```

В нашем примере записи получат номера так: `22 → 1`, `13 → 2`, `12 → 3`, `11 → 4`, `21 → 5`.
Нумерация больше не начинается заново для каждого счёта.

В PostgreSQL допустимо убрать и сортировку:

```sql
row_number() OVER ()
```

Номера будут присвоены, но соответствие строк номерам не определено. Для выбора последних операций такой вариант
не подходит. Внешняя сортировка не заменяет сортировку внутри `OVER`.

## Одинаковое время и роль id

Если оставить только `ORDER BY created_at DESC`, записи 12 и 13 всё равно получат разные номера 1 и 2.
Но какая из них получит 1, запрос не определяет. Нельзя полагаться на порядок вставки или наблюдаемый порядок одного запуска.

Уникальный `id` устраняет эту неоднозначность. При неизменном наборе данных и тех же значениях сортировки
нумерация будет однозначной.

Однако для UUID «больше» не означает «операция произошла позже». Здесь `id` служит дополнительным правилом
сравнения при равном времени. Если требуется восстановить фактическую последовательность операций по счёту,
её нужно хранить явно. Нумерация по времени и UUID сама такую последовательность не восстанавливает.

## На какие строки действует функция

В этом простом запросе логический порядок такой:

```text
FROM → WHERE (если есть) → оконное вычисление → итоговый ORDER BY
```

Если до вычисления оставить только списания через `WHERE amount < 0`, пополнения не получат номера вообще.
Для A1 останутся записи 13 и 12 с номерами 1 и 2, для A2 — запись 22 с номером 1.
Это номера среди отобранных списаний, а не позиции в полной истории.

Условие `WHERE position = 1` на том же уровне запроса не работает: оконное значение ещё не вычислено.
Запись `WHERE row_number() OVER (...) = 1` тоже недопустима. Нужен внешний запрос, как в
[пункте 11.2](../relational-model-and-sql.md#windows): внутренний запрос присваивает номера,
а внешний отбирает строки с нужными номерами. `position <= 3` таким способом даст до трёх записей каждого счёта;
обычный `LIMIT 3` ограничивает весь результат тремя строками.

Номера вычисляются по строкам, дошедшим до окна. Если соединение таблиц размножило записи журнала,
`row_number()` пронумерует и эти повторения; функция не устраняет дубликаты.

## Аналогия с TypeScript

Для уже отобранных записей **одного счёта**, упорядоченных по нужным полям, идея похожа на:

```ts
const numbered = sortedEntries.map((entry, index) => ({
  ...entry,
  position: index + 1,
}));
```

`PARTITION BY` означает, что такую нумерацию выполняют независимо для каждого счёта.
Это аналогия результата, а не утверждение, что PostgreSQL выполняет `map` или загружает данные в приложение.

## Не путать с другими вычислениями

| Выражение                              | Что получится                                                |
|----------------------------------------|--------------------------------------------------------------|
| `row_number() OVER (...)`              | Порядковый номер каждой строки                                |
| `count(*) OVER (PARTITION BY account_id)` | Число записей счёта рядом с каждой его записью              |
| `sum(amount)` с `GROUP BY account_id`  | Одна строка с суммой на каждый счёт                           |

В примере для A1 оконный `count(*)` дал бы `3, 3, 3`, а `row_number()` даёт `1, 2, 3`.
Отличия от `rank()` и `dense_rank()` уже приведены в пункте 11.1; накопленная сумма и рамка окна разобраны в 11.3.
Для `row_number()` рамка не определяет нумерацию: важны разделение на группы и порядок внутри группы.
